# 카이로 에셋 계약 — 설계 스펙

날짜: 2026-08-17 · 상태: 리뷰 대기
전제 문서: `docs/kairo-pivot-decisions.md` (확정 결정 17건) · `docs/design.md` (게임 설계 v4)
기계 판독본: **`assets/kairo-asset-contract.json`** — 이 문서와 같은 숫자를 담은 SSoT

## 0. 이 스펙이 정하는 것

카이로소프트(워터파크 스토리) 방식으로 전면 전환하면서 **에셋을 먼저 확정한다**.
기능보다 에셋이 먼저인 이유는 하나다 — 지금까지 세 번 갈아엎은 원인이 전부
"에셋 규격이 화면·타일·카메라 중 무엇에 묶였는지 불명확"이었기 때문이다.
규격이 흔들리면 뽑아 둔 그림이 전부 폐기된다 (직전에 yaw20 규격 11장을 버렸다).

정하는 것: 투영과 스케일 · 손님 표현 · 벽 타일셋 · 시설 73종의 크기와 슬롯 · 배경 2겹 ·
품질 게이트 · 파일 계약.

**정하지 않는 것** (후속 스펙): 배치 UI, 벽 도달 검사 알고리즘, 견인 루프 시뮬,
계절 전환 로직, 밸런싱 수치.

## 1. 투영과 스케일 — 1 월드 = 1 텍셀

이 절이 스펙의 핵심이다. 나머지는 여기서 파생된다.

### 확정 수치

| 항목 | 값 | 근거 |
|---|---|---|
| yaw | **45°** | 두 지면축의 화면 기울기가 같아진다 (대칭) |
| elev | **30°** | `sin 30° = 0.5` 정확 → 화면 기울기 **정확히 1:2** |
| 타일 한 변 | **22.627417 월드** (= 32/√2) | §1.1 |
| 타일 다이아몬드 | **32 × 16 텍셀** | 카이로 실측 (Pool Slide Story: 1280px 화면 / 40타일) |
| **1 월드 단위** | **= 1 텍셀** | 위에서 파생 |
| 격자 한 걸음 | **화면 (16, 8) 텍셀 — 정수** | 검산 완료 |
| 카메라 zoom | **1.0 고정, 영구히** | §1.3 |
| 손님 키 | **24 텍셀** (타일 높이 1.5배) | 카이로 실측 |

### 1.1 타일 한 변을 22.627 로 잡는 이유

다이아몬드 가로폭을 32 텍셀로 두면 타일 한 변 = 32/√2 = 22.627 월드가 된다.
이때 격자 한 걸음의 화면 이동량은

```
+X 한 걸음 → ( +16, +8 ) 텍셀
+Z 한 걸음 → ( -16, +8 ) 텍셀
```

**정확한 정수다.** 이게 전부다 — 격자 좌표를 몇 번 더해도 텍셀 격자에서 벗어나지 않는다.
소수 누적이 없으니 스프라이트가 반 픽셀 밀려 흐려지는 일이 구조적으로 불가능하다.

그리고 월드 단위와 텍셀이 1:1 이므로 **"스프라이트 폭 48텍셀"과 "월드 폭 48"이 같은 숫자**다.
`TEXEL_WORLD`, `WORLD_PER_PX`, `MIN_DETAIL` 같은 변환 상수가 전부 사라진다.
이 변환들을 헷갈려 로지를 1.9배로 키운 버그가 있었다 — 그 버그 종류가 소멸한다.

### 1.2 화면에 담기는 양

렌더 버퍼(텍셀) = `ceil(CSS 크기 / S)`, 카메라 절두체(월드) = 버퍼 크기와 동일.

| 업스케일 S | 버퍼 (393×852 폰) | 가로 타일 | 쓰임 |
|---|---|---|---|
| **1** (기본) | 393 × 852 | **12.3** | 카이로 폰 체감과 일치 |
| **2** (근접) | 197 × 426 | 6.2 | 손님 포즈·이모트·탑승 관찰 |

`S=1` 의 12.3 타일은 카이로 폰 화면 실측에 맞춘 값이다 (1280px에 40타일 = 타일 32px = 텍셀 1px).

### 1.3 줌은 카메라가 아니라 업스케일 배율이다 ★

`camera.zoom` 은 **1.0 에서 절대 움직이지 않는다.** 확대는 렌더 버퍼를 줄이고 캔버스
업스케일 배율 S 를 올리는 것으로만 한다.

왜: 우리를 세 번 괴롭힌 "도트 느낌이 안 난다"의 근본 원인은 전부 **비정수 배율**이었다
(논리 320 → 캔버스 393 = ×1.228). 카메라 줌을 쓰면 임의 배율이 가능해지고, 가능하면
언젠가 쓰게 된다. **S 를 정수로 제한하면 비정수 배율이 표현 불가능해진다.**

부작용을 미리 밝힌다:
- **축소(S<1)가 없다.** 리조트 전체 조망은 **스크롤(팬)**로 한다 — 사용자가 이미 그렇게
  요구했다 ("배경은 위로 스캔했을 때 전체가 보이게").
- 예외 하나: v4 의 **감상 화면**(스크린샷·공유)만 비정수 축소를 허용한다. 게임 플레이 화면이
  아니고 도트 정합을 포기해도 되는 정지 화면이다. `S` 사다리와 별도 코드 경로로 둔다.

### 1.4 맵 전체는 폰 한 화면에 안 들어간다 — 파노라마로 간다

격자 40×32 의 다이아몬드는 **1152 × 576 텍셀**이다. 폰(393×852)과 비교하면:

- **세로**: 576 < 852 → 전부 들어가고 **276 텍셀이 남는다**. 이 여백이 배경 자리다
  (위 200 텍셀 = 능선·건너편, 아래 76 텍셀 = 앞물)
- **가로**: 1152 > 393 → **2.9 화면**. 좌우로 팬한다

아이소메트릭 맵의 바운딩 박스는 격자 비율과 무관하게 **항상 2:1 가로형**이다
(가로 `(W+D)×16`, 세로 `(W+D)×8`). 세로 폰에 전체를 담는 건 수학적으로 불가능하다.
그래서 결함으로 두지 않고 **소재로 흡수한다** — 빠지는 강을 따라 늘어선 파노라마다.
강이 가로로 흐르고 플레이어는 강변을 따라 좌우로 훑는다. 세로는 항상 다 보이므로
배경(산·건너편)이 스크롤 없이 상시 보인다 — 사용자가 요구한 조건 그대로다.

초반 체감도 확인했다: 시작 리조트는 중앙 **14×12** 타일에 들어가고, 이건
`(14+12)×16 = 416` 텍셀 ≈ **한 화면**이다. 나머지는 토지 매입으로 열리며 팬 거리가 늘어난다.
즉 "처음엔 한 화면, 키우면 파노라마"가 된다.

## 2. 손님 — 포즈 7 + 이모트 6

사용자가 카이로의 핵심이라고 지목한 부분이다: *"npc들의 표정을 보고, 그들이 놀이기구나
상호작용을 눈으로 볼 수 있다."* 따라서 손님은 **적게, 크게, 읽히게** 그린다.

### 2.1 규격

| 항목 | 값 |
|---|---|
| 크기 | **14 × 24 텍셀** (키 = 타일 높이의 1.5배) |
| 방향 | 4 (격자축 기준 `+X` / `+Z` / `-X` / `-Z`) |
| 팔레트 | 8종 (구명조끼 주황 우세, 반바지·머리·피부로 변화) |
| 아웃라인 | **1px 베이크 필수** (`#2b1d12`) |
| 동시 표시 | **60명** |

**아웃라인을 베이크하는 이유**: 픽셀화 외곽선 패스는 깊이 불연속에서만 선을 그린다.
손님이 줄을 서면 서로 붙어 깊이가 연속이 되어 **갈색 덩어리로 뭉친다** (실측). 아틀라스
셀 경계를 존중하며 스프라이트 안에 선을 구워야 한다.

### 2.2 포즈 7종

| 포즈 | 프레임 | 방향 | 쓰임 |
|---|---|---|---|
| `idle` | 2 | 4 | 대기·줄서기 |
| `walk` | 4 | 4 | 이동 |
| `swim` | 2 | 2 | 물속 (방향 2로 축약 — 상체만 보인다) |
| `float` | 2 | 1 | 튜브·인플레이터블 |
| `sit` | 1 | 4 | 평상·의자·카페 |
| `lie` | 1 | 2 | 선베드·찜질방 |
| `ride` | 1 | 4 | 탑승 (슬라이드 포함) |

셀 합계: 팔레트당 40셀 × 8 = 320셀. **코드 베이크**로 시작한다 (`guest-sprite.ts` 방식).
사용자가 "에셋도 더 고도화 시켜야 한다"고 했으므로 나중에 AI 픽셀아트로 교체하는데,
계약(크기·포즈·방향·셀 배치)이 고정돼 있으니 **게임 코드 0줄 변경**으로 갈아끼운다.

### 2.3 이모트 6종

말풍선 오버레이. 손님 머리 위 +4 텍셀, 크기 **12 × 12 텍셀**.

`happy` 만족 · `love` 최고 · `neutral` 보통 · `annoyed` 불만 · `hot` 더움 · `alert` 문제(고장·혼잡)

얼굴 표정 스프라이트는 **만들지 않는다.** 24텍셀 키에서 표정은 2~3 도트인데 그걸로
감정을 읽히게 만들 수 없다. 카이로도 표정이 아니라 **포즈 + 말풍선**으로 읽힌다.
동시에 여러 개 뜨면 화면이 시끄러우니 **최대 3개**만 표시한다 (카메라에 가까운 순).

### 2.4 탑승 합성 — 슬롯 계약

사용자 요구: *"놀이기구를 똑같은 사람이 타고 → 탄 디자인이 실시간으로 변경되는 것."*

시설 스프라이트는 **빈 상태 1장**만 그린다. 손님은 시설이 선언한 슬롯에 오버레이한다.

```
slots: [ { "x": 0, "y": 0, "pose": "sit", "facing": "+Z", "z": 0 }, ... ]
       // x,y = 앵커 기준 텍셀 오프셋 · z = 시설 앞/뒤 정렬
```

이게 결정 15 "전부 합성"의 구체형이다. 시설 × 손님 조합을 그리지 않으므로
샤워 4칸에 누가 몇 명 있든 **그림은 1장**이다. 슬롯 총계 **185개**.

슬라이드류는 슬롯 대신 경로를 선언한다:

```
entry: {"x":..,"y":..}   exit: {"x":..,"y":..}   path: [ {"x":..,"y":..}, ... ]
       // ride 포즈로 path 를 보간 이동
```

입구·출구가 명시되므로 "미끄럼틀 로직이 자연스러운 것" 요구가 데이터로 해결된다.

## 3. 벽 — 타일 점유 방식 (카이로 정석)

### 3.1 결정 요약

- 벽은 **타일을 점유**한다 (타일 경계에 얹는 방식이 아니다). 사용자 선택.
- 벽 타일 = 못 걷는다. 문 타일 = 걷는다.
- 플레이어가 자유롭게 그린다. **밀폐만 막는다** — 배치 시 게이트에서 flood fill 도달 검사.
- **방 타입 시스템 없음.** 사우나 공간·매점 공간을 벽으로 나누는 건 플레이어의 표현이고,
  게임은 "무슨 방인지" 판정하지 않는다.

### 3.2 오픈탑 ★ 새 결정 (18번)

**벽으로 둘러싼 실내는 지붕을 그리지 않는다.** 벽만 서고 내부가 위에서 보인다.

이유: 사용자가 첨부한 워터파크 스토리 실내 스크린샷이 정확히 이 방식이다. 그리고 이 결정 하나가
문제 두 개를 동시에 없앤다 — (1) 지붕이 내부를 가리는 오클루전 처리가 아예 불필요해지고,
(2) 실내 시설을 낮게 그릴 이유가 생겨 벽(24텍셀) 뒤로 숨지 않는다.

따라서 **실내 시설의 `bodyH` 는 20 텍셀 이하**로 고정한다 (벽 24보다 낮게).
펜션·방갈로는 예외 — 프리셋 벽 발자국이고 내부 배치가 없으므로 **지붕 있는 단일 스프라이트**다.

### 3.3 타일셋 18장

4방 이웃 비트마스크 16장 + 문 2장.

| 마스크 | 형태 | 장수 |
|---|---|---|
| 0 | 독립 기둥 | 1 |
| 1,2,4,8 | 끝단 4방향 | 4 |
| 3,6,9,12 | 코너 4종 | 4 |
| 5,10 | 직선 2종 | 2 |
| 7,11,13,14 | T 4종 | 4 |
| 15 | 십자 | 1 |
| — | 문 (X축 런 / Z축 런) | 2 |

캔버스 **32 × 40 텍셀** (다이아몬드 32×16 + 높이 24). 앵커 bottom-center.

유리벽(실내풀 구획용)은 **MVP 제외**. 같은 18장 구조를 재질만 바꿔 복제하면 되므로
확장 슬롯으로 남긴다.

## 4. 시설 73종

캔버스 크기는 발자국에서 파생된다 — 수식이 계약이다:

```
캔버스 가로 = (w + d) × 16
캔버스 세로 = (w + d) × 8 + bodyH
앵커        = bottom-center (다이아몬드의 앞쪽 꼭지점)
```

**이 수식을 벗어난 그림은 자동 실패다.** 과거 아틀라스 셀 크기와 매니페스트 논리 크기가
안 맞아 조용히 잘못 슬라이스된 사고가 두 번 있었다 — 파생 수식으로 못을 박는다.

`skillcheck` 9번은 지금 **`폭 ≤ 다이아몬드 + 2`** 만 본다 (`skillcheck.mjs:128`).
부족하다 — **등호로 조여야** 한다. 작게 그린 그림은 통과해 버리고, 그러면 접지가 어긋난다.
이 조이기는 구현 계획의 첫 항목이다.

`슬롯` = 동시에 손님이 보이는 칸 수. `벽부착 ●` = 벽에 등을 대야 배치 가능.

## 5. 배경 2겹

| 레이어 | 내용 | 알파 |

- **하늘과 물은 그림에 넣지 않는다.** 셰이더가 그린다. 그림에 넣으면 색이 조금이라도
  어긋날 때 두 톤 이음새가 생긴다 (실측 사고 1건).
- 가로 **타일러블** — 타일 폭 512 텍셀, 랩 크로스페이드 12 텍셀. 맵 폭 1152 + 팬 여백을
  덮어야 하므로 3장 이상 이어 붙는다.
- 맵 타입별 변형: `river` / `mountain` / `lake` (v4 재플레이 결정).
- 배치: 맵 위쪽 꼭지점 기준 위로 200 텍셀 대역 (§1.4).

**전 세대 `farbank.ts` 의 수직 벽 배경막은 폐기한다.** 그 구조가 "배경은 뒤에 세운 벽"
가정의 산물이고, 그 가정이 이번 전환의 원인이다.

### 6.1 되풀이하지 말 함정 (전부 실측)

- **크로마 키는 소재색으로 분기한다.** 초록·청록 소재 → 마젠타 `#FF00FF`.
  빨강·분홍·노랑 소재 → 그린 `#00FF00`. 분홍 꽃잎을 마젠타로 뽑아 추출이 막힌 적 있다.
- **재추출 시 키는 원 런의 `sprite-request.json` 에서 확인한다. 추리 금지.**
  슬라이드를 그린으로 재추출해 마젠타 사각형을 게임에 구워 넣은 사고가 있었다.
- **팔레트 양자화는 hue 버킷 우선(v4)** — 나이브 최근접은 음영을 윤곽갈로 몰아 윤곽률
  56~60% 를 만든다. 전역 최근접 → 차가운 캐치올 → 암녹 지붕이 빨강으로 새는 순서로 세 번 실패했다.
- **셰이더 색을 바꾸면 양자화 팔레트에도 넣어야 한다.** 안 넣으면 옛 색조로 스냅백된다.
- **지형을 건드렸으면 가로 화면도 찍는다** (`tools/shot-wide.mjs`). 세로 폰만 보고
  물이 육지를 덮는 버그를 놓쳤다.
- **빌보드 재질 계약 3종**: `transparent:false` + `alphaTest:0.5` (깊이 실루엣 외곽선이
  사각형이 아니라 알파 모양을 따게) · `SRGBColorSpace` · `NearestFilter`.
