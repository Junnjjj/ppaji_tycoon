## 1. 투영과 스케일 — 1 월드 = 1 텍셀 (수평)

| 항목 | 값 | 근거 |
|---|---|---|
| yaw | **45°** | 두 지면축의 화면 기울기가 같다 |
| elev | **30°** | `sin30 = 0.5` → 화면 기울기 정확히 1:2 |
| 타일 한 변 | **22.627417 월드** (= 32/√2) | §1.1 |
| 타일 다이아몬드 | **32 × 16 텍셀** | §1.2 실측 |
| 격자 한 걸음 | **화면 (16, 8) 텍셀 — 정수** | 검산 완료 |
| 수평 1 월드 | = 1 텍셀 | 파생 |
| **수직 쿼드 높이 배율** | **1.1547005** (= 1/cos30) | ★ 소멸하지 않는다 |
| 카메라 zoom | **1.0 고정, 영구히** | §1.4 |
| 손님 키 | **24 텍셀** (실측 22.8) | §1.2 |

### 1.1 타일 한 변을 22.627 로 잡는 이유

다이아몬드 폭 32 텍셀 → 한 변 = 32/√2. 이때 격자 한 걸음의 화면 이동이

```
+X 한 걸음 → ( +16, +8 ) 텍셀
+Z 한 걸음 → ( -16, +8 ) 텍셀
```

**정확한 정수**라 격자 좌표를 몇 번 더해도 텍셀 격자를 벗어나지 않는다.

### 1.2 스케일 실측 — 세 번 계산해서 확정했다

`art-reference/competitor/pool-slide-story-park.jpg` 로 실측했다. **이 절차를 다시 하지 말 것.**

1. 아트 업스케일 배율을 도트 행 경계 간격으로 측정 → **2.5배** (세 영역 독립 측정
   2.52 · 2.54 · 2.56). 즉 1280×720 은 네이티브 **512×288** 의 2.5배본이다.
2. 타일이 정수 텍셀이려면 이미지 타일폭이 2.5의 배수여야 한다 →
   64px(25.6) ✗ · 72px(28.8) ✗ · **80px(32.0) ✓** · 96px(38.4) ✗
3. 손님 = 눈금으로 읽은 57 이미지px ÷ 2.5 = **22.8 텍셀**, 타일 높이의 **1.43배**
4. 머리 = 28 이미지px ÷ 2.5 = **11.2 텍셀** → 눈 1텍셀 · 입 1텍셀

**함정**: 손님을 이미지px 로 재고 타일을 텍셀로 나누면 3.3배가 나온다 (리뷰에서 실제로 나왔고
나도 한 번 틀렸다). 배율을 먼저 확정하고 같은 단위로 비교할 것.

### 1.3 수직은 1 월드 ≠ 1 텍셀 ★

elev 30 오소 카메라에서 **세계 수직축 1 월드는 화면에서 0.866 텍셀**이다. 시설·벽·손님은
수직 쿼드 빌보드이므로 (카메라 정면 쿼드는 두 번 실패해 폐기했다) 쿼드 높이를
**1/cos30 = 1.1547 배**로 미리 늘려야 화면에서 텍셀이 원본 비율로 찍힌다.

이 상수는 "1월드=1텍셀"로 소멸하지 않는다. 폐기 대상은 `TEXEL_WORLD`(= 1 이 되어 소멸)뿐이다.
`prototype-3d/src/sprite-facility.ts:96` 이 이미 이 보정을 갖고 있다.

### 1.4 줌은 카메라가 아니라 정수 업스케일 S

`camera.zoom` 은 1.0 에서 절대 안 움직인다. 확대는 렌더 버퍼를 줄이고 업스케일 S 를 올린다.

```
렌더 버퍼(텍셀)   = ceil(CSS / S)
카메라 절두체(월드) = 버퍼 크기와 동일
캔버스 백킹(px)   = 버퍼 × S × round(DPR)
캔버스 CSS(px)    = 버퍼 × S        ← 화면보다 최대 S-1 px 넘칠 수 있다 → overflow:hidden
DPR              = 정수로 반올림     ← 2.625·2.75 를 그대로 쓰면 비정수 배율이 돌아온다
```

| S | 버퍼 (393×852 폰) | 가로 타일 | 쓰임 |
|---|---|---|---|
| **1** (기본) | 393 × 852 | **12.3** | 카이로 폰 체감과 일치 |
| **2** (근접) | 197 × 426 | 6.2 | 손님 표정·이모트·탑승 관찰 |

**왜 카메라 줌을 없애나**: "도트 느낌이 안 난다"의 원인이 세 번 다 비정수 배율이었다.
카메라 줌을 쓰면 임의 배율이 가능해지고, 가능하면 언젠가 쓰게 된다. S 를 정수로 제한하면
비정수 배율이 **표현 불가능**해진다. 예외는 v4 감상 화면(스크린샷)뿐 — 별도 코드 경로.

### 1.5 카메라를 텍셀 격자에 스냅한다 ★

팬으로 `target` 이 소수 좌표가 되면 모든 스프라이트가 반 픽셀 밀린다. **매 프레임
`target.x`·`target.z` 를 1 월드(= 1 텍셀) 단위로 반올림**한다. 반올림 전 값을 따로 들고
있어야 관성이 끊기지 않는다.

### 1.6 맵 전체는 폰 한 화면에 안 들어간다 — 파노라마

격자 40×32 → 다이아몬드 **1152 × 576 텍셀**. 폰(393×852) 기준 세로는 다 들어가고
276 텍셀이 남아 배경 자리가 되며, 가로는 **2.9 화면**이라 좌우로 팬한다.

아이소메트릭 맵의 바운딩 박스는 격자 비율과 무관하게 **항상 2:1 가로형**(가로 `(W+D)×16`,
세로 `(W+D)×8`)이라 세로 폰에 전체를 담는 건 수학적으로 불가능하다. 그래서 소재로 흡수한다 —
빠지는 강을 따라 늘어선 파노라마다. 시작 리조트는 중앙 14×12(416 텍셀 ≈ 한 화면)에 들어가고,
토지 매입으로 팬 거리가 늘어난다.

⚠ **"세로는 항상 다 들어간다"는 W+D ≤ 106 에서만 성립한다** (852/8 = 106.5).
40×32(=72) 는 여유가 있으나 확장으로 W+D 가 106 을 넘으면 세로도 팬해야 한다.
확장 상한을 격자 합 **W+D ≤ 100** 으로 못박는다.

## 2. 손님 — 포즈 7 + 이모트 6 + **표정**

| 항목 | 값 |
|---|---|
| 셀 | **14 × 24 텍셀** |
| 방향 | 4 (`+X` / `+Z` / `-X` / `-Z`) |
| 팔레트 | 8종 |
| 아웃라인 | **1텍셀 베이크 필수** (`#2b1d12`) |
| 동시 표시 | 60명 |

**아웃라인 베이크 이유**: 픽셀화 외곽선 패스는 깊이 불연속에서만 선을 그린다. 손님이 줄을 서면
깊이가 연속이 되어 갈색 덩어리로 뭉친다 (실측). 아틀라스 셀 경계를 존중해 스프라이트 안에 굽는다.

### 2.1 표정을 그린다 ★ v1 에서 뒤집음

v1 은 "24텍셀에서 표정은 2~3도트라 못 읽힌다"고 판단해 표정을 포기했다. **사실과 다르다** —
레퍼런스는 머리 11텍셀에 **눈 1텍셀 · 입 1텍셀**로 표정을 또렷하게 그린다 (§1.2 실측).
사용자가 카이로를 택한 이유가 "npc들의 표정을 보고"이므로 이건 선택이 아니다.

표정 4종: `평온` · `기쁨`(눈 감김 + 입 벌림) · `불만`(눈썹 내림) · `지침`(눈 감김 + 땀).
포즈와 **직교**한다 — 머리 영역만 교체하므로 셀이 4배로 늘지 않는다 (머리 오버레이 4장).

### 2.2 포즈 7종

| 포즈 | 프레임 | 방향 | 쓰임 |
|---|---|---|---|
| `idle` | 2 | 4 | 대기·줄서기 |
| `walk` | 4 | 4 | 이동 |
| `swim` | 2 | 2 | 물속 (상체만 보인다) |
| `float` | 2 | 1 | 튜브·인플레이터블 |
| `sit` | 1 | 4 | 평상·의자·카페 |
| `lie` | 1 | 2 | 선베드·찜질방 |
| `ride` | 1 | 4 | 탑승 (슬라이드 포함) |

팔레트당 40셀 × 8 = 320셀 + 표정 머리 4장. **코드 베이크**로 시작하고, 계약이 고정돼 있으므로
나중에 AI 픽셀아트로 게임 코드 0줄 변경으로 교체한다.

### 2.3 이모트 6종

말풍선 오버레이, 머리 위 +4 텍셀, **12 × 12 텍셀**.
`happy` · `love` · `neutral` · `annoyed` · `hot` · `alert`. 동시 최대 3개(카메라 가까운 순).

### 2.4 인물 6종 추가 — 직원과 아이

v1 은 성인 손님 1종만 계약했다. design.md 는 직원 5직종을 쓰고 손님의 40%가 가족이다.

- **직원 5**: 안전요원 · 매점 · 청소 · 정비 · 안내 — 손님과 같은 14×24 셀, 유니폼 팔레트 고정
- **아이 1**: **10 × 17 텍셀** (성인의 0.7). 포즈는 `idle`/`walk`/`swim`/`float` 4종만

### 2.5 탑승 합성 — 슬롯 계약

시설 스프라이트는 **빈 상태 1장**만 그린다. 손님은 시설이 선언한 슬롯에 오버레이한다.

```json
"slots": [ { "tile": [0, 0], "pose": "sit", "facing": "+Z" } ]
```

**`tile` 은 발자국 안의 타일 인덱스다.** 텍셀 좌표를 직접 적지 않는다 — 앵커나 투영이 바뀌면
185개가 전부 틀어진다. 렌더러가 투영으로 텍셀 위치를 계산한다. 한 타일에 둘 이상이면
`offsetTexel` 로 나눈다 (파라솔 1×1 에 2인).

슬라이드류 4종은 `entryTile` · `exitTile` · `ridePose` 를 선언한다.

## 3. 벽 — 타일 점유 + **스티플 유리**

### 3.1 결정

- 벽은 **타일을 점유**한다. 벽 = 못 걷음, 문 = 걸음.
- 플레이어가 자유롭게 그린다. **밀폐만 막는다** (게이트에서 flood fill 도달 검사).
- **방 타입 시스템 없음.**
- **오픈탑** — 벽 안 실내는 지붕을 그리지 않는다. 실내 `bodyH ≤ 20` (벽 24보다 낮게).

### 3.2 왜 전부 유리인가 ★ v1 에서 뒤집음

v1 은 "오픈탑이 오클루전을 없앤다"고 했지만 **가리는 것은 지붕이 아니라 근측 벽**이었다.
벽 스프라이트는 화면에서 자기 밑변 위로 40텍셀을 덮고, 한 타일 뒤로 갈 때마다 밑변은 8텍셀만
올라간다:

| 벽에서 k타일 뒤 | 손님 24텍셀 은폐량 |
|---|---|
| 1 | **24/24 (완전 은폐)** |
| 2 | 24/24 |
| 3 | 16/24 |
| 4 | 8/24 |
| 5 | 0 |

실내 27종(시설의 37%)에서 "손님이 노는 광경"이 안 보인다는 뜻이고, 그건 이 게임의 핵심 보상이다.
레퍼런스는 이 문제를 **유리벽**으로 푼다 (`pool-slide-story-park.jpg` 실내를 10배로 확대하면
유리 패널 안에 뒤쪽 물체가 흐릿하게 비친다).

**카메라 yaw 가 45°로 고정이므로 어느 면이 근측인지 영구히 정해져 있다** — 벽 타일이 화면에
보여주는 면은 항상 근측 면이다. 그래서 동적 판정이 필요 없다: **18장 전부를 유리로 그린다.**

### 3.3 스티플 — 알파 블렌딩을 쓰지 않는 이유

레퍼런스는 진짜 알파 블렌딩이다. 우리가 그대로 하면 **팔레트 게이트에 걸린다** — 블렌딩이
팔레트에 없는 중간색을 만들고, 양자화가 가장 가까운 색으로 스냅해 비치는 형체가 사라진다
(기록된 함정: "셰이더 색을 바꾸면 팔레트에도 넣어야 한다").

**스티플(50% 체커 알파)** 은 새 색을 하나도 만들지 않아 팔레트 계약과 재질 계약
(`transparent:false` + `alphaTest:0.5`)을 둘 다 지킨다. 1텍셀 = 1 CSS px 이라 눈에는
반투명 유리로 읽힌다. 픽셀아트가 원래 유리를 그려 온 방법이다.

구성: **불투명 기단 + 불투명 멀리온 + 스티플 유리 패널 + 베이크 아웃라인**.

### ⚠ 순서가 중요하다 — 아웃라인을 먼저 굽고 그다음 뚫는다 (K3 실측)

`bakeOutline` 은 "실체에 인접한 투명 픽셀"에 윤곽색을 칠한다. 50% 체커에서는 뚫린 픽셀
**전부**가 실체에 인접해 있어서, 스티플을 먼저 뚫고 아웃라인을 구우면 구멍이 통째로
메워진다 (실측 투과율 **0%**). 반드시 이 순서다:

1. 패널을 **불투명하게** 그린다
2. 아웃라인을 굽는다 (실루엣이 꽉 찬 상태)
3. **마지막에** 체커로 구멍을 뚫는다 — 멀리온·실루엣 가장자리는 남긴다

가장자리를 함께 뚫으면 윤곽선이 끊겨 벽이 부서져 보인다. 검증은 스프라이트 알파를 직접
읽어 투과율이 30~70% 안인지 본다 — **합성된 화면에서 재려 하지 말 것.** 옆 벽의 뚜껑이
그 자리를 덮어 엉뚱한 색이 나온다 (이것도 실측으로 겪었다).

## 4. 시설 73종

```
캔버스 가로 = (w + d) × 16
캔버스 세로 = (w + d) × 8 + bodyH
앵커        = (캔버스 가로 / 2, 캔버스 세로)
```

### 4.1 앵커는 좌표다 ★ v1 에서 고침

v1 은 앵커를 "bottom-center (다이아몬드의 앞쪽 꼭지점)"이라 썼다. **괄호가 틀렸다** —
두 점은 다르다. 발자국 꼭지점의 화면 x = 16(i−j) 이므로

- 바운딩박스 가로중심 = 캔버스 가로 / 2 ← **이것이 앵커 x**
- 최하단(앞) 꼭지점 x = 16(w−d) ← 정사각(w=d)에서만 위와 같다

차이는 비정사각 **32/73종**에서 최대 **24텍셀(1.5타일)**이다.
`prototype-3d/src/sprite-facility.ts:74-90` 이 이 함정을 경고로 남겨뒀는데 v1 이 되풀이했다.

게이트에 **"실루엣 최하단 픽셀의 x 가 앵커 x 와 일치할 필요는 없다"**를 명기한다. 대신
바닥 다이아몬드 네 꼭지점이 가이드와 ±0px 인지 검사한다.

### 4.2 캔버스 패딩 규칙 ★ 신규

파이프라인(`prepare_sprite_run.py`)의 자유도는 **1개**(로지컬 높이)이고 폭은 실루엣 아스펙트에
따라 결정된다. 그래서 캔버스를 가로·세로 둘 다 정확히 맞출 수 없다 — 82런 실적 정확 일치 0건.

**계약은 프레임이고 실루엣이 아니다.** 파이프라인 출력을 다음 규칙으로 정확 캔버스에 배치한다:

1. 로지컬 높이 = `(w+d)×8 + bodyH` 로 추출한다
2. 출력 폭이 캔버스 폭보다 작으면 **좌우 균등 투명 패딩**, 크면 **리롤** (축소 금지 — 이중 열화)
3. 세로는 바닥을 앵커선에 맞추고 위쪽에 투명 패딩
