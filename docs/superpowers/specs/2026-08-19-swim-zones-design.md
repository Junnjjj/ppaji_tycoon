# 수영 구역 — 야외 수영장 + 플로팅덱 수영 구역 (v1.1, 적합성 검증 반영)

**v1 → v1.1 (코드 실측 적대 검증, 2026-08-19):**
- ⚠ v1 의 "코스가 이미 permitArea 를 쓴다"는 **거짓이었다** — `permitArea` 는 등급
  데이터에 정의만 있고 **소비처가 0** 이다 (grep 실측). 수영 구역이 **첫 소비자**가
  된다. 코스를 같은 회계에 넣는 것은 별도 작업 (밸런스 변화가 섞이면 원인을 못 가린다)
- ⚠ need 축에 'fun' 은 없다 — 실제 축은 play(14)·thrill(11)·rest(9)·scenery(5)·… 이다.
  수영은 **`play`** 다
- ⚠ 콤보는 `adjacent | cluster | resort` 셋뿐이고 `evaluateCombos(placement)` 가
  지형을 모른다 — 구역 콤보(나이트풀 등)는 kind **`zone`** 추가 + 시그니처에 지형
  전달이 필요하다 (호출부: main·exam·봇·검사). S4 비용에 계상
- ✅ 강점 실측: `GuestPose` 에 `'swim' | 'float'` 가 **이미 있고**, 절차 손님 아틀라스
  (`kairo-guest-sprite.ts`)에 swim 2프레임 · 물 클리핑 · "물에선 그림자 없음"까지
  구워져 있다. 실내 풀 3종(pool_kids/warm/lazy)이 이미 이 포즈를 쓴다
  (`guests.ts:950`). **수영 손님은 새 에셋이 0장이다**
- 신규 시설 id 는 `pool` 접두를 피한다 (`dj_booth`·`stage_river`) —
  `id.includes('pool')` 포즈 휴리스틱과 얽히지 않게

사용자 요청 (2026-08-19):
① **실외 대형 수영장** — 건물처럼 확장하고, 손님이 안에서 놀고, 저녁 파티·DJ·공연,
콤보·해금 연계. ② **플로팅덱 수영 구역** — 파란 조립식 플로팅덱으로 강 위에 사각형을
만들면 그 안이 수영 구역이 되고, 안에 플로팅 놀이기구를 띄운다. **한국 빠지의 시그니처.**

실물 근거 (가평 빠지 리서치): 수영 구역은 부표·플로팅덱 라인으로 두르고 구명조끼를
입고 들어간다. 놀이기구(에어바운스·수상 트램폴린·슬라이드)는 구역 **안**에 정박한다.
패키지에 구명조끼·샤워가 포함된다 — 위생 시설과의 연계가 실물에 있다.

## 0. 핵심 아키텍처 — "바닥이 곧 방"의 물 버전

이 게임의 확정 패턴 (K27): 플레이어는 사각형을 그리지 않는다. **바닥을 깔면 그게 방**이고
벽은 파생이다. 수영 구역도 같은 문법으로 간다:

- **수영장(땅)**: `pool_water` 지면을 **붓으로 칠하면** 이어진 덩어리가 수영장이다.
  가장자리 테두리(코핑)와 사다리는 파생 — 따로 안 놓는다.
- **수영 구역(강)**: 플로팅덱(+선착장)으로 물을 **둘러싸면** 그 안이 수영 구역이다.
  부표 라인은 파생 — 구역 안쪽 경계에 절차적으로 그린다.

**구역은 저장하지 않는다** (terrain.isIndoor 와 같은 규칙). 지면·시설 배치에서 매번
파생한다 — 별도 저장소는 반드시 어긋난다 (K27 실증).

두 구역은 생산자만 다르고 **소비자는 하나다**:

```
생산자 A: pool_water 덩어리 (땅)      ┐
생산자 B: 덱으로 밀폐된 물 (강)        ┴→ SwimZone { tiles, capacity, entry } →
소비자: 수영 활동 (손님) · 위험도 · 콤보 · 결산
```

## 1. sim — 구역 파생 (`src/sim/kairo/swim.ts`)

### 1.1 수영장 (땅)

- 지면 종류 `pool_water` 추가. 플래그: `walkable: false · guestWalk: false ·
  buildable: false · paintable: true`, `cost: 40000/칸` (실내 바닥 30,000 보다 비쌈 —
  굴착+방수). **새 지면 종류는 네 곳** (kairo-ground.json · 렌더 계약 · GROUND_BASE ·
  paintable) — K38 체크리스트 그대로.
- 물·도시 띠·암반 위에는 못 칠한다 (기존 붓 규칙이 이미 막는다). 토지 제한도 그대로.
- 수영장 = `pool_water` 4-연결 덩어리, **최소 4칸**. 3칸 이하는 "장식 웅덩이" —
  구역이 아니다 (미니 수영장 남발 방지).
- **입수 조건**: 덩어리가 `guestWalk` 포장과 한 칸 이상 접해야 한다. 접점이 곧
  사다리(파생)다 — 문이 포장 닿은 쪽에만 나는 것과 같은 규칙 (K32-B).

### 1.2 수영 구역 (강)

- 물 타일의 4-연결 컴포넌트를 flood fill 한다. 컴포넌트의 경계가 전부
  **플로팅덱·선착장 발자국 또는 뭍**이고, **강의 열린 가장자리(맵 밖으로 이어지는 물)에
  닿지 않으면** 밀폐 — 수영 구역이다.
- 상한: 구역 면적은 **수면 사용 허가 면적(permitArea)을 소비한다** (설계 §의 "허가는
  돈으로 못 산다"와 연결 — 등급이 곧 수영 구역의 크기 상한이 된다). ⚠ v1.1 실측:
  permitArea 는 지금 소비처가 0 인 죽은 값이다 — 수영 구역이 **첫 소비자**가 되고,
  코스 편입은 백로그로 뺀다.
- 입수 조건: 둘러싼 덱 중 한 칸이 게이트에서 `guestWalkable` 로 닿아야 한다.
- **플로팅 놀이기구**: 물 위 시설(`requiresDeck` 계열)이 지금은 덱 인접만 허용 —
  **수영 구역 안이면 덱 인접 없이도 허용**으로 확장 (`needs-deck` 판정에 구역 검사 추가).
  구역 안 기구는 수영 손님의 만족 보너스 (아래 2.3).

### 1.3 검증 (단위)

- 파생 왕복: 덱을 한 칸 빼면 구역이 즉시 사라지고, 다시 놓으면 되살아난다 (희망≠상태)
- 음성 대조군: 열린 강에 덱 ㄷ자(미밀폐)는 구역이 아니다 · 3칸 수영장은 구역이 아니다 ·
  포장이 안 닿은 수영장은 `no-entry`
- permitArea 회계: 구역+코스 합이 상한을 넘으면 마지막 덱 설치가 거절된다
  (`permit-over`) — 처방은 "등급을 올리세요"

## 2. sim — 수영 활동 (손님)

### 2.1 모델

- 수영 구역은 **가상 시설**로 손님 목적지 목록에 들어간다 (need: `play` — v1.1 실측 축).
  용량 = `floor(면적 × 0.8)`명, 요금 = 수영장 800 / 강 구역 500 (1/10 눈금).
- 손님은 **입수점(사다리·덱 가장자리)까지 걷고**, 구역 안에서는 flow field 를 안 탄다 —
  구역 타일 안을 시드 RNG 로 유영 (tick 마다 이웃 물 타일로 보간 이동). 체류 8~14 tick.
- 수영 중 렌더 상태 `swimming` — 몸 절반 잠김 + 물결 (렌더 §4).

### 2.2 위험도

- 수영 구역은 위험 +2/구역 (물이다). **안전요원**(기존 시설)이 구역에 인접하면 −2,
  구명조끼 대여소가 리조트에 있으면 전 구역 −1. 실물 근거: 빠지는 조끼가 기본이다.
- 위험도 4단계 상시 표시 규칙 그대로 — 구역이 위험 단계를 올리면 칩에 반영된다.

### 2.3 저녁 파티 (수영장 전용 축)

- 신규 시설 **DJ 부스**(2×1, 3등급 해금) · **공연 무대**(3×2, 4등급 해금).
- 흐르는 낮의 저녁 구간(frac > 0.7)에 수영장+DJ 부스 인접이면 해당 수영장이
  **나이트풀**: 저녁 수요 가중 ×1.5, 만족 +5. 날씨 규칙과 같은 "수요 구성 변화"다 —
  배수 아니라 시간대 구성 변화 (v4 결정과 정합).
- 콤보 (중형 2 + 대형 1): `풀 파티`(수영장+DJ+바), `빠지 오리지널`(강 구역+놀이기구
  2+조끼 대여소), 대형 `리버 페스타`(공연 무대+나이트풀+강 구역). ⚠ v1.1: 콤보 kind 에
  **`zone`** 을 추가하고 `evaluateCombos` 가 구역 정보를 받아야 한다 — 호출부
  (main·exam·봇·검사) 시그니처 변경 포함.

### 2.4 해금·의뢰

- `pool_water` 붓: 2등급 해금 (첫 심사 뒤 — 초반 과부하 방지).
- 강 구역: 덱은 1등급부터 있으므로 **구역 판정 자체는 항상 켜져 있다** — 첫 밀폐가
  일어나면 셀레브레이션 1회 ("수영 구역 개장!"). 해금이 아니라 **발견**이다 (K41 문법).
- 의뢰 2종: "첫 수영 구역" (구역 1) · "나이트풀" (저녁 가중 1회 발동). 의뢰 조건은
  골격만으로 충족 가능 규칙 준수 (덱·붓 모두 골격 해금).

## 3. 저장

- `pool_water` 는 지면이라 **세이브 변경 없음** (지면 격자에 이미 실린다).
- DJ 부스·무대는 시설이라 변경 없음. 구역은 파생이라 저장 안 함.
- 세이브 버전 유지 (v7). 마이그레이션 불필요 — 새 지면 종류는 신규 인덱스만 추가.

## 4. 렌더 (전부 `source: 'procedural'` — AI 에셋 대상 아님)

- `pool_water` 타일: 밝은 청록 + 가장자리 코핑 테두리 (이음새 규칙: 물 계열이므로
  유기적 — K38 반대 적용 금지 규칙 확인 필요, 대비 측정으로 결정)
- 수영 구역: 안쪽 경계를 따라 **부표 라인** (노랑·주황 점선 — 실물 부표). 절차적.
- 수영 손님: **이미 있다** (v1.1 실측) — 절차 아틀라스의 `swim` 포즈 (2프레임,
  하반 클리핑·무그림자 구움 완료, 실내 풀이 현재 사용 중). 구역 유영은 이 포즈 재사용.
  **신규 에셋 0장.**
- DJ 부스(`dj_booth`)·무대(`stage_river`): 임시 도형 + 계약 등록 (`source: 'ai'` —
  AI 픽셀 대상은 이 **2장뿐**). **저녁 나이트풀은 FX 슬롯**(등록부)로 — 하드코딩
  이펙트 금지 (슬롯 계약 규칙).

## 4.5 S2 실측 기록 (2026-08-19)

- 구역은 `GuestStore` 의 **가상 시설**이다: 핸들 대역 `ZONE_HANDLE_BASE`(1<<20),
  입수점이 거리장 목적지, 정원은 `claims` 공용, 유영은 tick rng (결정론 유지)
- Guest 에 필드를 안 늘렸다 — 입수점 기억은 `rideFrom` 재사용 (rideTotal 0 이라
  ride 분기와 안 얽힘). **세이브 버전 그대로 v7**
- ⚠ 봇 실측: 심사 등급 중앙값이 **52주에도 1** 이라 수영장(2등급 붓)이 median 0 이다.
  S2 버그가 아니라 등급 페이싱 문제 (CLAUDE.md "다음 할 일" 3과 같은 뿌리) — 별도 과제.
  p75 시드는 수영장을 파고 경보 0 이므로 수영 경제 자체는 재진다

## 4.6 S3·S4 실측 기록 (2026-08-19)

- S3: 씬 `setSwimZones` — 코핑/부표는 **칸마다 그래픽 하나** (한 장에 최대 깊이를 주면
  북쪽 손님이 덮인다 — 보트 문제의 면적판). create() 전 호출은 setLand 규칙으로 지연
  (실측: 세이브 복원 부팅이 죽었다 — CLAUDE.md 가 경고한 그 함정)
- S3: **자연 연못은 구역이 아니다** — 덱 0장 밀폐 물 제외 (실측: 판마다 공짜 구역
  2개 + 허가 잠식)
- S4: 콤보 kind `zone` + `evaluateCombos(placement, extra?, zones)` — 의뢰·심사·소원·
  UI·봇 전부 같은 zones 를 받는다 ("의뢰로는 3개, 심사로는 2개" 방지). 콤보 70→73
  (풀 파티 · 빠지 오리지널 · 리버 페스타, 전부 숨은 콤보)
- S4: 나이트풀 = 저녁(하루 마지막 20%) × DJ 부스 반경 3 수영장 → 수영 만족 +5.
  tick 의 순수 함수라 주 항등(run ≡ step)이 유지된다
- S4: 시설 73→**75** (dj_booth 3등급 · stage_river 4등급, capacity 0 분위기 시설)
- ⚠ 콤보 보너스(satisfaction/revenue 숫자)는 **주간 경제에 안 물린다** (실측 — 조건·
  발견·미리보기용이다). permitArea 와 같은 계열의 죽은 축 — 별도 과제로 기록
- ⚠ **도감 발견 경로가 zones 를 안 받는다** (2026-08-19 감사 실측). `evaluateCombos` 는
  의뢰·심사·소원·건설 토스트·봇 다섯 곳에서 zones 를 받는데, 도감의
  `activeComboIds(placement)` (`ui/kairo-catalog.ts` → `main.ts` 의 `noteDiscoveries`)
  만 인자 없이 부른다 — **zone 콤보 3종이 실게임에서 영원히 발견되지 않는다.**
  봇(`kairo-sim.ts`)은 넘기므로 헤드리스와 실제 판이 갈라진 상태다. S4b 최우선
- ⚠ 봇 재실측 (12시드 52주, 감사 시점): 심사 등급 중앙 **1**(최대 2) · 수영 구역 중앙
  **0개**(p75 1). §4.5 의 진단이 52주에서도 그대로다 — 수영 경제는 p75 시드에서만 재진다
- 백로그 (S4b): 도감 발견 배선 · 의뢰 2종("첫 수영 구역"·"나이트풀" — 조건 kind 확장
  필요, `kairo-quests.json` 은 16종 그대로) · 발견 셀레브레이션 · 안전요원 인접 감면
  (`swimRiskPoints` 는 아직 구역당 +2 만) · 봇 등급 페이싱 · 코스의 permitArea 편입

## 5. 순서 (커밋 단위 — 섞으면 밸런스 원인을 못 가린다)

1. **S1** `swim.ts` 구역 파생 + `pool_water` 지면 + 단위 검사 (음성 대조군 먼저)
2. **S2** 수영 활동 + 용량·요금·위험도 + 봇에 수영장 짓기 + 밸런싱 (26/52주 경보 0 유지)
3. **S3** 렌더 (코핑·부표·수영 손님) + 붓 UI + 브라우저 검사
4. **S4** DJ·무대·나이트풀·콤보 3종·의뢰 2종 + 해금 그래프 검사 통과

## 6. 하지 않을 것

- 수심·다이빙 깊이 — 칸은 평면이다
- 수영장 모양 벌점/보너스 — 덩어리면 된다 (경관 지표가 이미 있다)
- 강 구역 안 손님-보트 충돌 — 코스와 구역은 permitArea 에서 이미 배타적이다
- 유수풀·파도풀 — 시설 75종(S4 후 실측)에서 이미 커버하거나 후속
