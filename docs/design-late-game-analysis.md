# 후반 설계 — 카이로소프트 × 롤러코스터 타이쿤, 그리고 모바일

> 작성 2026-08-19. 목표는 **"후반에 지을 게 없다"** 를 푸는 것이고, 방향은 사용자가 정했다:
> **카이로소프트처럼 가볍게, 그 안에서 롤코 타이쿤처럼 짓는 즐거움.** 모바일 전용.
>
> 이 문서는 **분석**이다. 결정은 뒤에 붙는 설계 문서에서 한다.

---

## 0. 문제의 크기 (실측)

우리 저장소에 이미 측정값이 있다 (`economy.test.ts`):

| 측정 | 값 | 출처 |
|---|---|---|
| 시설 개선 상한이 3일 때 | **312주 중 281주가 "지을 게 없다"**, 현금 1.5억 적체 | `economy.test.ts:96` |
| 개선 축이 아예 없을 때 | **80주 중 58주가 "지을 게 없다"** | `economy.test.ts:14` |
| 헤드리스 26·52주 | 밸런스 경보 0 (초반·중반은 건강하다) | `sim:kairo` |

즉 **초반 설계는 작동하고 후반만 비었다.** 지금 후반을 막는 것은 자리가 아니라
**등급 상한**이다 — 5등급 `maxGuests` 230 · `permitArea` 500 에서 끝이고, 토지를 넓혀도
K37 로 테라스가 늘어도 그대로다.

⚠ 설계서에는 이미 ★1~★5 사다리와 "한 판 12~18시간"이 적혀 있다 (design.md §9.2, §14).
**설계가 없는 게 아니라 사다리 끝에 방이 없다.** 그래서 이 분석의 질문은
"진행을 어떻게 만드나"가 아니라 **"★5 이후에 무엇을 하나"** 그리고
**"올라가는 동안 무엇이 더 재미있어지나"** 다.

## 1. 카이로소프트 (Pool Slide Story) — 무엇을 잘하나

근거: `art-reference/competitor/pool-slide-story-park.jpg`,
`pool-slide-story-indoor.png`, 그리고 이미 기록된 실측
(`art-reference/competitor/README.md`).

### 장점

| 잘하는 것 | 실측/근거 | 우리가 이미 가져온 것 |
|---|---|---|
| **경계를 안 보여 준다** | 스크린샷에 하늘·지도 끝이 한 픽셀도 없다. 놀이터가 화면을 가득 채운다 | K38 에서 지형으로 채웠다 (다른 방식, 같은 목표) |
| **손님 밀도가 낮다** (화면 타일의 2%) | 적은 손님이 **무엇을 하는지** 보인다. 붐빔이 아니라 개체가 읽힌다 | 유지 중 |
| **N×1 연립 시설** | 샤워 칸마다 손님이 서서 "동시에 쓰인다"가 보인다. 탭도 절약된다 | K5 에서 가져왔다 |
| **한 화면에 정보를 다 띄우지 않는다** | 상단 얇은 띠 + 하단 얇은 띠. 나머지는 전부 놀이터 | K28 화면 예산 (세로 ≤14%) |
| **진행이 숫자가 아니라 사건** | 연차·심사·이벤트로 리듬을 만든다 | 주 루프 + 카드 + 의뢰 |

### 약점 (우리가 반복하면 안 되는 것)

1. **배치의 자유도가 낮다.** 대부분 "빈칸에 놓기"이고, 놓는 순간 결과가 정해진다.
   되돌아와 다듬을 이유가 약하다.
2. **공간이 곧 성능인 관계가 얕다.** 인접 보너스는 있지만 **동선**이 성능을 크게
   좌우하지 않는다. 그래서 "이 배치가 왜 더 좋은가"를 플레이어가 못 읽는다.
3. **후반이 수치 확장이다.** 더 큰 시설·더 큰 숫자. 새로운 **결정**이 잘 안 생긴다.
   ← **우리가 지금 겪는 문제와 같은 종류다.**

## 2. 롤러코스터 타이쿤 — 무엇을 잘하나

### 장점

| 잘하는 것 | 왜 재미인가 | 우리에게 가능한가 |
|---|---|---|
| **짓는 행위 자체가 창작** | 코스터를 그리는 것이 곧 콘텐츠. 같은 부품으로 무한히 다른 것이 나온다 | ⚠ 부분적으로. 우리는 코스 프리셋+핸들 (K33) — 자유 스플라인은 폰에서 폐기했다 |
| **결과가 즉시 읽힌다** | 흥분도·멀미도·안전도가 코스 모양에서 바로 나온다. **왜 좋은지**를 숫자가 설명한다 | ✅ 이미 있다 (장비×프리셋 적합도 19×6) |
| **동선이 성능이다** | 길·벤치·쓰레기통·직원 배치가 손님 행동을 실제로 바꾼다 | ✅ K32-B 이후 길이 곧 동선이다 |
| **손님 한 명을 들여다볼 수 있다** | "이 손님은 왜 화났나"를 추적 가능. 실패가 납득된다 | ⚠ 없다. 우리는 집계만 보여 준다 |
| **되돌아와 다듬는다** | 완성이 없다. 항상 더 나은 배치가 있다 | ⚠ 약하다 — 놓으면 끝 |

### 약점 (모바일에서 특히)

1. **입력이 무겁다.** 코스터 하나에 수십~수백 클릭. 폰에서 그대로는 불가능하다.
2. **정보 밀도가 높다.** 창이 여러 개 뜨고 숫자가 많다. 393px 폭에 안 들어간다.
3. **실패가 늦게 보인다.** 몇 분 뒤에야 손님이 화난다 — 2분 세션과 안 맞는다.

## 3. 두 게임의 교차점 — 우리가 서 있어야 할 자리

```
카이로: 탭이 적다 · 결과가 빨리 온다 · 화면이 비어 있다   ← 접근성
RCT   : 배치가 창작이다 · 동선이 성능이다 · 다듬게 된다     ← 깊이

우리   : 탭은 카이로만큼 적게, 그 한 번의 탭이 RCT만큼 많은 것을 바꾸게
```

**핵심 통찰**: RCT 의 재미는 "많이 조작해서"가 아니라 **"내 선택이 결과를 설명한다"**
는 데서 온다. 조작량을 카이로 수준으로 줄여도 그 성질은 유지할 수 있다 —
**적은 탭이 큰 차이를 만들면 된다.**

그러려면 후반에 필요한 것은 **더 많은 시설**이 아니라 **같은 시설로 더 다른 결과를 낼 수
있는 축**이다. 이것이 §0 의 질문에 대한 답의 방향이다.

⚠ 그래서 "시설을 30종 더 만든다"는 **틀린 답**이다 — 카이로의 약점 ③(수치 확장)을
그대로 복제하는 것이고, 우리 설계서가 §1.5 에서 이미 금지했다
("콘텐츠를 시설 수로 세지 않는다").

## 4. UI/UX 점검 — 우리 현재 화면

지금 상태 (K28·K34·K35 기준, 전부 검사로 강제되고 있다):

| 항목 | 현재 | 판정 |
|---|---|---|
| 화면 예산 | 세로 ≤14% · 가로 ≤22% (검사가 지킨다) | ✅ 카이로급 |
| 상시 컨트롤 | 3개 (메뉴·건설·한 주) | ✅ 카이로급 |
| 패널 | 한 번에 하나 (K37) · 표면 3종 · 버튼 클래스 한 벌 | ✅ |
| 터치 타깃 | 44px 이상 (검사) | ✅ |
| 색 소유권 | `style.css` 하나 · TS 하드코딩 0 (검사) | ✅ |
| 대비 | WCAG 14쌍 (검사) | ✅ |
| **배치 흐름** | 탭 → 고스트 → 확정 | ✅ 폰에 맞다 |
| **왜 좋은지 설명** | 결산의 히트맵·요일 막대·병목 1종 | ⚠ **주 단위로만 온다** |
| **손님 개체 추적** | 없음 | ❌ RCT 의 핵심 하나가 비어 있다 |
| **되돌아와 다듬기** | 철거는 되지만 유도가 없다 | ❌ |
| **후반 목표 제시** | 의뢰 16종 · 카드 24종 | ⚠ 등급 상한에 닿으면 같이 마른다 |

### 모바일 제약 (우리 실측)

- 화면 **393×852**, 확대는 정수 배율만 (반 픽셀 금지 — K1)
- 카메라 줌 영구히 1 → **전체 조망이 없다.** 96×72 맵이 한 화면에 안 들어간다
- 세션 2분 가정 → 한 주 = 계산 0.6초 + 연출 3~5초
- 한 손 엄지 도달 범위 → 상시 컨트롤이 **하단**에 있는 이유

⚠ **전체 조망이 없다는 것이 후반 설계에 직접 걸린다.** RCT 는 공원 전체를 내려다보며
"저기가 비었네"를 읽는데, 우리는 못 본다. 후반에 "무엇을 더 할지"가 안 보이는 이유의
일부가 이것일 수 있다 — 감상 화면(축소)이 있지만 **놀이 중에 쓰는 도구가 아니다.**

## 5. 다음에 답해야 할 질문

이 분석이 좁혀 준 것:

1. **후반의 새 축은 무엇인가?** (시설 수가 아니라 — §3)
   후보: 손님 유형별 특화 · 계절 운영 전략 · 직원/서비스 품질 · 구역(zone) 개념 ·
   기존 시설의 조합 심화
2. **"왜 좋은지"를 주 단위보다 자주 보여줄 수 있나?** (§4 의 ⚠)
3. **되돌아와 다듬을 이유를 어떻게 만드나?** (RCT 의 성질, 우리에 없음)
4. **전체 조망 없이 "여기가 비었다"를 어떻게 읽히나?** (모바일 제약)
5. **★5 이후는 무엇인가?** — 끝을 두나, 무한히 두나

⚠ 1~5 는 **서로 얽혀 있다.** 하나씩 답을 정하고 나서 시스템을 설계해야 하고,
그 전에 코드를 건드리면 또 방향을 세 번 틀게 된다 (K38 에서 겪었다).
