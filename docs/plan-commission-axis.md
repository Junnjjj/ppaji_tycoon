## §0. 한 줄 정의 · 왜 · 기준선

### 한 줄

**돈을 내고 며칠 기다리면 사람·물건·손님이 도착하고, 그 도착이 연출로 회수된다.**

### 왜 — 통째로 빠진 사분면

|  | 즉시 끝난다 | 시간이 걸린다 |
|---|---|---|
| **게임이 내민다** | 주간 카드 27종 ✅ | — |
| **내가 고른다** | 가격·직원·개선·건설·코스 ✅ | **0건 ← 여기** |

직원은 누르면 즉시 고용(비용 0, 주급만), 개선은 돈 내면 즉시 레벨업, 가격 슬라이더는 즉시 반영.
**산 것도, 기다린 것도, 회수한 것도 없다.** 그래서 "운영에서 뭘 할지 명확하지 않다"가 된다.

베낄 대상은 초밥도 컨설턴트도 아니라 그 밑의 엔진이다:
① 게임이 먼저 제안한다 → ② 효과가 아니라 **티켓**을 산다 → ③ 시간이 흐르고 그동안 개입할 수 있다
→ ④ 결말을 **연출로 회수한다** → ⑤ 결과가 다음 제안의 재료가 된다.

**이 표에서 읽어야 할 넷**

1. **「후반이 빈다」 경보가 구조적으로 침묵한다** — 조건 `capped.med > 26 && idleCash.med > 1,500만`,
   실측 `15 && 1,144만`. 두 조건 다 미달이라 52~80주에서 절대 안 터진다.
2. **돈이 문제가 아니다** — 돈 부족 **0회/판**. 후반 공백은 궁핍이 아니라 **쓸 곳 없음**이다.

   항상 같은 가지를 탄다. 헤드리스가 게임이 아니라 **봇의 한계**를 재는 네 번째 사례다.
4. **현금이 후반에 다시 오른다** — 4주마다 `787 → 819 → 1,131 → 1,259 → 1,144만`. 28~52주 **+45%**.
   이것이 "출구 없음"의 직접 증거이자 H1의 표적이다.

## §1. 확정 결정 (뒤집지 말 것)

| # | 결정 | 근거 |
|---|---|---|
| **D1** | **컨설(맡긴다)과 경영(직접 만진다)은 다른 칸이다** | 회전초밥 메뉴 실측. 합치려 하면 계속 안 맞는다 |
| **D2** | **구입 = 지금 있는 걸 즉시 산다 / 수배 = 없는 걸 구해 오게 시킨다** | 새 콘텐츠의 소속이 자동으로 정해지는 한 줄. **테스트로 강제한다**(§3.6) |
| **D3** | 회전초밥 `요리` 자리에 들어갈 것은 **코스**다 | `요리`는 그 게임의 **상품**이다. 우리 상품은 수상레저다. 음식을 그 자리에 두면 테마가 흐려진다 (`pss-hermes-research.md` §3.4) |
| **D4** | 수배 시간은 **혼합** — 조달·홍보 2~3일, 구인 1~2주 | 하루 = 120tick = 24초 · 한 주 = 840tick = 168초 |
| **D5** | 하단 **`MENU` 토글 → 오른쪽 밴드**가 나타난다. **밴드가 곧 메뉴다** | 평소엔 지도 100%. 메뉴 시트가 사라져 깊이 3단 → **2단** |
| **D6** | 밴드 **6칸**, 아직 못 여는 칸은 **`?`** | `?`가 곧 튜토리얼이다 — 온보딩이 IA에 박힌다 |
| **D7** | 성장 목록 넷 해체 → **지도 말풍선 + 피드 + `목표` 한 장** | 넷이 문법이 같은데("조건 N/M → 보상") 화면이 넷이었다. 그리고 이것들은 내가 여는 게 아니라 **오는 것**이다 |
| **D8** | 음식은 **`요리` 한 화면**(요리→시설) + **2단 강화 사슬 · 약 60종** | 시설이 늘어도 화면은 하나 |
| **D9** | 시설 개선은 **지도(시설 상세)** 로. 강화품을 요구한다 | 대상이 지도 위에 있다. 목록으로 만들면 다시 뒤지기가 된다 |
| **D10** | 음식 = 체류·단체 만족, 코스 = 스릴·평판. **다른 자원** | 화면 수가 아니라 자원으로 균형을 잡는다 |
| **D11** | **게임플레이 동사가 7개가 된다** — "구해 온다" 추가 | 기존 여섯 중 어디에도 안 들어간다. 의뢰는 *받는* 것, 짓는다는 *이미 가진 걸 놓는* 것 |

### D11 보충 — v4 "재고관리 금지"와의 선

금지된 것은 **매주 발주·소모·폐기하는 관리 루프**이지 **재료를 모아 영구 해금하는 수집 루프**가 아니다
(`docs/research/pss-menu-requests.md` §2 판정). 그래서:

- 재료·레시피·장비·장식 = **영구 해금 키** (수량 없음) — 선 안쪽
- 강화품 = **시설 handle에 붙는 1회용** (`PlacedFacility.fittings?`) — 풀 재고를 만들지 않는다
- ❌ `MenuStore.ingredients`를 `Map<string, number>`로 바꾸지 않는다 — 그 순간 다음 요청은 확정적으로
  "자동 발주"와 "부족 경고"이고 HUD에 매 프레임 봐야 하는 숫자가 하나 는다

### 2.2 밴드 6칸

| # | 칸 | 회전초밥 | 안에 |
|---|---|---|---|
| 1 | **건설** | 건설 | 시설·바닥·건물·철거·이동 |
| 2 | **코스** | 요리 | 프리셋·터닝포인트·장비·시험 운행·기록 |
| 3 | **요리** | (요리의 조합) | 조합·**강화**·도감·장착 대상 |
| 4 | **상점** | 구입 + 컨설 | 탭 둘 — `지금 산다` / `맡긴다` |
| 5 | **경영** | 경영 | 가격 · 직원 배치 · **심사** |
| 6 | **목표** | (카이로엔 없음) | 열린 의뢰 · 노리는 인증 · 단골 요청 · 다음 심사 · 첫 엔딩 |
| 7 | **정보** | 정보 + 시스템 | 결산 · 도감 · 감상 · 엔딩 · 설정 |

`구입`과 `수배`를 한 칸에 둔 이유: **나란히 있어야 "이건 지금, 저건 며칠"이 대비로 읽힌다.**

`목표`를 `정보`에서 뺀 이유: **"지금 걸린 조건"을 보려고 기록을 여는 것은 성격이 반대다.**
7칸이 되지만 `?` 로 잠겨 있다가 **첫 의뢰에 열리므로** 실제 동시 노출은 5~6칸이다.

**가로 852×393 — 밴드를 2열로 접는다** (4×2). 288px → 144px 로 높이의 37%.
⚠ 세로와 **같은 DOM·같은 CSS** 다. 미디어 쿼리로 **열 수만** 바꾼다 — 방향별로 레이아웃을
두 벌 만들면 안 본 쪽이 깨진다 (기존 계약).

|---|---|---|
| **모달** | 축하 — 내가 부른 것(즉시) · 기다려서 온 것(아침) | 멈춘다 |
| **티커** | 뉴스 — 내가 안 했는데 일어난 일 **+ 내가 시킨 일의 진행률** | 안 멈춘다 |
| **토스트** | 내 행동의 짧은 대답 (거절 이유 · 확정 −N) | 안 멈춘다 |
| **지도 FX** | 어디가 좋아졌나 | 안 멈춘다 |

⚠ 티커가 진행률을 겸하는 것은 **K47-① 계약의 명시적 확장**이다. 근거: 진행률은 "지금 무슨 일이
일어나는 중인가"이고 뉴스와 같은 비차단 성질이다. **한 사건을 두 채널에 넣지 않는다**는 규칙은 그대로다 —
진행 중은 티커에만, 완료는 모달에만.

### 2.6 이펙트 모달 — 이 엔진의 5번째 단계

지금 축하 모달 11종은 **이름만 말한다** (`title`/`name`/`sub`/썸네일). *"수배 완료 · 빙수 기계"* 로 끝난다.
**무엇이 얼마나 좋아졌는지를 안 보여준다** — 회수가 안 된다.

```
┌───────────────────────────┐
│        ✨ 스프라이트        │
│        수배 완료            │  ← kicker
│        빙수 기계            │  ← title
│  ─────────────────────    │
│   카페 요금   900 → 1,150  │  ← ★ 델타 줄 (카운트업) — 지금 없는 것
│   만족            +3       │
│   메뉴 칸        2 → 3     │
│  ─────────────────────    │
│         [ 좋아! ]          │
└───────────────────────────┘
```

```ts
export interface CelebrationDelta {
  label: string;              // '카페 요금'
  from?: number | string;     // 없으면 증분만 (+3)
  to: number | string;
  tone?: 'up' | 'down' | 'flat';
}
// Celebration 에 deltas?: readonly CelebrationDelta[]
// EventShellView 에 .kevent-deltas 슬롯 (kairo-event-shell.ts)
```

⚠ 델타 값은 **sim 실효값에서 읽는다** (`feeOf`·`capacityOf`·`satisfactionBonusOf`·`menuSlotCount`).
데이터 `desc`에 글로 적지 않는다 — 밸런싱 때마다 조용히 거짓말이 된다.

**연출 순서**

| t(ms) | 무엇 | 기술 |
|---|---|---|
| 0 | 스크림(`--scrim-deep`) 페이드 | `opacity` |
| 100 | 상자 팝 | `transform: scale(.92→1)` |
| 300 | 스프라이트 튐 (`.fx-pop` 기존 클래스) | `transform` |
| 500 | 델타 줄이 한 줄씩 | `transform` + `opacity` |
| 600~ | **숫자 카운트업** (400ms) | `textContent` — 레이아웃 속성 애니메이트 금지 계약 안 |

⚠ `prefers-reduced-motion`이면 **움직임만 빼고 최종 숫자는 남긴다**. 색은 `style.css` 소유.

**어디서 · 언제** — 규칙 하나: **내가 방금 누른 것은 즉시, 기다려서 온 것은 아침에.**

| 사건 | 언제 | 델타 줄 | 상한 |
|---|---|---|---|
| 강화품 적용 | **즉시** | 요금 · 정원 · 만족 · 메뉴 칸 | 없음 |
| 요리 발견 | **즉시** | 가격 · 만족 · 태그 | 없음 |
| 요리 강화 | **즉시** | 가격 `900 → 1,150` · 만족 · 바뀐 손님층 | 없음 |
| 밴드 칸 해금 | **즉시** | 열린 칸 + 무엇을 할 수 있게 됐나 | 없음 |
| 수배 완료 — 구인 | 아침 | 역할 인원 `2 → 3` · 안전/청결 · 주급 | 하루 2건 |
| 수배 완료 — 조달 | 아침 | 들어온 재료·장비 + 그것이 여는 것 | 하루 2건 |
| 수배 완료 — 특수 | 아침 | 사건별 | 하루 2건 |
| 수배 완료 — **홍보** | — | **모달 아님, 티커** (축하할 물건이 없다) | — |
| 기존 11종 | 아침 | 해당하면 델타 줄 추가 | 하루 2건 |

⚠ **상한을 즉시형에 안 거는 이유**: PSS 부정 리뷰 1위 "팝업 과다"는 **내가 안 부른 팝업**을 말한다.
내가 강화 버튼을 눌러 뜨는 상자는 방해가 아니라 **대답**이다. 도착형에만 상한을 건다.
넘치면 버리지 않고 **티커로 강등**하고 알림함에서 다시 연다.

**요리 발견·강화의 모달은 「무엇과 바꿀까」를 묻는다** (2026-08-27 추가)

⚠ **지금 게임은 묻지 않고 덮어쓴다** — 실측으로 두 자리:
· `kairo-menu-lab.ts:155` 발견 직후 — 칸이 차 있으면 `slot = slotCount-1` 로 **마지막 칸을 교체**
· `:200` 「바로 장착」 칩 — 빈 칸이 없으면 `slot = empty ?? 0` 으로 **0번 칸을 교체**

즉 플레이어가 올려 둔 메뉴가 **묻지도 않고 사라진다.** 그리고 이것이 「슬롯이 1칸이라
음식 축이 잠겼다」는 진단을 절반 틀리게 만들었다 — 팔 수는 있는데 **그 교환이 결정으로
안 보였을** 뿐이다.

| 상황 | 모달이 하는 일 |
|---|---|
| 빈 칸이 있다 | **바로 걸고** 델타 줄로 알린다 (선택 없음) |
| 칸이 차 있다 | **지금 걸린 메뉴들이 선택지**가 된다 — 고르면 교체, `나중에` 면 도감에만 남는다 |
| 그 시설에 craft 가 아니다 | 애초에 이 경로가 없다 |

⚠ **두 입구가 같은 경로를 지난다** — 개발 버튼과 「바로 장착」 칩이 다르게 동작하는 것이
지금의 버그다. ⚠ `나중에` 는 **아무것도 안 지운다** — 되돌릴 수 없는 교체를 기본값으로
두지 않는다 (「파괴적 행동은 한 겹 안쪽」과 같은 규칙).

**배경** — `.kevent-stage` 는 지금 `art | placeholder` 두 상태이고 실제 삽화가 없어 늘
`placeholder`(CSS 절차 무대)다. **P1.5-B 가 `art` 를 채운다** — 한국 빠지 풍경 9종
(`CardTheme` 8 + 축하 1). ⚠ **전경은 기존 스프라이트 합성을 유지한다** — AI 가 그리는 것은
배경뿐이고 그 위에 게임의 실제 손님·시설이 올라가야 "이 사건이 **내 빠지**에서 일어났다"가 된다.

**모달과 FX의 분업**

|  | 모달 | 지도 FX |
|---|---|---|
| 시간 | **멈춘다** | 안 멈춘다 |
| 자리 | 화면 가운데 | **그 칸 위** |
| 무엇 | 무엇이 **얼마나** 좋아졌나 | **어디가** 좋아졌나 |

강화 적용은 **둘 다** 쓴다 — FX가 그 칸에서 먼저, 모달이 그 위에.
❌ 진행 게이지를 FX로 만들지 말 것 (`FxHandle`은 일회성, `fx.ts:162-169` 주석).

### 3.1 이름

`src/sim/kairo/commission.ts` / `CommissionStore` / `src/data/kairo-commissions.json`.

⚠ **파일 머리말에 용어 경고를 박을 것**: 한국어 "의뢰"는 이미 `progress.ts`의 `QuestDef`다.
컨설 작업은 화면에서 **"수배"**로 부르고 영어는 commission으로 쓴다. 이 한 줄이 없으면
다음 사람이 `QuestDef`에 `days`를 붙인다.

### 3.2 시간 모델 — 절대 tick 하나

```ts
// src/sim/kairo/week.ts
export function absoluteTick(weekNo: number, tickInWeek: number): number {
  return weekNo * TICKS_PER_WEEK + tickInWeek;
}
// WeekRunner getter — main 과 봇이 이 하나를 공유한다
get absTick(): number { return absoluteTick(this.weekNo, this.live?.tick ?? 0); }
```

주 경계에서 **연속이다** — 주 N의 마지막 tick은 `(N-1)*840+840`이고, `finish()` 뒤 `weekNo=N`·`live=null`이면
`N*840`이라 같은 값이다. 이 연속성이 깨지면 마감일이 주 경계에서 한 번씩 튄다.

**왜 쌍(週, tick)이 아닌가** — 판정이 `dueTick <= now` 비교 **한 번**이다. 쌍은 비교 순서가 둘이라
`exam`이 겪은 "화면은 이번 주말인데 판정은 다음 주" 부류가 재발한다.

**상수 변경 방어** — 데이터에는 `days`만 적고 환산은 발주 시 1회.
`fromSnapshot(s, nowTick)`이 `dueTick`을 `[now, now + MAX_JOB_DAYS*120]`로 **클램프**한다.

### 3.5 RNG

```ts
export const COMMISSION_RNG_SALT = 0xc0f5;
```
기존 salt 전수(충돌 없음): `0x57ea7 weather · 0x6ae57 guests · 0xae601 regular · 0xacc1 accident ·
0xca7d card · 0x57aff staff · 0xc0125 course · 0xbe0 bench · 0x4237 jitter · 0x7e44a1 worldgen`.

배선 4곳 (`cardRng` 전례): `main.ts:1568` 옆 · `tools/kairo-sim.ts:1604` 옆 ·
세이브 `commissionRngState?` · `week-rng-isolation.test.ts` 형태의 격리 검사.

⚠ **`staffRng` 재사용 금지** — `idleHandles`가 `unmaintained` 수에 **비례해** 뽑는다.
구인을 같은 스트림에 넣으면 구인한 주와 안 한 주가 고장 판정을 밀어 사고·선 시설이 달라진다
(K36-B③ 사고 `202,360 vs 191,680`의 정확한 재현).

⚠ **주 4스트림에 5번째를 더하지도 않는다** — 수배는 `begin/step/finish` **밖**, 주 경계의 플레이어 행동이다.

**뽑기 규약 둘**
1. **발주 시 roll을 1회 무조건 뽑는다** (`chance === 1`이어도). 안 뽑는 최적화를 넣는 순간
   "구인을 하나 끼웠느냐"에 따라 뒤에 발주한 조달의 roll이 통째로 밀린다.
2. **완료 판정은 결과와 무관하게 정확히 2뽑기** (성공 판정 1 + 결과 선택 1). 실패해도 결과 뽑기를
   **버리며 소비한다** — 안 그러면 성공한 판과 실패한 판의 그 뒤 특수 작업 결과가 갈린다.

**왜 완료가 아니라 발주에서 뽑나** — ① 흐름 모드(하루 advance)와 배치 모드(주 advance)의 뽑기 **순서**가
발주 순서로 고정된다 ② 완료 직전 리로드해 재굴림하는 세이브 스컴이 막힌다(발주 직후 `persist()`).
**`outcome: boolean`이 아니라 `roll: number`를 저장하는 이유**: 나중에 "추가 투자로 확률을 올린다"를
넣을 때 **재굴림 없이** `chance`만 바꾸면 된다 — 개입 슬롯을 여는 데 드는 비용이 필드 하나다.

### 3.6 완료를 어디서 부르나 — 판정 1곳, 호출 2곳, 연출 1곳

```
            week.step(n)        ← flowTick 게이트 5개가 여기까지만 온다
                 │
  afterStep() ───┴──→ commissions.advanceTo(week.absTick)   ← ① 하루 눈금
                            │
                            ├─→ 효과 적용 (재료 해금·채용·현금) ← **즉시. 여기가 상태다**
                            └─→ arrivalQueue.push(Celebration) ← 휘발. 연출만
                                       │
                     (다음 아침 tick>=8 & !panelHost.anyOpen) → unlockView.show

  settleWeek() ───→ commissions.advanceTo(week.absTick)      ← ② 주 눈금 (배치·봇용)
```

**① `afterStep()` — `syncCash()` 바로 뒤** (`main.ts:1914`).
`flowTick`의 게이트 5개(`flow.frozen` · `hud.confirming` · 주 경계 · `scene.tickingEnabled` ·
`panelHost.anyOpen`)가 **전부 자동으로 상속된다** — `advanceTo`가 읽는 건 `week.absTick`뿐이고
그 값은 `week.step()`이 돌 때만 움직인다. **새 게이트를 하나도 안 만든다.**

⚠ **효과는 due tick에, 연출은 아침에.** `arrivalQueue`는 저장 안 된다(`main.ts:1547`).
그러므로 재료 해금·채용·현금은 `advanceTo`가 돌려준 **그 자리에서** 적용하고 `persist()`한다.
큐에는 표시용 데이터만 넣는다. 이 분리가 없으면 리로드 한 번에 2주짜리 구인이 증발한다.

**② `settleWeek()` — `week.finish()` 뒤.** 흐름 모드에서는 ①이 이미 tick 840으로 불렀으므로
**완전한 no-op**이다(멱등). 존재 이유는 `week.run()` 배치 경로(`tools/kairo-sim.ts`, `golden.test.ts`)다.
**멱등이 이 설계의 하중 지지점이다.**

★ **팔레트가 원인이 아니다.** 색상환도 채도도 재질도 이미 있다. 1순위는 **타이포 위계** —

⚠ 이 진단이 "예쁘게 만들자"를 **네 개의 잴 수 있는 축**으로 바꾼 것이 이 페이즈의 전제다.
막연한 미감으로 CSS 를 만지면 다음 사람이 되돌린다.

이 페이즈는 **두 단**이다. A 는 이 머신에서 끝나고, B 는 그림 생성 권한이 있는 세션에 위탁한다.
⚠ **A 가 B 없이도 닫힌다** — 절차 폴백이 계약을 채우므로 그림이 안 와도 게임이 안 깨진다.
이 순서가 아니면 "그림을 기다리는 동안 아무것도 못 하는" 상태가 된다.

## §5. 페이즈 종료 게이트 — 6부

모든 페이즈가 **같은 6부**로 닫힌다. 하나라도 빨간불이면 다음 페이즈로 안 넘어간다.
`/ppaji-phase-gate <페이즈>` 가 이것을 수행한다.

| 부 | 무엇을 재나 | 어떻게 |
|---|---|---|
| **A. 구현 완료** | 계획의 필수 항목이 실제로 있나 | §4의 체크리스트를 파일·심볼·데이터 항목 수로 **세어서** 대조 |
| **B. 아키텍처 정합** | 불변식 1·2·3이 안 깨졌나 | `sim/`이 `phaser`/`render`/`ui`/`assets`/`save`를 import 안 함 · `Math.random`/`Date.now`/`performance.now`/`new Date` 0건 · 새 콘텐츠가 JSON에 있고 코드에 목록 0 · `npm run lint` (ESLint가 강제) · `npx vitest run src/sim/invariants.test.ts` |
| **C. 계약 정합** | **코드·게이트·문서가 같은 말을 하나** | 이 저장소가 반복해서 어긋난 지점. CLAUDE.md 문장 ↔ 코드 상수 ↔ `verify-kairo.ts` 판정을 **3자 대조**. 예: "상시 제어 N개" 문장 vs 게이트 판정 vs 실제 DOM |
| **D. 검사 정직성** | 새 검사가 **실제로 뭔가를 재나** | 그 페이즈가 추가한 음성 대조군을 **하나씩 켜서** 대응 검사가 빨간불이 되는지 확인. 안 빨개지면 그 검사는 아무것도 안 재는 것 |
| **E. 밸런스·성능** | 숫자가 문턱 안인가 | `sim:kairo --seeds 12 --weeks 26` + `--seeds 24 --weeks 52` · 골든 15/15 · `--determinism` · 프레임 예산 |
| **F. 사람 확인** | 자동이 못 잡는 것 | 393×852 실제 터치 · 30초 무설명 과업 · 첫 화면 인상. **자동 통과를 사람 승인으로 보고하지 않는다** |

### 왜 B·C·D인가

이 저장소는 **「검사가 조용히 통과」를 열 번 밟았다**. 대표 사례:
- 회전 게이트 — 118회 생성이 접지·광원·팔레트를 **전부 통과하고도 한 장도 안 돌아 있었다**
- `controls === 6` — 수가 우연히 같아져 "가려졌다"와 "안 가려졌다"를 구분 못 했다
- `[data-goal-role].length === 3` — 메뉴 행 2개가 수를 채워 **조용히 통과**
- `.kgoal-secondary` 대조군 — 삭제된 선택자를 계속 대조해 항상 `false`

**D의 규칙**: 대조군은 **코드에** 둔다. 손으로 한 번 되돌려 확인한 것은 다음 사람에게 안 남는다.

### 판정 표기

| 표기 | 뜻 |
|---|---|
| ✅ 통과 | 실제로 재서 문턱 안 |
| ❌ 실패 | 실제로 재서 문턱 밖 |
| ⬜ **미측정** | 못 쟀다. **통과로 쓰지 않는다** |

⚠ 워크트리에 `assets/generated/kairo/*.png`가 없으면 픽셀 게이트는 **⬜ 미측정**이다.
`npm run test`의 실패 2건이 그것이고, **정확히 2건인지** 매번 확인한다 (3건이면 새 실패).

첫 진단은 「봇이 단골 요청만 개발한다」였다. 그래서 계측기를 먼저 고쳤다 — 봇에
**메뉴 개발 정책**(주당 시도 2회 · 한 주에 한 시설 · 실패한 짝은 건너뛴다 · **정답표는

**그래도 안 움직였다.** 그리고 새 지표가 이유를 숫자로 냈다:

| 지표 (52주) | 값 |
|---|---|
| **2칸 열린 craft 시설** | **중앙 0%** |
| 발견한 레시피 | 중앙 **0종**/판 (최대 1) |
| 평균 개선 단계 | 1.81 / 5 |

⚠ **`menuSlotsForLevel` 이 병목이다.** 슬롯은 레벨 **3** 에 2칸이 되는데, 52주 봇 플레이에서
craft 시설이 거기 닿는 판이 **중앙 0%** 다. 즉 **레시피를 스물여섯 종 넣든 예순 종 넣든
시설마다 파는 것은 한 종**이고, 시작 메뉴가 그 한 종이다.

**콘텐츠가 아니라 게이트의 문제다.** 계획 §3.10 이 「`menuSlotsForLevel` 을 개선 단계에
그대로 묶어 둔다 — 그것이 '시설을 키우면 안이 달라진다'를 만드는 유일한 고리다」라고
적었는데, 실측은 그 고리가 **한 번도 안 걸린다**고 말한다.

**다음 결정은 페이싱이다 (사용자 몫)** — 셋 중 하나:
· 슬롯 문턱을 3 → **2** 로 (레벨 2 에 2칸)
· 레벨 1 에 **2칸** (시작부터 두 종)
· 개선 자체를 빠르게 (avgLevel 1.81 을 올린다 — 다른 축을 통째로 흔든다)

⚠ 어느 쪽이든 **밸런싱 재측정이 필요하고**, 그래서 데이터를 더 넣기 전에 이 결정이 먼저다.
강화 사슬(2단 ~30종)도 같은 게이트 뒤에 있으므로 지금 넣으면 **역시 안 재진다.**

**안 한 것**: **2단 강화 사슬**. `base`/`add`/`hint` 필드와 타입은 넣었지만 `develop()` 의
강화 흐름과 데이터(강화 레시피 ~30)는 아직이다. ⚠ **지금 넣으면 안 된다** — 위 게이트 뒤에
