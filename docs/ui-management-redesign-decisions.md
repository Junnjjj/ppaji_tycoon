# 모바일 경영 UX 전면 재구성 — 계획·결정·구현 추적

> **상태:** 2026-08-26 `main`의 UI 재구성 기준 문서  
> **구현 기준점:** `818f62e58e9dd40819e3a64155ca11bcb4e362b3` (`feat(ui): 모바일 경영 UX 전면 재구성`)  
> **범위:** 홈, 전체 메뉴, 운영·성장·기록·설정, 의뢰·소원·인증·단골, 건설, 코스 결과 확인, 한국어 문구, 검증 계약  
> **주의:** 자동 검증 통과는 사람의 시각 선호·30초 사용성 승인과 같은 뜻이 아니다.

이 문서는 최종 화면 목록만 적는 문서가 아니다. **어떤 문제가 있었고, 어떤 대안을 버렸으며, 왜 현재 구조를 골랐고, 코드와 검증에서 어디를 보면 그 결정을 확인할 수 있는지**를 추적한다.

내부 조사·Claude 감사 원문은 `.hermes/plans/`에 같이 보존한다. 이 문서가 현재 구현을 읽는 정본이고, 원문은 당시 판단과 변경 이력을 확인하는 역사 자료다.

## 1. 왜 전면 재구성이 필요했나

이전 UI는 기능이 없는 것이 아니라 **기능이 사용자의 행동 흐름으로 묶이지 않은 상태**였다.

- 하단 메뉴 한 장에 운영, 성장, 기록, 설정, 의뢰, 소원, 인증을 길게 쌓아 목적지를 찾기 어려웠다.
- 393×852에서 버튼 상자는 44px였지만 하단 바가 입력을 가로채 실제로 눌리지 않는 항목이 있었다.
- 홈의 A/B/C 목표 중 보조 목표는 글자가 숨고 아이콘만 남아 다음 행동을 예측하기 어려웠다.
- 건설 성공 뒤 붓이 남아, 사용자가 연속 설치를 선택하지 않았는데도 다음 탭에서 다시 결제될 수 있었다.
- 코스 적용 성공은 짧은 토스트 뒤 사라져 무엇이 적용됐는지 확인할 영속 결과 화면이 없었다.
- 의뢰의 조건 달성과 실제 보상 지급이 한 문장에 섞여, 지금 보상을 받은 것인지 주말에 받을 것인지 구분되지 않았다.
- `Today`, 내부 ID, 영문 등급명, 서로 다른 금액 눈금과 명사형 라벨이 섞여 있었다.
- 기존 브라우저 검사는 상자 크기나 개수를 주로 확인했고, 실제 터치 소유권과 기능의 정체를 충분히 재지 못했다.

따라서 목표는 CSS를 새로 칠하는 것이 아니라 다음 다섯 계약을 동시에 세우는 것이었다.

1. 홈에서 다음 행동이 한 줄로 읽힌다.
2. 메뉴에서 목적지를 이름과 위계로 예측할 수 있다.
3. 한 순간에 화면 하나만 입력을 소유한다.
4. 건설·코스·의뢰의 완료 상태가 명시적으로 끝난다.
5. 393×852 실제 터치와 기존 세이브에서 회귀를 막는다.

## 2. 왜 `운영 / 성장 / 기록 / 설정`인가

네 그룹은 기능 이름이 아니라 사용자가 메뉴를 열 때 묻는 질문으로 나눈 것이다.

| 그룹 | 사용자의 질문 | 포함하는 기능 | 다른 그룹에 두지 않은 이유 |
|---|---|---|---|
| **운영** | “지금 돌아가는 것을 무엇으로 조정하지?” | 가격, 직원, 시설 개선, 코스 | 현재 운영값을 바꾸는 동작이다. 진행 목표나 과거 결과와 섞으면 조정과 확인의 경계가 흐려진다. |
| **성장** | “다음에 무엇을 달성해야 하지?” | 목표, 심사, 의뢰, 소원, 인증, 단골, 도감 | 모두 진행 조건과 해제 경로를 보여 준다. 인증은 이미 딴 기록이기도 하지만, 플레이 중에는 ‘따는 중인 목표’이므로 기록보다 성장에 둔다. |
| **기록** | “지난 운영에서 무슨 일이 있었지?” | 지난 결산, 리조트 보기, 엔딩 이정표 | 이미 일어난 결과를 다시 확인하는 영역이다. 현재 조건을 채우는 인증은 여기에서 제거했다. |
| **설정** | “판 자체를 어떻게 다루지?” | 배속, 소리 자리, 자동 저장 정보, 새 게임 | 운영 추천 대상이 아니며, 특히 새 게임은 파괴적 행동이라 가격·직원과 같은 위계에 둘 수 없다. |

### 버린 대안

- **기존 한 장 스크롤 유지:** 구현은 작지만 항목이 추가될 때마다 발견 가능성이 계속 나빠진다.
- **기능별 상시 홈 버튼 추가:** 홈의 터치 예산과 지도 면적을 침범하고, 상단은 읽기 전용이라는 원칙을 깨뜨린다.
- **설정을 경영 추천 그룹에 포함:** 추천기가 “새 게임을 시작하세요”를 오늘 할 일로 고를 수 있어 의미가 맞지 않는다.
- **인증을 기록에 유지:** 획득 이력보다 현재 달성 조건과 다음 행동이 더 중요하다.

현재 라우터와 화면 깊이 계약은 `src/ui/kairo-management.ts`의 `ManageRouteId`, `ManageScreenId`, `MANAGE_ROUTES`, `MANAGE_LISTS`가 소유한다. 깊이는 **홈 → 메뉴 인덱스 → 목적지/목록**을 넘기지 않는다.

## 3. 홈에서 결과를 확인하고 다시 돌아오는 흐름

기본 경로는 다음과 같다.

```text
홈
 ├─ 다음 할 일 ───────────────► 현재 필요한 실제 동작
 ├─ 메뉴
 │   ├─ 운영 ─► 세부 기능 ─► 결과 확인 ─► 닫기/뒤로
 │   ├─ 성장 ─► 진행 목록 ─► 상세 사건 화면 ─► 다음 행동/복귀
 │   ├─ 기록 ─► 지난 결과 확인 ─► 복귀
 │   └─ 설정 ─► 판 설정/새 게임 확인 ─► 복귀
 └─ 건설 ─► 대상 선택 ─► 조준 ─► 확정 ─► 완료/반복
```

이 구조를 택한 이유는 **진입과 결과 확인을 분리하되 길을 잃지 않게 하기 위해서**다.

- 홈은 전체 기능을 나열하지 않고 `다음 할 일`, `메뉴`, `건설`만 직접 노출한다.
- 메뉴 인덱스는 행동을 수행하는 긴 문서가 아니라 목적지를 고르는 라우터다.
- 세부 기능은 자체 제목과 결과를 가진다. 버튼 이름과 열리는 화면 제목은 같은 뜻을 쓴다.
- `뒤로`는 한 단계 위로, `닫기`는 홈으로 돌아간다는 차이를 유지한다.
- 상세를 브라우저 `alert`/`prompt`로 열지 않는다. 게임의 패널 소유권, 44px 터치, 한국어 문구, 모바일 레이아웃 검증을 모두 받는 내부 화면을 사용한다.

상세 사건 화면의 공용 경계는 `src/ui/kairo-event-dialog.ts`, 리조트 이름 변경은 `src/ui/kairo-showcase.ts`에 있다.

## 4. 의뢰 생명주기와 보상 시점을 왜 분리했나

의뢰는 단순히 `진행/완료` 두 상태가 아니다. 사용자가 실제로 이해해야 하는 흐름은 다음과 같다.

```text
발견
 → 조건 확인
 → 진행 추적
 → 조건 달성
 → 보상 지급 시점 확인
 → 보상 확인
 → 다음 행동
```

조건을 달성한 순간과 보상이 지갑·해금에 반영되는 순간이 다를 수 있다. 이 둘을 `완료` 한 단어로 합치면 다음 문제가 생긴다.

- 조건만 채운 상태를 보상을 받은 상태로 오해한다.
- 주말 판정 전까지 무엇을 기다려야 하는지 알 수 없다.
- 보상을 실제로 받았는지 확인할 영속 증거가 없다.
- 같은 사건을 토스트·티커·모달에 중복 발화하기 쉽다.

그래서 목록 카드에는 **조건, 현재 진행량, 조건 달성 여부, 보상, 지급 시점**을 따로 표시한다. 예를 들어 조건을 채웠지만 주말 지급 전이면 `조건 달성 · 주말에 보상`처럼 말한다. 상세 화면에서는 보상 확인 후 가능한 다음 행동을 제공한다.

사건 채널은 기존 계약을 유지한다.

| 채널 | 역할 | 의뢰에서의 사용 |
|---|---|---|
| 모달/상세 사건 화면 | 사용자가 열어 본 상세, 축하, 되돌릴 수 없는 확인 | 의뢰 조건·보상·다음 행동을 읽는 영속 표면 |
| 티커 | 내가 조작하지 않아도 일어난 뉴스 | 보상 발생 등 실제 사건 알림. 목표 설명을 복창하지 않음 |
| 토스트 | 방금 한 행동의 짧은 답 | 열기 실패·조건 미달 등 즉시 응답 |

한 사건을 여러 채널에서 동시에 반복하지 않는다.

## 5. 한국어·금액·행동 라벨 원칙

### 5.1 한국어

- 내부 ID(`hygiene`, `shower_row`)를 화면에 노출하지 않는다.
- 번역투 명사 나열보다 사용자가 결과를 예상할 수 있는 자연스러운 동사형 라벨을 쓴다.
- 같은 개념은 같은 이름과 같은 눈금을 사용한다.
- 버튼 라벨과 열리는 화면 제목의 의미를 맞춘다.
- `Today`, 영문 등급명, 개발자 용어를 사용자 화면에서 제거한다.
- 잠김 문구는 이유에서 끝내지 않고 가능한 해제 방법까지 말한다.

공통 용어는 `src/ui/kairo-terms.ts`가, 공통 원화 표시는 `src/ui/money.ts`가 소유한다.

### 5.2 금액

- 같은 화면 안에서는 한 눈금을 사용한다.
- 0에도 단위를 붙여 `0원`처럼 표시한다.
- 비용, 현재 현금, 실제 차감액의 관계를 확인할 수 있게 한다.
- 명목가를 전역으로 ×10 하는 별도 디자인 결정과, 화면 내 포맷 일관성을 혼동하지 않는다.

### 5.3 행동 라벨

- `적용`보다 `이 설정 적용`처럼 대상과 결과를 말한다.
- 토글은 현재 상태와 누르면 일어날 행동을 구분한다.
- `닫기`는 목적지 탭과 같은 줄에 섞지 않는다.
- `새 게임 시작`은 설정 아래에 두고, 지워지는 현재 진행을 수치로 보여 주는 두 번째 확인을 거친다.

## 6. 회귀 계약으로 남긴 세 가지

### 6.1 단일 입력 소유권

이전에는 시트가 열려도 홈의 하단 바나 티커가 같은 z축에서 터치를 가로챘다. 크기 검사는 통과했지만 실제 버튼은 안 눌렸다.

현재 계약은 다음과 같다.

- 홈, 메뉴/시트, 조준, 코스, 모달 중 **하나만** 입력을 소유한다.
- 가림 문제를 `z-index` 경쟁으로 덮지 않는다.
- 보이는 enabled control의 중앙과 네 inset 지점에서 `elementFromPoint`가 자기 자신 또는 자식을 반환해야 한다.
- `PanelHost`가 화면 배타성을 소유하고, 홈 입력층은 표면 상태에 맞춰 같이 내려간다.

관련 구현: `src/ui/panels.ts`, `src/ui/kairo-hud.ts`  
브라우저 게이트: `tools/verify-kairo.ts`의 393×852/852×393 실제 터치·5점 소유권 검사

### 6.2 건설 one-shot 기본

시설·바닥·건물·철거·이동마다 성공 후 붓을 정리하는 코드를 따로 두면 한 경로가 반드시 빠진다. 그래서 `src/ui/kairo-build-flow.ts`의 `BuildSession`이 `idle/selecting/aiming/repeating`을 한 경계에서 관리한다.

- 기본은 한 번 설치하고 종료한다.
- 사용자가 `연속 설치`를 명시적으로 켠 경우에만 붓·조준·확정 상태를 유지한다.
- 성공·취소·패널 전환에서 brush, aim, ghost, reticle, confirm callback을 함께 정리한다.
- one-shot 완료 뒤 빈 지도 터치가 추가 상태 변화나 비용 차감을 만들면 회귀다.

### 6.3 영속 결과 화면

짧은 토스트는 결과 확인의 유일한 증거가 될 수 없다.

- 코스는 조정 → 4초 시험 → 결과 확인 → 적용 완료 단계를 가진다.
- 변경값이 없으면 `변경 없음`으로 적용을 막는다.
- 적용 성공 뒤 패널을 즉시 닫지 않는다.
- 새 현재값, 실제 차감액, 저장 여부를 사용자가 확인하고 `닫기`를 눌러야 홈으로 돌아간다.
- 재열기와 새로고침 뒤에도 적용값이 같아야 한다.
- 의뢰 완료·보상 확인도 자동 소멸 토스트가 아니라 상세 사건 화면에서 읽을 수 있게 한다.

관련 구현: `src/ui/kairo-course.ts`, `src/ui/kairo-event-dialog.ts`, `src/main.ts`  
행동 계약: `courseDockActions()`와 코스 브라우저 스위트

## 7. 계획에서 실제 구현으로 바뀐 점

감사 문서는 당시 화면과 코드에 대한 계획이므로 최종 구현과 일치하지 않는 제안도 포함한다. 다음 표로 변경을 추적한다.

| 계획/문제 | 최종 선택 | 이유 | 상태 |
|---|---|---|---|
| 홈 A/B/C 3칸 | 홈은 즉시 행동 한 줄, 중·장기는 성장 화면 | 좁은 B/C 칸에서 이름이 사라지고 아이콘만 남았기 때문 | 구현 |
| 한 장 메뉴 스크롤 | 인덱스 + 운영/성장/기록/설정 라우터 | 기능 추가 때마다 메뉴 길이가 늘어나는 구조적 문제 제거 | 구현 |
| 인증을 기록에 유지 | 성장으로 이동 | 현재 달성 조건과 해제 경로가 핵심 | 구현 |
| 의뢰/인증 버튼이 같은 시트로 스크롤 | 전용 목록 화면 | 같은 모양 버튼의 동작 차이와 무반응 앵커 제거 | 구현 |
| 상세를 `alert`로 표시 | 공용 게임 내 사건 화면 | 입력 소유권·모바일·스타일·후속 행동 검증을 받기 위해 | 구현 |

## 9. 검증 계획과 현재 증거

### 9.1 필수 자동 검증

```bash
npm run typecheck
npm run lint
npm run test
npm run build
npm run verify:kairo
```

브라우저는 최소 다음을 확인한다.

- 393×852 세로와 852×393 가로
- 신규 세이브와 기존 v8 세이브
- 보이는 enabled control의 44×44px 이상과 5점 실제 소유권
- 홈→메뉴→성장→의뢰→상세→다음 행동→복귀
- 건설 one-shot 뒤 추가 지도 탭으로 상태·현금이 변하지 않음
- 명시적 연속 설치에서만 두 번째 설치·결제 발생
- 코스 실제 핸들 drag → 4초 시험 → 결과 → 적용 완료 → 닫기 → 재열기/새로고침 일치
- 가로 화면 overflow와 화면 밖 반쪽 버튼 0
- 콘솔 오류 0, 요청 실패 0

### 9.2 외부 공유 검증

외부 URL만 확인하지 않는다. 같은 실행에서 다음을 함께 확인한다.

1. dev 서버를 재기동한다.
2. 브라우저를 하드 리로드한다.
3. DNS와 HTTP 200을 확인한다.
4. branch, SHA, source digest, 첫 DOM을 현재 소스와 대조한다.
5. 393×852에서 실제 사용자 경로를 조작한다.
6. 콘솔 오류와 요청 실패가 0인지 확인한다.

Quick Tunnel 주소는 일시적이므로 URL 문자열 자체를 완료 증거로 보존하지 않는다.
