# 시간 모델 재검토 — 주 버튼이 맞나, 카이로식 흐르는 낮이 맞나

> 2026-08-19. 사용자 질문: "주 빨리감기(1주, 2주, 3주…)가 맞을까? 카이로소프트식
> 낮밤 형식이 더 적절하지 않을까?" + "메인 타겟은 **쉽게 하는** 플레이어다."
>
> 이 문서는 **기획/설계만** 다룬다. 코드 변경 없음. 결론은 §5, 결정 요청은 §7.

---

## 0. 지금 우리가 서 있는 자리

v2 가 실시간을 버리고 주 단위를 고른 근거는 design.md 에 한 줄이다:

> "실시간이 폰에 안 맞는다 — 지속적 주의를 요구해 2분 세션에서 성립하지 않는다" (design.md:11)

**이 근거에 논리적 결함이 있다.** "실시간"에는 두 종류가 있는데 하나로 뭉뚱그렸다:

- **압박형 실시간** (RCT·스타크래프트) — 안 보고 있으면 나빠진다. 폰에 안 맞는 건 이쪽이다
- **관조형 실시간** (카이로소프트) — 천천히 흐르고, 결정할 땐 암묵적으로 멈추고,
  안 본다고 나빠지지 않는다. **2분 세션의 왕이 바로 이 방식이다**

우리는 전자를 기각하면서 후자까지 같이 버렸다. 그리고 v4 에서 그 대가를 이미
한 번 치렀다 — *"손님이 노는 광경이 이 게임 최대의 보상인데 리플레이로 격리시켰다"*
(CLAUDE.md v4 표). 그때의 처방(압축 연출 3~5초)은 격리를 완화한 것이지 해소한 게 아니다.
**공원은 여전히 버튼과 버튼 사이에 죽어 있다.**

## 1. 카이로소프트의 시간은 실제로 어떻게 되어 있나 (1차 소스)

Pool Slide Story 위키 원문(wiki.gg, 인포박스+본문)에서 직접 확인한 사실:

| 사실 | 원문 근거 |
|---|---|
| **1년 = 16일** (계절 4 × 4일) | "Each season consists of 4 in-game days: 3 weekdays and 1 weekend (when peak customers arrive)" |
| 한 판 = 8년 = **128일** | "The game ends at the end of Winter, Year 8" |
| 시간은 **자동으로 흐른다**, 배속은 엔드게임 해금 | 인포박스 `fastmode = endgame` |
| 시간은 **세션에 묶인다** — 끄면 멈춘다, 방치 진행 없음 | High Sea Saga 스레드 "Time stops when I leave the game and pauses construction" |
| **계절 이벤트가 마디**를 만든다 | "Each Spring and Fall … Certification … judged on that season's weekend at 3pm" — 마감이 있는 심사 |
| 손님이 **개별 인물**이다 (71명, 선물·요청 3단계) | "71 Friends … make 3 requests … triggered at Satisfaction thresholds" |
| 손님 사진 = SNS 좋아요 → **1000개 모이면 다음 구역 해금** | "When an Area has received 1000 Likes … the next area will become available" |

구조를 요약하면: **시간은 흐르는 낮이고, 마디는 하루 → 계절 이벤트 → 연말 순으로
겹겹이 있다.** 플레이어는 손님이 노는 걸 **보면서** 짓는다. 시간 압축이 극단적이라
(1년=16일) "하루를 구경하는 것"이 지루할 새가 없다.

플레이어 반응 (스팀 리뷰, 상위 추천):

- "All kairosoft games have a simple loop that is addictive and charmingly presented"
- "The Kairosoft Effect did eventually get its hooks in me!" — 새벽 7시까지 플레이
- "didn't ever feel bored doing" — 다른 카이로작보다도 지루하지 않았다는 평
- 비판: "took a few hours to really get into its groove" (초반이 느리다),
  Steam 이식판 조작 불편 — **초반 페이싱과 입력이 이 장르의 약점**이라는 뜻.
  우리 UX 검수(design-ux-audit.md)가 잡은 초반 30분 문제와 정확히 같은 자리다

카이로 중독성의 정체 (복수 소스 교차):

- "**항상 무언가를 향해 가고 있다**" — 해금·확장·순위가 끊기지 않는다 (TheXboxHub, Grokipedia)
- 짧은 세션 + 깊은 진행 = "중독적 단순함"
- 손님이 이름 있는 개인이라 **애착**이 생기고, 좋아요→구역 해금으로 **구경이 곧 진행**이 된다

## 2. 반대편 근거 — 턴(주) 버튼의 힘도 진짜다

주 단위를 그냥 깎아내리면 안 된다. "한 턴만 더" 심리는 문명이 증명한 실재하는 훅이다:

- 턴은 **달성 가능한 정지점**을 만든다 — "이번 주만 보고 자야지" (kangmu, neurospicy)
- 보상이 **지연**되어 있어 다음 턴을 눌러야 확인된다 — 기대가 증폭된다
- Sid Meier: "인간은 서프라이즈를 사랑한다. 결과를 기다리는 것이 그 효과를 증폭시킨다"
  (gamedeveloper.com)
- 실시간 vs 턴 일반론 (multibit games 외): 실시간 = 진행바를 지켜보는 기대감·도파민,
  턴 = 숙고와 통제감, 대신 느리게 느껴질 수 있다

**단, 이 훅이 작동하려면 턴의 끝에 보상이 있어야 한다.** 우리 실측(design-ux-audit.md §5)은
`한 주` 버튼이 보상(결산)이 아니라 **질문(카드)** 부터 돌려준다는 것을 잡았다. 지금 우리는
턴제의 힘도 제대로 못 쓰고 있다.

## 3. "쉽게 하는" 타겟이 가리키는 방향

한국어 소스 포함 (에어브릿지·MAF·나무위키 건설경영 항목):

- 이 장르의 유인은 **컨트롤이 쉬운 것**과 **편안함** — 휴식을 원하는 플레이어
- "**하염없이 구경하는** 방치형 게임스러운 플레이도 가능" — 구경 자체가 유효한 플레이다
- 배치를 결정하고 최적화하는 과정 자체가 재미의 핵심 (드로잉 툴과 닮은 인터페이스)

쉬운 타겟에게 두 모델을 대 보면:

| | 주 버튼 (현행) | 흐르는 낮 (카이로) |
|---|---|---|
| 아무것도 안 하면 | **아무 일도 안 일어난다** (버튼을 눌러야 게임이 존재) | 공원이 돌아간다 — 구경이 플레이다 |
| 매 턴 요구되는 것 | 카드 선택 + 결산 읽기 = **매번 의사결정** | 없음. 결정은 하고 싶을 때 |
| 실수의 무게 | 한 주가 통째로 결과로 돌아온다 | 보다가 이상하면 바로 고친다 |
| 세션 끝내기 | 턴 경계에서 (좋음) | 아무 때나 (더 좋음 — 시간이 세션에 묶임) |

**"쉽게"의 관점에서 매 턴 의사결정을 요구하는 현행이 오히려 무겁다.** 결산 숫자를
읽어야 다음 행동이 나오는 구조는 엑셀을 싫어하는 타겟에게 벽이다.

## 4. 우리 코드는 어느 쪽에 가까운가 (실측)

전환 비용을 재 보니 **생각보다 가깝다**:

- sim 은 이미 tick 기계다: 하루 = 120 tick, 주 = 840 tick (`week.ts:39-42`).
  주는 tick 의 묶음일 뿐이다
- 렌더러는 이미 tick 프레임을 **연속 재생**할 줄 안다 — 압축 연출이 그것이다
  (`playWeek(rep.playback, 3500)`, `main.ts:868`). 손님 보간·깊이·버스 동기화까지
  K36-B~K37 에서 이미 풀었다
- 결정론 불변식은 **안 다친다**: 실제 시간은 "tick 을 언제 소비하나"만 정하고 tick 의
  내용은 그대로다. clock.ts 의 원칙("배속은 tick 수를 곱함")과 같은 사상이다
- 헤드리스·골든·밸런싱은 지금처럼 840 tick 을 한 번에 돌리면 **같은 결과**다

즉 "흐르는 낮"은 새 시뮬이 아니라 **같은 시뮬의 재생 속도 문제**다.

## 5. 제안 — 하이브리드: 낮은 흐르고, 주는 마디로 남는다

카이로를 통째로 베끼면(주 개념 제거) 결산·카드·의뢰·밸런싱 검사를 전부 다시 짜야 하고,
§2 의 "한 주만 더" 훅도 버리게 된다. 둘 다 갖는 구조가 있다:

```
[기본 상태] 공원이 산다 — 하루가 저절로 흐른다 (버스 도착 → 손님 놀이 → 해질녘 퇴장)
     │         짓기·바닥·코스는 언제든. 시트/패널이 열리면 시간은 암묵적으로 멈춘다
     │         하루 끝: 토스트 한 줄 (오늘 +32만 · 손님 41 · 첫 손님 의뢰 6/10)
     ▼
[주 경계]   7일째 밤 → 결산 (히트맵·요일 막대·숫자, 지금 그대로) → 주간 카드
     │         "한 주만 더" 훅은 여기 산다
     ▼
[빨리 감기] `한 주 ▶` 는 남는다 — 의미가 "다음 결산까지 감기"로 바뀐다
              (계산은 이미 0.6초. 바쁜 세션은 10초, 느긋한 세션은 구경)
```

핵심 규칙:

1. **하루의 길이**: 기본 배속에서 하루 ≈ 40~60초 (120 tick 을 실시간으로 풀면 12초 —
   너무 빠르다. 재생 간격을 벌린다). 2배속 제공. 카이로 준거: 1년 16일의 극압축이
   "구경이 지루하지 않은" 비결이므로, 우리도 하루를 1분 안쪽에 둔다
2. **시트·패널·카드가 열리면 시간이 멈춘다** — 카이로의 암묵 멈춤. "쉽게"의 핵심이다.
   지속적 주의를 요구하지 않으므로 v2 가 실시간을 기각한 이유가 소멸한다
3. **앱을 끄면 멈춘다. 방치 진행 없음** — 카이로와 같다. 프리미엄 유료 모델과도 맞는다
   (방치 보상은 광고 시청과 한 몸이 되기 쉽다)
4. **주간 카드는 주 경계에 그대로** — 단, 결산 **뒤에** 온다 (UX 검수 §5 의 처방과 합류)
5. **사건은 일어날 때 보여 준다** — 의뢰 진척·콤보 발동·사고 위험을 토스트/이모트로.
   "항상 무언가를 향해"가 화면에 상시 존재하게 된다 (검수 §1 의 처방과 합류)
6. **낮밤 표현은 렌더 전용** — 하루 안에서 아침/낮/저녁 톤을 살짝 준다. sim 은 모른다
   (불변식 1). 버스 시간표가 이미 하루의 리듬을 만들어 놨다

이 구조가 UX 검수의 치명 3건을 어떻게 건드리나:

- **#1 (목표가 화면에 없다)** — 규칙 5 로 의뢰 진척이 사건으로 노출된다. 상시 목표란
  교체와 병행
- **#2·#3 (시작이 실패로 읽힌다)** — 공원이 살아 있으면 첫 화면의 보상이 "숫자 0"이
  아니라 "손님이 논다"가 된다. 단 **시작 킷 재조정은 여전히 필요하다** (만족도 0 은
  시간 모델과 무관한 밸런스 문제다)
- **#5 (버튼이 질문부터 준다)** — 규칙 4 로 해소

### 무엇을 잃나 (정직하게)

- **구현 비용**: 재생 루프 상시화, 멈춤 규칙, 하루 마디 토스트, 낮밤 톤, 배속 UI.
  sim 은 거의 그대로지만 main.ts 의 주 루프 배선은 크게 바뀐다
- **"주 사이에 짓는다"의 의미 변화**: 지금은 건설이 주와 주 사이(정지 상태)에서만
  일어난다. 흐르는 낮에서는 **주 중간에 지은 시설이 그 주 결산에 섞인다** — 밸런싱
  검사(봇)는 주 경계에서만 짓게 유지해 골든을 보존한다
- 결산 화면의 "다시 보기"(압축 연출 리플레이)는 존재 이유가 약해진다 — 이미 봤으므로

## 6. 기각한 대안들

| 대안 | 기각 이유 |
|---|---|
| **현행 유지 + 연출만 늘리기** | v4 에서 이미 시도한 방향의 연장. 공원이 버튼 사이에 죽어 있다는 구조 자체는 그대로다. "쉽게" 타겟에 매 턴 의사결정 요구도 그대로 |
| **카이로 완전체 (주 제거, 계절=며칠)** | 결산·카드·의뢰·골든·밸런싱을 전부 재설계. K7~K9 를 다시 하는 비용. "한 주만 더" 훅 상실. 하이브리드가 같은 체감을 훨씬 싸게 준다 |
| **방치형 (오프라인 진행)** | 카이로도 안 한다 (세션에 묶임 — 1차 소스 확인). 프리미엄 유료 모델과 충돌. 밸런스가 "접속 빈도"라는 외생 변수에 오염된다 |

## 7. 결정 요청

1. **방향**: §5 하이브리드로 가나? (낮은 흐르고 · 주 경계에 결산+카드 · `한 주 ▶`는 빨리감기)
2. **하루 길이**: 기본 배속 40~60초 제안 — 더 길게/짧게?
3. **멈춤 범위**: 시트·패널·카드가 열리면 멈춤(제안). 아예 "보이는 동안은 항상 흐름"으로
   더 카이로답게 갈 수도 있다 (카이로는 메인 화면에선 계속 흐른다)
4. 승인되면: 스펙 문서 → 구현 계획 → K39 로 착수. **UX 검수의 A(목표란)·B(시작 킷)는
   시간 모델과 독립이라 먼저 갈 수 있다**
