## 아키텍처 결정

**Phaser 2D 로 갔다.** 카이로는 2D 스프라이트 아이소라 3D 가 필요 없고, `prototype-3d` 의
픽셀화·외곽선 후처리도 필요 없다 — 아웃라인은 스프라이트에 굽고 색은 팔레트로 미리
양자화하므로 런타임 후처리가 할 일이 없다. `prototype-3d` 는 룩 참고용으로 동결.

**카메라 줌을 버렸다.** Phaser 의 `camera.setZoom(2)` 는 worldView 를 `width·(1−1/z)/2`
만큼 미는데 폰 393px 에서 그게 **98.25px** — 없애려던 반 픽셀이 거기서 다시 들어온다.
카메라 줌은 영구히 1 이고 확대는 `ScaleManager` 로 캔버스 전체를 정수배 늘린다.

**시뮬/렌더 분리를 지켰다.** 지형·벽·시설·손님·주 루프·콤보·의뢰·위험도가 모두
`src/sim/kairo/` 에 있고 렌더는 읽기만 한다. 그래서 `npm run sim:kairo` 가 브라우저 없이
돈다 — 그게 도는 것 자체가 불변식 1 의 실증이다.

## 페이즈별로 실제로 잡은 것

### K1 — 부팅이 멈추던 함정
같은 크기로 `scale.resize()` 를 부르면 ScaleManager 가 RESIZE 를 되쏘고 그 리스너가 또
resize 를 불러 **루프가 아예 시작되지 않는다** (`loop.started=false`, `frame=0` 인데
`children=1280` 이라 create 는 끝난 상태). 크기가 실제로 바뀔 때만 부른다.

### K2 — 1px 이음새
다이아몬드를 AA `fill()` 로 그려 경계가 흐려졌다. 정수 스캔라인 마스크로 바꿨고, 그게
평면을 겹침 0·틈 0 으로 덮는 근거는 면적이다 — 격자 `(16,8)·(−16,8)` 의 기본 영역이
256 이고 마스크가 정확히 256 픽셀이다.

### K3 — 아웃라인이 스티플을 메운다
아웃라인을 먼저 굽고 스티플을 뚫으면 투과율이 **0%** 가 된다. `bakeOutline` 이 "실체에
인접한 투명 픽셀"을 칠하는데 50% 체커에서는 뚫린 픽셀 전부가 인접해 있다.
순서를 불투명 → 아웃라인 → 펀치로.

### K4 — 앵커 두 정의
`footprintAnchor` 는 (bbox 가로중심, 최하단 꼭지점 y) 다. 최하단 꼭지점의 **x** 를 쓰면
비정사각에서 어긋난다 — `pyeongsang_row 4×1` 에서 중심 8 vs 꼭지점 32, **24텍셀(1.5타일)**.
검증이 수치로 확인하므로 회귀가 잡힌다.

### K6 — 손님이 시설을 뚫고 지나갔다
K5 까지 통행 판정이 지형과 벽만 봤다. 시설이 길을 막지 않으면 배치가 동선에 영향을 주지
않아 "배치가 결과를 바꾼다"가 성립하지 않는다. 고친 직후 반대 버그가 나왔다 — 거리장
목적지에서 "점유된 칸"을 전부 뺐더니 **덱 위가 목적지가 되지 못했다**.

### K7 — 만석을 세지 않아 주말이 한가해 보였다
성공한 입장만 셌더니 주중에 정원 60이 차서 주말 입장이 전부 실패하고, 실패는 어디에도
안 남았다. `arrivals = visitors + turnedAway` 항등식을 유지하고 결산 막대에 만석을
빗금으로 얹는다.

히트맵에 **선형 정규화를 쓰면 안 된다** — 게이트 앞 한 칸이 29,477 이라 나머지가 전부
깔린다. 감마 0.32.

`hidden` 오버레이가 모든 입력을 막던 버그도 여기서 잡혔다 — 인라인 `display:flex` 가
`hidden` 속성을 이긴다.

### K9 — 만족도에 하향 압력이 없었다
50 에서 시작해 이용당 +12씩 오르기만 해서 전 판 98·전 판 5등급이었다. 걷기·대기 페널티와
이용 상승 체감을 넣어 등급 2~4 · 만족도 62~79 로 분포가 생겼다.

한 방문이 하루(120tick)를 넘어 공원이 영구 포화됐던 것도 여기서 잡았다 (useTicks 40 → 12).

손님이 거리만 보면 가까운 시설이 빨리 비는 순간 **먼 시설을 아무도 안 간다**. 안 채운
수요를 우선하게 바꿨다.

## K10 밸런스 — 후반 정체를 풀었다 (경보 2건 → 0건)

`npm run sim:kairo --seeds 24 --weeks 40` 이 경보 2건을 띄우고 있었다. 셋 다 원인이 달랐다.

### 등급이 성장의 축이 아니었다
등급이 시설과 토지만 열고 **동시 손님 상한과 수요를 안 건드렸다**. 그래서 시설을 늘려도
정원 60 에서 막혀 후반 손익이 25% 꺾였다. 등급에 `maxGuests`·`reputationPull` 을 붙였다.

**상한이 수요보다 빨리 자라야 한다** (30→150 은 5배, 수요는 1.0→2.5 로 2.5배). 같은 비율로
올리면 만석 비율이 영구히 고정되고(실측 43%) 플레이어가 만석을 해결할 방법이 사라진다.

### 입장 상한을 등급만 보고 정하면 죽음의 나선이 생긴다
등급 상한까지 받으면 슬롯보다 많이 받아 줄만 길어지고, 대기 페널티로 만족도가 붕괴하고,
등급이 떨어져 수요가 줄고 다시... (36주 실측: 만석 100% · 만족도 0 · 손익 37% 하락).
`admissionLimit = max(8, min(등급 상한, 공급×1.5))` — 늘리는 방법은 시설을 더 짓는 것뿐이다.

### 하루 입장이 tick 나머지로 잘렸다
도착을 `tick % 간격` 으로 뽑아 간격이 1 tick 에서 바닥을 쳐 **하루 120명이 하드 상한**이었다.
누적기(accumulator)로 바꿔 소수 도착률이 그대로 반영된다.

### ⚠ 경보가 계절을 무시해 가짜 하락을 잡고 있었다
"정점 57만 → 마지막 36만, 37% 하락" 은 **버그가 아니라 겨울**이었다. 봇의 계절 순환에서
마지막 4주가 겨울이라 무조건 하락으로 잡혔다. 이제 **같은 계절끼리** 전반/후반 평균을
비교한다. 이걸 고치니 남은 경보는 하나였고, 그게 진짜였다.

### 건설비가 싸서 돈이 병목이 아니었다
가장 싼 시설 26,400원 · 시작 현금 500만 → **시설 189개를 즉시 살 수 있었다**. 4배로 올려
(최저 105,600원 → 47개) 파산이 1/24 판 나온다. 돈이 판단이 됐다.

시설 상한은 자리 문제가 아니었다 — 건설이 막힌 주가 판당 3회뿐이다 (계측 추가).

**결과** (시드 24 × 40주): 시설 105~120 · 등급 4 · 만족도 76~82 · 만석 14% ·
파산 1/24 · 계절별 손익 여름 42만 · 가을 45만 · 겨울 26만 · 봄 44만 · **경보 0건**

## K11 4방 이음새 QA — 에셋 생산 전 게이트 (`npm run seam`)

적대적 리뷰 CONFIRMED 항목이었다. 지금 플레이스홀더는 정수 스캔라인 마스크라 틈·겹침이
수학적으로 0 이지만 **AI 픽셀아트로 갈면 그 보장이 사라진다.** 40~50장을 다 뽑은 뒤에
"눈으로 보니 격자가 보인다"가 되면 전부 다시 뽑아야 한다.

`verify:kairo` 에 묶었고 `--selftest` 를 항상 켠다. 프로바이더 인터페이스만 쓰므로
`AtlasProvider` 로 바뀌어도 그대로 돈다.

### 지표를 네 번 고쳤다 — 전부 대조군이 잡았다

**① 다리를 4방 타일로 재고 있었다.** `bridge_x/z` 는 32×28 — 물 위로 들린 **방향 런**이다.
격자 검사에서 빼고 런 검사로 보냈다.

**② 인접 열의 최상단 y 비교는 틀렸다.** 다리 난간 기둥 때문에 정상 에셋이 8px 로 실패했다.
런의 진짜 질문은 **주기성**이다 — 한 칸 옆이 정확히 (Δx, Δy) 만큼 밀린 같은 모양인가.
이 지표는 내부 디테일에 무관하다.

**③ 그런데 주기 검사가 정상 벽까지 잡았다 — 지표가 아니라 내 캔버스가 스프라이트를
잘라내고 있었다.** 벽은 40px 인데 타일 기준 오프셋은 위로 24px, i-런 첫 칸은 왼쪽으로
14px 넘었다. 잘린 걸 모르고 재서 정상 에셋이 주기 오차 8px 로 나왔다. 이음새는 **상대**
기하만의 문제이므로 첫 칸을 (2,2) 에 놓고 상대로만 깐다. 넘침은 이제 에러다.

**④ 이음새 대비 하나로는 격자 밴딩을 못 잡는다.** 가장자리 링을 65% 어둡게 하니 대비가
**0.18 로 내려갔다** — 경계 양쪽이 둘 다 어두워지기 때문이다. 랩 블렌드가 잔디에 16px
밴딩을 만들던 그 사고가 정확히 이 모양이다. **경계 밝기 편향**(경계 밴드 평균 − 내부 평균,
σ 정규화)을 따로 잰다. 문턱 1.2σ 의 근거는 실측 — 플레이스홀더 20종이 최소 0.023 ·
중앙 0.222 · 최대 0.778 (최대는 `path_stone`, 포장 이음선을 일부러 경계에 그린다).

### 음성 대조군 — 주입한 위반 6건이 전부 잡힌다

지표를 `window.__seam` 라이브러리로 빼서 **대조군이 실측과 같은 코드를 탄다.** 대조군을
따로 구현하면 그 구현이 맞는지 재는 셈이 된다.

| 주입 | 지표 | 값 |
|---|---|---|
| 타일 내부 1px 삭제 | 틈 | 25 |
| 마스크 행 1px 확대 | 겹침 | 640 |
| 가장자리 링 65% 어둡게 | 경계 편향 | 2.162σ |
| 3번째 칸만 4px 내림 | 주기 최상단 오차 | 4px |
| 같은 조작 | 주기 커버리지 불일치 | 31열 |
| 가운데 20열 삭제 | 실루엣 구멍 | 12열 |

⚠ 마지막 것은 처음에 **8열**을 지웠는데 빈 열이 0 이었다 — 벽 스프라이트가 32px 인데
런 간격이 16px 이라 이웃이 그대로 메운다. **구멍은 간격보다 넓어야 위반이다.**
주입이 위반이 아니었던 것이지 지표가 틀린 게 아니었다.

## K12 세이브·건설비 — 기본 씬으로 올리기 전에 필요했던 것

기본 씬을 바꾸려다 두 가지가 걸렸다. **순서가 중요했다** — 이걸 안 고치고 기본으로
올리면 폰에서 새로고침마다 판이 날아가고, 지어도 돈이 안 나간다.

### 세이브가 없었다
`src/save/kairo.ts` 를 v1 세이브와 **완전히 분리**해 만들었다. 담을 것이 겹치지 않아
(격자·주 단위 vs 자유 배치·실시간) 한 포맷에 유니온으로 섞으면 마이그레이션 체인이
두 갈래로 갈라진다. 키도 다르므로 서로를 덮어쓰지 않는다.

손님은 저장하지 않는다 — 한 주 안에서만 사는 개체다. **히트맵·재생 프레임도 저장하지
않는다** (타일 1,280칸 + tick 단위 프레임이라 localStorage 를 넘긴다). 대신 `WeekSummary`
4필드만 남긴다 — 의뢰 판정과 등급이 읽는 것이 정확히 그 넷이라 복원 후에도 그대로 돈다.
`questStatuses` 가 `WeekReport` 대신 `WeekSummary` 를 받게 바꿨다.

### UI 가 시설을 공짜로 지었다
`KairoFacilityDef` 에 `cost`·`upkeep`·`fee` 가 **없었다** — `week.ts` 는 인라인 캐스트로
upkeep 만 읽었고, 그래서 헤드리스 봇만 돈을 쓰고 플레이어는 공짜로 지었다. K10 에서
건설비를 4배로 올린 것이 실제 플레이에는 없던 셈이다. 타입에 넣고 캐스트를 없앴다.

건설비는 **놓기 전에** 확인한다 — 놓고 나서 차감하면 잔액 부족 시 되돌려야 하고 그
되돌리기가 점유 격자·거리장까지 건드린다. 철거는 50% 환급 (전액이면 시행착오가 공짜라
배치가 판단이 아니게 되고, 0원이면 오조작 한 번이 판을 망친다).

### ⚠ 프레임이 초기화 전 상태를 읽어 루프가 죽었다
세이브를 붙인 뒤 새로고침하면 **화면은 그려진 채 멈췄다.** `started:true, frame:0,
children:1282` — K1 과 같은 서명인데 원인이 달랐다. `bootKairo` 뒤에 `await import` 가
하나 남아 있어, 그 지점에서 양보한 사이 첫 프레임이 `onFrame` 을 호출하고 아직 초기화
안 된 `const week` 를 건드려 TDZ ReferenceError 가 났다. 그 예외가 루프를 죽인다.

세이브가 원인이 아니라 **타이밍을 바꿔 잠재 경합을 드러냈을 뿐**이다. await 를 boot 앞으로
모으고, 그것만으로는 재발을 못 막으므로 프레임이 읽는 상태를 **널 가능 참조**로 바꿨다.

### ⚠ 탭이 반 타일 밀려 있었다
배치 검사를 쓰다가 나왔다. `screenToTile(world.x, world.y − TILE_H/2)` 가 탭 지점을
**격자 꼭지점**(네 타일이 만나는 점)으로 옮겨서, 반올림 하나로 타일이 뒤집혔다
(실측: (10,10) 중심을 탭했는데 (9,10)). 지면 칠하기로는 이웃 칸이 칠해져도 티가 안 나서
오래 안 잡혔지만 2×2 시설은 곧바로 "다른 시설이 있습니다"로 거절된다. 보정을 없애고
5칸 회귀 검사를 넣었다 (5/5).

⚠ 검사를 쓰다 두 번 더 걸렸다: **탭 간격을 700ms 이상** 둬야 한다 (300ms 안에 두 번이면
더블탭 확대가 발동해 배율이 바뀌고 좌표 환산이 전부 어긋난다). 그리고 후보 타일마다
`focusTile` 로 카메라를 맞추고 **탭 지점이 캔버스 위인지** 확인해야 한다 — 안 하면 토스트·
붓 바 같은 DIV 가 탭을 먹고 "배치가 안 된다"로 나온다.

⚠ 새로고침 비교는 **세이브에 담긴 수**와 해야 한다. 하네스가 앞 단계에서 시뮬을 직접
불러 놓은 시설은 저장을 안 타므로, 화면상의 수와 비교하면 정상 동작이 실패로 나온다
(실측 28 vs 21).

## K13 기본 씬 전환 — 카이로가 기본이다

`?kairo=1` 이 아니라 그냥 열면 카이로다. v1 은 `?v1=1` 로만 열린다.

`verify:mobile` 은 v1 을 검사하는 하네스이므로 URL 에 `?v1=1` 을 명시했다. **카이로용으로
다시 쓰지 않았다** — `verify:kairo` 가 이미 같은 아이폰 프로파일·터치·CDP 멀티터치 핀치로
86종을 본다. 두 벌을 유지하면 어느 쪽이 진짜 게이트인지 흐려진다.

v1 은 폐기됐지만 지우지 않았다 — 지우는 것은 별도 결정이다.

## K14 주간 의사결정 카드 24종 — 루프를 지탱하는 장치

적대적 검증에서 나온 최대 결함이 "시설을 20개쯤 지으면 할 게 없어지고 `한 주 진행` 이
**스킵 버튼**으로 전락한다"였다 (§3.5). 카드는 매주 선택을 강제한다.

`src/data/kairo-cards.json` 에 24종, 해석은 `src/sim/kairo/cards.ts`. **효과 어휘를 8개로
묶었다** — 카드마다 새 효과를 만들면 24종이 24개의 특수 규칙이 되고, 카드를 추가할 때
시뮬을 고쳐야 한다. 그게 불변식 3 이 막으려던 상태다. 카드 추가 = JSON 항목.

`한 주 진행` → **카드 먼저** → 계산 → 압축 연출 → 결산. 결산 뒤에 띄우면 이미 끝난 주에
대한 선택이 되어 의미가 없다.

### ⚠ 한 선택지가 서로 다른 기간의 효과를 못 담았다 — 4주 폐쇄
방송 촬영 카드에 `closed` 와 `reputationDelta` 를 **한 객체**에 넣고 `weeks: 4` 를 걸었더니
**4주 연속 폐쇄**가 됐다. 후반 수익 중앙값이 **0** 이 되고 16판 중 4판이 파산했다.

처음엔 "유지비가 무겁다"로 보였는데 유지비는 20만이었고 **수익이 사라진 것**이었다 —
수익·유지비·건설비·현금 곡선을 따로 찍고 나서야 보였다. 선택지가 **효과 목록**을 갖도록
바꿔 폐쇄는 1주, 평판은 4주로 각각 살게 했고, `validateCards` 가 **여러 주 폐쇄를 금지**한다.

### ⚠ 봇 정책이 분기를 안 태워 계측이 없는 것과 같았다
"낼 수 있으면 지출 쪽"으로 썼더니 루프가 항상 **마지막 무지출 선택지**로 끝나 혼잡(단체
예약)·폐쇄(방송 촬영)를 한 번도 안 탔다. **카드를 넣기 전과 숫자가 완전히 같아서** 알아챘다.
낼 수 있는 선택지 중 균등 무작위로 바꿨다.

### ⚠ 계절 성장 판정이 시간순이 아니었다
계절별 배열이 **판 순서**라 전반/후반이 "시드 0~7 vs 8~15" 를 비교하고 있었다. 주차로 묶어
고쳤다. 그리고 **경보는 성수기만** 본다 — 비수기는 수요가 상한이라 수익이 고정이고 시설을
늘리면 유지비만 는다. 그건 결함이 아니라 "비수기에는 사우나·숙박·식음을 지어라"는 판단을
요구하는 설계다. 구분하지 않으면 **내 문턱을 만족시키려고 게임을 주무르게 된다.**

### 카드가 실제로 무는지 확인하며 고친 것 셋
- **`crowdMult`·`accidentMult` 가 아무 데도 안 쓰였다** — 단체 예약의 "혼잡 +35%" 가 무효였다.
  `admissionLimit`·`accidentChance` 에 배율 인자를 넣었다. 단, **안전 단계에서는 사고 배율이
  0 이다** — 카드로 위험을 만들면 v4 에서 없앤 "RNG 세금"이 된다.
- **누적 상한** (`MOD_CAPS`) — 음수 만족도 카드가 겹치면 K10 에서 없앤 죽음의 나선이
  되살아난다. 어떤 한 시스템도 게임을 나선으로 밀 수 없어야 한다.
- **비수기 유지비** (`OFFSEASON_UPKEEP`·`ACTIVE_NEEDS`) — 겨울에 안 도는 시설은 세워둔다.
  없으면 "지을수록 겨울이 나빠진다"가 되어 후반에 확장할 이유가 사라진다.

### 봇에 예비비를 줬다
예비비 없이 매주 3채를 지어 건설 70만 + 카드 19만 vs 손익 40만으로 초기 자금을 다 쓰고
16판 중 4판이 파산했다. **계측 도구가 스스로 파산하면 게임이 아니라 봇의 무모함을 재게 된다.**
150만(카드 한 장의 최대 지출)을 남긴다 → 파산 1/16.

**결과** (시드 16 × 40주): 파산 1/16 · 카드 0.90장/주 · 카드 지출 중앙 765만 ·
계절별 손익 여름 45만 · 가을 48만 · 겨울 30만 · 봄 44만 · **경보 0건**

## K15 손님 그룹 유형 4종 — 시설 구성이 손님 구성을 통해 매출로

스펙 §10.4. 가족·커플·친구·회사 단체. `src/data/kairo-groups.json` + `src/sim/kairo/groups.ts`.

**손님은 일행 단위로 들어온다.** 한 명씩 넣으면 "단체 예약 40인" 같은 카드·의뢰가 숫자로만
존재하고 화면에서 무리가 안 보인다. 단, 일행 전체를 한 번에 넣으면 도착률 계산이 무너지므로
(주간 도착 수는 누적기가 정한다) **한 명씩 연속으로** 넣는다 — 같은 일행이 몇 tick 안에
줄줄이 들어온다.

유형이 바꾸는 것 셋: **지갑**(객단가) · **인내**(커플·단체는 짧다) ·
**수요 편향**(`needBias` 를 거리에 곱한다 — 1.0 미만이면 "멀어도 간다"). 그래서 가족은
놀이·위생을 찾아가고 친구는 스릴을 찾아간다. 결산에 **유형 구성 막대**를 넣었다 —
"누가 왔나"가 "무엇을 지을까"의 근거다.

### ⚠ 요금 계수가 틀려 있었다 (매출 2.15배)
`usingBefore − usingNow` 로 "이용을 끝낸 수"를 셌는데 **같은 tick 에 시작과 종료가 겹치면
놓친다.** 손님 쪽이 완료를 직접 세고 지갑 배율 합을 주도록 바꾸니 매출이 약 2.15배가 됐다 —
즉 그동안 계통적으로 적게 받고 있었다. 밸런스 지점을 유지하려고 요금 데이터를 ×0.465 했다.

### ⚠ 객단가 검사가 혼잡에 오염됐다
"여름 vs 겨울 손님 1명당 매출"로 지갑 효과를 재려 했더니 **겨울이 1.8배**로 나왔다 —
겨울은 안 붐벼서 손님이 이용을 다 끝내고 가고, 여름은 줄을 서다 못 채우고 나가기 때문이다.
지갑 효과가 반대로 보였다. 요금 경로를 **직접** 재도록 바꿨다 (완료 손님의 지갑 합 / 인원).

### ⚠ 검증이 약하게 통과할 뻔했다 (두 번)
- 결산 구성 검사가 **"입장 0명" 분기로 통과**했다 — 하네스가 앞서 주를 여러 번 돌려 공원이
  상한까지 찬 상태였고, 막대는 정상적으로 "손님 없음"을 띄웠다. 밖에서 상한을 올려도
  `runWeek()` 이 등급 기준으로 다시 정해 덮는다. 검사가 **자기 결산을 직접 만들도록** 바꾸고,
  판정을 **유형 합 = 입장 수**라는 진짜 불변식으로 세웠다.
- 하네스가 카드 0번을 무조건 골라 **방송 촬영의 "수락(폐쇄)"** 을 집었고, 그 주 손님이 0명이
  됐다. `currentCard` 를 열어 폐쇄가 없는 선택지를 고르게 했다.

`div[title]` 로 요일 막대를 세던 검사가 구성 막대까지 세는 것도 여기서 드러났다 —
`data-day`·`data-group` 표시로 바꿨다.

**결과** (시드 16 × 40주): 계절별 손익 여름 40만 · 가을 42만 · 겨울 22만 · 봄 42만 ·
파산 1/16 · **경보 0건**

## K16 직원 5직종 — 여섯 동사 중 "사람을 쓴다"

스펙 §11. 안전요원·운영요원·청소부·정비공·매점직원. **인건비는 고정비**라 손님이 없어도
나간다 — 그게 "겨울에 몇 명을 남길까"를 판단으로 만든다.

부족은 **비율**로 나타난다. 절벽을 두면 "한 명 부족해서 판이 끝났다"가 되고, 그건 v4 에서
없애기로 한 종류의 실패다:
안전요원↓ 사고 위험 · 운영요원↓ 수상 시설이 **선다** · 청소부↓ 만족도 · 정비공↓ **고장** ·
매점직원↓ 식음 매출 (전체가 아니라 **식음 몫만** — 그래야 종류별 판단이 된다).

**배치는 의도적으로 뺐다.** 스펙은 "반경 8타일"을 말하지만 직원 스프라이트·배치 브러시가
필요하고 에셋은 이 골 밖이다. 경제적 결정("몇 명을 쓸 것인가")이 이 동사의 핵심이고, 공간
배치는 그 위의 층이다 — `coverage()` 가 비율을 주므로 나중에 타일 거리로 바꿔 얹으면 된다.

### 주급을 두 번 조정했다
문서 값(안전요원 40만/주)은 우리 경제에서 **한 명이 한 주 이익을 통째로 먹는다**. 처음에
시설 60개 완전 배치 기준 23만/주(수익의 33%)로 잡았더니 후반에 **건설이 아예 멈추고
인건비도 못 냈다** (마지막 8주 건설비 0). 유지비와 비슷한 15% 안팎(약 11만/주)으로 낮췄다.

### ⚠ 봇이 "돈이 없어서"를 "자리가 없어서"로 보고했다
`buildOne` 이 0 을 돌려주는 이유가 둘인데 한 통으로 세고 있었다. 경보가 "토지 해금을
보라"고 엉뚱한 곳을 가리켰다 — 실제로는 인건비로 돈이 마른 상태였다. **가장 싼 시설도 못
살 예산이면 돈 문제**로 나눠 센다. 나눠 보니 돈 부족 12회 vs 자리 부족 1회였다.

### ⚠ 봇 건설 예산을 고치다 성장 교착을 만들었다
"수입의 1.5배까지만 짓는다"로 바꿨더니 초기 자금을 안 써서 시설이 12개에 머물고, 슬롯이
모자라 손님이 전부 헛걸음하고(헛걸음 106%), 만족도 0 · 등급 1 · 수입 0 이 되어 예산이
영원히 최저에 머물렀다 — **작아서 못 크는 상태.** 은행에 돈이 있으면 사람은 짓는다:
`max(최저가, 수입×1.5, 여유현금×1/4)`.

### 비수기 감원이 실제로 보상된다
봇이 계절과 무관하게 인원을 유지하면 비수기 손익이 −50% 였다. 여름 1.0 · 봄가을 0.75 ·
겨울 0.5 로 줄이자 −19% 로 좁혀졌다 (직원 17.3 → 11.8명/주). §11 이 요구한 판단이
기계적으로 보상된다는 증거다 — 봇이 그 판단을 안 하면 "기계가 나쁘다"로 잘못 읽게 된다.

**결과** (시드 16 × 40주): 시설 76~115 · 등급 2~4 · 만족도 62~80 · 파산 2/16 ·
계절별 손익 여름 22만 · 가을 26만 · 겨울 12만 · 봄 29만 · **경보 0건**

## K17 수상 코스 — 여섯 동사 중 "코스를 그린다"

스펙 §7. 프리셋 6종 + 터닝포인트 핸들, 장비 19종(견인 15 + 동력 4), **적합도 19×6**.
**프리셋 탭 1 + 핸들 드래그 2~4 + 확정 1 ≈ 5회** (조각 조합 방식은 10~15회였다).

**스플라인·곡률 수학은 v1 것을 그대로 쓴다.** `src/sim/spline.ts` 와 `computeMetrics` 는
스펙 §7.6 공식 그대로 구현·검증돼 있다. 폐기된 것은 **조작 방식**이지 수학이 아니다 —
다시 짜면 검증된 것을 버리고 같은 버그를 다시 만든다.

적합도는 **스릴과 만족만** 건드린다. 처리량·안전까지 깎으면 "부적합"이 전면 하향이 되어
고를 이유가 사라진다 — 처리량이라는 다른 축이 남아야 "부적합이지만 대수로 민다"가 가능하다.
UI 는 표가 아니라 **프리셋 탭의 배지**(◎○△✕)로 보여준다 (§B).

### ⚠ 코스 하나가 공원 전체 매출을 넘었다 — 시계 단위
`computeMetrics` 의 처리량은 v1 시계(하루 3,600 tick · 영업 10시간 → 시간당 360 tick)
기준 "명/h" 다. **카이로의 하루는 120 tick** 이라 그대로 쓰면 30배가 부푼다 — 실측으로
코스 하나가 주매출 59만(공원 전체 ~50만)을 냈다. 속도(타일/tick)는 두 시계에서 같은
축이므로 주기는 그대로 두고 **주간 tick 수만** 카이로 것으로 바꿨다.

### ⚠ 스릴이 전부 100 에 붙어 지표가 구분을 못 했다
장비 기본 스릴을 프리셋 기본에 **더했다.** 스펙 §7.6 은 장비의 몫을 **속도계수와
스릴계수**로 넣는다 — 기본값을 또 더하면 세 번 세는 것이다. 6×3 조합 중 10칸이 100 이었다.
프리셋 기본만 쓰도록 고쳐 18~100 으로 벌어졌다.

### ⚠ 직선 코스는 경계 상자가 선이라 "수면이 좁다"가 나왔다
필요 수면을 코스 경계 상자 안의 물 타일로 셌더니, 왕복처럼 직선인 코스는 넓은 호수
한가운데서도 막혔다 (봇이 코스를 **한 개도** 못 놓았다). 필요 수면이 묻는 것은 "이 형태를
돌릴 만한 물이 **주변에** 있나"다 — 상자에 3타일 여유를 둔다.

### ⚠ 코스가 항상 정답이 됐다
장비값을 다른 데이터와 같은 축척(×0.03)으로 낮췄더니 회수가 **3주** — 시설(7~10주)의
2~3배였다. 코스가 항상 정답이면 "무엇을 지을까"가 사라진다. ×0.08 로 올려 회수를 맞췄다.

### ⚠ 겨울에도 배가 돌았다
코스 매출이 계절을 안 타서 비수기 손익을 통째로 떠받쳤다 (겨울 −17% → +2% 로 평평해짐).
매출은 계절을 타고 **유지비는 안 탄다** — 장비는 세워둬도 돈이 든다.

**결과** (시드 16 × 40주): 코스 4개 · 코스매출 10~33만/주 (계절) · 현금 295~534만 ·
**경보 0건**

## K18 배경 2겹 · 도감 · 감상 화면 — 스펙에 남아 있던 화면들

### 배경 2겹 (§7 배경)
능선(시차 0.15)과 먼 강둑(0.35). **시차가 핵심이다** — 지도와 같은 속도로 움직이면 큰 그림
한 장이고, 안 움직이면 벽지다. 그래서 검사도 "떠 있나"가 아니라 **"카메라보다 느리게
따라오나"**를 잰다.

가로 이음새는 **스프라이트가 좌우로 이어지도록 그려서** 없앤다 (주기가 폭의 약수인 사인 합).
랩 크로스페이드로 덧칠하면 그 부분만 색이 달라져 오히려 이음새가 보인다.
하늘과 물은 안 그린다 (계약의 `sky:false`·`water:false`) — 색이 두 곳에서 정해지면 어긋난다.

⚠ **게터가 조용히 안 붙었다.** 파이썬 치환의 앵커 문자열이 실제 주석(`테스트·도구용`)과
달라 `backdropInfo` 가 추가되지 않았는데, **타입체크는 통과했다** (없는 것을 안 부르니까).
브라우저 검사가 `undefined` 로 잡았다. 코드를 문자열 치환으로 넣을 때의 실패 모드다.

### 도감 (§15.8 · §D)
콤보 70 + 시설 73 + 장비 19 = **162 항목**. 스크롤 지옥을 피하는 장치 셋:
**티어 탭** · **기본은 미발견만**(할 일이 보여야 목표가 된다) · **한 항목 56px**.

미발견은 **힌트만** 준다 (`매점 + ? + ?`) — 전부 보여주면 발견이 아니라 체크리스트가 되고,
전부 가리면 힌트가 아니라 벽이 된다.

발견은 **누적**한다. 지금 발동 중인 것만 보여주면 시설을 지웠을 때 도감이 줄고, 그건
발견이 아니라 현황판이다. 그래서 세이브에도 들어간다.

### 감상 화면 (§15 v4 신규)
"10시간 뒤의 리조트가 **스크린샷 찍고 싶은 화면**이어야 한다." UI 를 걷어내고 최대 축소로
전체를 보여준다. **씬은 멈추지 않는다** — 손님이 움직여야 "살아 있다"가 된다.

이름을 탭하면 바꾼다 (내 리조트라는 감각의 절반은 이름이다). 공유는 **지금 보이는 캔버스**를
그대로 복사해 이름·등급·방문객을 얹는다 — 따로 렌더하면 화면과 다른 그림이 나온다.

⚠ **저장(다운로드)은 하지 않는다.** 뷰어 환경에 따라 조용히 막히고, 막힌 걸 모른 채
"저장했다"고 말하게 된다. 새 탭으로 띄워 사용자가 저장하게 한다. 그리고 결과 이미지가
**검은지 검사해서** 비어 있으면 실패로 돌려준다 — WebGL 버퍼가 보존 안 되면 검은 그림이
나오고, 그건 이 프로젝트에서 `readPixels` 로 이미 겪은 함정이다.

## K20 PWA 포장 — 홈 화면 앱 + 오프라인

Phase G 의 절반(포장). **에셋 생산이 아니라 "폰에서 돌아가는 것"의 마무리다.**

아이콘은 **코드로 굽는다** (`npm run icons`). 에셋 생산은 골 밖이지만, 아이콘이 없으면
홈 화면에 **회색 사각형**이 뜨고 그건 "폰에서 돌아간다"가 절반만 참인 상태다. Node 에는
캔버스가 없어 이미 있는 Playwright 로 그려 PNG 로 받는다 — **의존성을 안 늘린다.**

서비스 워커는 **직접 썼다** (Workbox 미사용). 필요한 규칙이 셋뿐이고 60줄은 읽어서
검증할 수 있다: 해시 자산은 캐시 우선 · HTML 은 네트워크 우선(안 그러면 새 빌드가 영원히
안 보인다) · 나머지는 stale-while-revalidate. **개발 서버에서는 등록하지 않는다** —
낡은 번들이 캐시에 남는 함정을 스스로 만들지 않는다.

### ⚠ 첫 방문에는 아무것도 캐시되지 않는다
`fetch` 핸들러로만 캐시하면 **첫 방문에 워커가 페이지를 제어하지 않아** 요청이 워커를
안 거친다. 한 번 보고 닫았다가 오프라인으로 돌아오면 흰 화면이다 (검증에서 실패했다).
빌드가 `dist/precache.json` 을 만들고 워커가 **설치 시점에 미리 담는다** — 파일 이름에
해시가 붙어 목록은 빌드 뒤에야 알 수 있다.

### ⚠ 캐시에 있는데 `net::ERR_FAILED` — `Vary` 함정
미리 담은 뒤에도 오프라인 부팅이 실패했다. 진단해보니 **문자열로는 캐시가 맞는데
Request 로는 안 맞았다** — `cache.add` 때와 모듈 스크립트 요청의 `Accept-Encoding` 이
달라 서버의 `Vary: Accept-Encoding` 에 걸린 것이다. 모든 조회에 **`ignoreVary: true`**.

"캐시에 35개 담겼다"는 통과했는데 오프라인은 실패했다 — **담긴 것과 꺼내지는 것은 다르다.**
그래서 검증의 마지막 항목이 "네트워크를 끊고 새로고침해서 게임이 실제로 뜨는가"다.

**결과**: `npm run verify:pwa` 8/8 — 매니페스트·아이콘 4장·워커 활성·캐시 35개·
페이지 제어·**오프라인 부팅 FPS 60**

## K21 사고 (§12.1) — 계산만 되고 아무 데도 안 쓰이던 코드

### ⚠ `accidentChance` 가 죽은 코드였다
K9 에서 위험도 4단계와 사고 확률을 만들었는데, **어디서도 호출하지 않았다.** 위험도 게이지는
화면에 떠 있고 "안전 시설 N개 더"라고 말하는데 **사고는 한 번도 안 났다.** 게이지가
장식이었던 셈이다 — 검증도 위험도 *계산*만 봤지 결과를 안 봤다.

### 사고는 선택으로 끝난다
스펙 §12.1: "순수 처벌은 기억에 안 남는다." 사고가 나면 시설이 1~3주 닫히고 **대응 카드**가
뜬다 — 즉시 보상 합의(돈) / 법적 대응(평판) / 전면 안전 점검(돈+휴업, 이후 사고율 −50%).
어느 쪽도 편하지 않다.

카드 체계를 그대로 쓴다. 다만 `trigger: 'accident'` 를 붙여 **무작위 뽑기에서 뺀다** —
사고가 안 났는데 사고 대응을 고르는 화면이 뜨면 안 된다.

금액은 문서(1,200만/2,000만/1,800만)를 우리 경제로 축소했다. 주간 손익 20~50만에 그대로
두면 **사고 한 번이 곧 파산**이고, 그건 v4 가 없애기로 한 "억울한 실패"다.

### 결산 **전에** 띄운다
결산 뒤에 띄우면 이미 숫자를 본 뒤라 "내 선택으로 끝난다"는 감각이 안 생긴다.

### "사고 0회"가 왜 0인지 보이게 했다
봇이 안전요원을 채우니 80주에 사고가 0회다. 그 숫자만 보면 사고 체계가 도는지 알 수 없어,
**위험 단계 분포**를 함께 찍는다: 사고 가능 주 2회/80주 · 마지막 단계 watch 15판 · safe 8판 ·
danger 1판. 0 은 확률이 없어서가 아니라 **관리했기 때문**이라는 게 숫자로 보인다.

**결과**: 578 테스트 · 126/126 · 사고 0회(관리 덕) · 경보 0건

```
북한강형        48만    62    50     26     32
계곡형         62만    76    54     52     18
호수형         52만    72    50     52     11
```

가족 26% vs 52%, 친구 32% vs 11% — 구성이 확실히 갈린다. **북한강형이 손익 48만으로 낮은
것은 봇이 맵에 맞춰 안 짓기 때문**이고, 그게 오히려 "맵마다 다른 빌드가 필요하다"는 증거다
(봇은 친구 비중이 높은 맵에서도 같은 순서로 짓는다).

### 판정에서 조심한 것
- **승리가 먼저다.** 마감 주와 목표 달성이 같은 주에 성립하면 승리 — 패배를 먼저 보면
  "이겼는데 졌다"가 된다.
- **비중은 다시 정규화한다.** 배율만 곱하면 맵마다 손님 총량이 달라져 맵 특성이 아니라
  난이도 조절이 된다.
- **세이브가 URL 을 이긴다.** `?map=` 은 새 판을 시작할 때만 쓰인다 — 진행 중인 판의 맵을
  URL 로 바꿀 수 있으면 손님 구성이 통째로 뒤집힌다.

### ⚠ 템플릿 리터럴 안의 백슬래시 함정 (세 번째 계열)
`page.evaluate` 에 넘기는 문자열 안에서 `/\n/g` 를 썼더니 TS 가 **실제 줄바꿈으로 바꿔**
페이지 쪽 정규식이 `SyntaxError` 로 깨졌다. 백틱(§K11)·`__name`(§K0)에 이어 세 번째다.
줄바꿈이 필요하면 `String.fromCharCode(10)`.

그리고 **고치는 과정에서 같은 함정을 한 번 더 밟았다** — 파이썬 치환 문자열에 `\n` 을
그냥 써서 실제 줄바꿈으로 해석돼 매칭이 안 됐다. raw 문자열로 고쳤다.

**결과**: 595 테스트 · 131/131 · 80주 경보 0건

## K23 312주로 늘려 찾은 것 — 죽은 코드 두 건과 진동

시나리오가 최대 **312주(6년)** 를 약속하는데 80주까지만 밸런싱했다는 걸 알아채고 돌렸다.

### ⚠ 평판이 지난주 값 하나였다 — 등급이 진동했다
40주를 찍어보니 **만족도 53↔75, 등급 2↔3 을 왕복**했다. 등급↑ → 수요↑ → 혼잡 →
만족도↓ → 등급↓ → 수요↓ → 만족도↑ → … 음성 피드백이 문턱에서 진동한다. **문턱을 못
넘어서가 아니라 문턱에서 진동해서** 못 올라갔다.

스펙 §9.2 는 처음부터 **"평판 = 이동평균(퇴장 만족도)"** 이라고 적어뒀다. 나는 지난주 값
하나를 썼다. 이동평균(α=0.25)으로 고쳤다.

그것만으로는 부족했다 — 문턱이 10점 간격인데 이동평균이 문턱 근처에서 ±3 흔들려
**40주에 35번** 바뀌었다. **이력(hysteresis)** 을 넣었다: 오를 때는 문턱에서, 내릴 때는
4점 더 떨어져야. 이력의 목적은 소음을 죽이는 것이고 사건을 지우는 게 아니다 —
재난급 한 주(−38)는 여전히 등급을 떨어뜨린다.

### ⚠ 요금을 "전체 시설 평균"으로 받고 있었다
사고 검사가 **닫힌 시설이 여전히 요금 평균에 들어간다**는 걸 잡았다 — 싼 시설이 닫히면
평균이 올라 매출이 **늘어났다** (43.9만 → 46.7만). 손님이 **실제로 이용한 시설**의 요금을
담아 오도록 고쳤다 (개선 단계·지갑 반영, 날씨는 종류별로 보정).

### ⚠ 그 과정에서 더 오래된 죽은 코드가 나왔다
`releaseSlot` 이 `usingHandle` 을 0 으로 지운 **뒤에** 그 값을 읽고 있었다. 그래서 K9 에서
넣은 **"채운 수요를 기록해 다음엔 다른 종류로 간다"가 한 번도 동작하지 않았다** —
손님이 같은 종류를 반복 이용하고 있었다. `accidentChance`(K21)에 이어 두 번째 죽은 코드다.

살리니 만족도가 10 내려갔다 — **맞는 방향이다.** 손님이 다른 종류를 찾아 더 멀리 걸으니
"펼쳐 놓으면 나빠진다"가 이제야 작동한다. 대신 **걷기 페널티를 0.35 → 0.22 로** 낮췄다:
이동 거리가 두 배가 된 만큼 총량도 두 배가 되어 80주 등급이 4→2 로 주저앉았기 때문이다.
의도는 "가깝게 놓는 것이 의미를 갖는다"이지 "펼치면 등급이 안 오른다"가 아니다.

### 시도했다가 되돌린 것
- **등급 상한을 스펙 비율(11.7배)로 넓히기** → 죽음의 나선이 되살아났다 (만족도 0 ·
  파산 3/12). 상한이 공급보다 빨리 자라면 줄만 길어진다 — K10 에서 고친 그 실패다. 되돌림.
- **값을 0.7 로 크게 내려 만족도 사기** → 매출이 무너져 인건비를 못 내고 청소부 부족으로
  만족도가 오히려 떨어졌다. 0.9 로만.

### 개선 단계를 3 → 5 로
후반이 비는 것(312주 중 281주 "지을 게 없다" · 현금 1.5억)을 개선이 흡수하게 했다.
현금 적체가 1.5억 → 2,285만으로 줄고 5등급이 닿았다.

### 미결이었던 양극화를 K24 에서 풀었다 (아래 참고)

### ⚠ (K23 시점의 기록) 312주에서 양극화한다
**80주는 건강하다** (시드 24: 등급 3 · 만족도 73 · 만석 30% · 파산 1/24 · 경보 0건).
**312주는 갈린다**: 절반은 5등급(만족 90~98), 절반은 1등급(41)으로 붕괴하고 만석 100%,
경보 2건이 돌아온다.

이번 단계에서 이미 다섯 번 튜닝했고 매번 더 깊은 상호작용이 나왔다. 지금 상태를 숨기지
않고 적어두는 편이 낫다 — 다음 사람이 이어서 볼 지점은 **"만석 100% 인데 만족도가 갈리는
이유"** 다 (인건비를 못 내는 판과 내는 판이 갈리는 것으로 보인다).

## K24 갇힌 손님 — 판이 얼어붙던 이유

K23 에서 "312주에서 양극화한다"를 미결로 적어두고, 다음 볼 지점을 **"만석 100% 인데
만족도가 갈리는 이유"**라고 남겼다. 그걸 따라갔다.

### 중앙값만 보면 양극화를 못 본다
먼저 `--each` 를 만들어 **판마다** 찍었다. 중앙값은 갈린 두 무리의 가운데 어딘가를 가리킬
뿐이다. 찍어보니 붕괴한 판의 공통점이 나왔다:

```
시드   등급  만족  시설    현금   만석%  직원  개선 | 살아 입장 헛걸음
1028    1     0    74   5569만   100  15.4  5.00 | 살아  75 입장   0 헛걸음   0
1070    1     0    83   9669만   100  15.8  5.00 | 살아  81 입장   0 헛걸음   0
```

**돈도 직원도 개선도 충분한데 만족도가 0.** 그리고 **입장이 0 인데 손님이 75~81명 살아
있다** — 상한이 30 인데. 만족도 0 은 "나쁜 경험"이 아니라 **"한 주 내내 아무도 퇴장하지
않았다"**였다 (`totalExited === 0` 이면 0 을 돌려준다).

### 원인: 시설로 막힌 구역에 갇힌다
`field.next()` 가 null 이면 `leaving` 손님은 `continue` 로 **제자리에 영원히 선다.**
그리고 배치 검사는 **지형과 벽만** 본다 (`reachable(terrain, walls, gate)`) — 다른 시설은
보지 않으므로 시설로 걸을 수 있는 구역이 막힐 수 있다.

그러면 나선이 닫힌다: 퇴장 없음 → 정원이 영원히 찬다 → 주간 입장 0 → 퇴장 만족도 0 →
등급 1 → 상한 30 → 그 30 이 갇힌 손님으로 차 있음 → **돌아올 길이 없다.**

**안전 밸브**를 넣었다: 제자리 200 tick(하루 반)을 넘으면 갇힌 것으로 보고 정리한다.
인내(300 tick)보다 짧게 둔 이유는 인내는 "갈 곳이 없다"이고 이건 "길이 없다"라서 더 빨리
판정해야 판이 안 얼어붙기 때문이다.

### 그 전에 하나 더 있었다 — 합계에 상한이 없었다
`staff.ts` 머리말에 "부족은 절벽이 아니라 비율"이라고 적어놓고 **합계에는 상한이 없었다.**
운영요원 0 → 수상 시설 전멸 + 정비공 0 → 고장 다발이면 **전부** 설 수 있었다.
`maxIdleRatio = 0.4` 로 한 번에 설 수 있는 비율에 상한을 뒀다 — 그래야 매출 바닥이 남고
직원을 다시 쓸 수 있다.

### 결과 — 양극화가 사라졌다
| | 등급 | 만족도 | 만석 | 붕괴한 판 | 경보 |
|---|---|---|---|---|---|
| K23 (312주) | 1 또는 5 | 0 또는 90~98 | 100% | **4/12** | 2건 |
| K24 (312주) | 2~5 | 65~100 | 0~32% | **0/12** | 1건 |
| K24 (156주) | 3~5 | 73~97 | 0% | 0/12 | **0건** |

갇힌 손님이 정원을 물고 있던 것이 풀리자 만석이 사라졌다. 파산 0.

**312주에 남은 경보 하나는 "후반이 빈다"** (272주에 지을 게 없고 현금 1.6억) — K19 에서
확인한 구조적 항목이고 개선 단계 5 로 완화했지만 312주를 채우진 못한다. 이건 미결로 둔다:
후반 돈 쓸 곳을 하나 더 만드는 결정(토지 매입 등)이 필요하고, 그건 설계 결정이다.
(K25 에서 격자를 넓혔지만 이 항목은 그대로다 — 막는 것은 자리가 아니라 등급 상한이다.)

**교훈:** "만족도 0" 을 나쁜 경험으로 읽고 밸런스를 만졌다면 영원히 못 찾았다.
0 이 **"측정 대상이 없다"**는 뜻일 수 있는지 먼저 물어야 했다.

## K25 벽을 경계로 · 건물 영역 · 격자 64×48

세 가지를 한 번에 바꿨다. 셋이 서로 물려 있어 따로 하면 중간 상태가 말이 안 된다.

### ① 벽이 칸에서 **경계**로 옮겨갔다

예전 벽은 타일 하나를 통째로 먹었다. 화면에서 **32텍셀 두께의 상자**로 보였고, 벽을
두르면 바닥이 그만큼 사라졌다. 실제 카이로의 벽은 칸과 칸 **사이**에 있고 바닥은 벽
밑까지 이어진다.

```
WallGrid              // 칸이 아니라 경계를 저장한다
  ei[]                // (i,j) ↔ (i+1,j)
  ej[]                // (i,j) ↔ (i,j+1)
  blocksMove(a, b)    // 이게 벽의 전부다 — 칸이 아니라 이동을 막는다
```

`-I`·`-J` 경계는 **이웃이 소유한다** (`edgeAt` 이 이웃에게 넘긴다). 한 경계가 두 곳에
저장되면 반드시 어긋난다.

길찾기도 같이 바꿨다 — `FlowField.build(walkable, targets, canCross)` 로 **간선 판정**을
받는다. `build` 에만 넣고 `next()` 를 빼먹으면 거리장은 맞는데 손님이 벽을 통과한다.

**측정된 결과** (골든 12주): 퇴장 만족 63→72 · 방문객 109→118 · 헛걸음 14→5.
개선이 아니라 **모델 변경의 직접 결과**다 — 벽 두 줄이 먹던 32칸이 돌아왔고, 걷는 거리가
줄어 걷기 감점이 줄었다.

에셋도 줄었다: 4방 비트마스크 16 + 문 2 = **18장 → 경계 4방 × (벽·문) = 8장.**
"이 칸이 어느 이웃과 이어지나"를 그림이 표현할 필요가 없어졌다.

### ② 벽을 한 장씩 놓지 않는다 — **영역**을 정하면 벽이 결과로 생긴다

실내 시설 9종이 전부 벽부착이고 위생 수요는 벽 없이는 못 채운다. 그래서 예전에는
**게임을 켜자마자 벽을 스무 칸 찍는 것**이 첫 할 일이었다. 그건 목표가 아니라 준비물이다.

```
BuildingStore.place(rect)
  → 겹치는 건물을 흡수한다        // "넓히기" 가 곧 새 사각형이다
  → walls.clear() 후 외곽선만 다시 굽는다
  → 게이트에서 가장 가까운 외곽 경계에 문 1개
  → 실내가 전부 닿는지 확인, 아니면 통째로 되돌린다
```

두 건물이 맞닿으면 그 경계는 **양쪽 다 실내라 외곽선이 아니다** — 벽이 자동으로 사라진다.
규칙을 따로 쓰지 않았고, 외곽선의 정의에서 따라 나온다.

조작은 **모서리 두 번 탭**이다. 드래그는 이미 카메라 팬이라 뺏을 수 없다. 첫 탭은 마름모
테두리로 표시한다 — 표시가 없으면 "아무 일도 안 일어났다"로 읽혀 같은 칸을 또 찍고,
1×1 이 되어 거절당한다.

### ③ 격자 40×32 → **64×48**, 등급마다 토지가 넓어진다

40×32 는 한 화면에 거의 다 들어와 "넓힌다"는 감각이 없었다. `GRID_SUM_MAX = 100` 을
의도적으로 넘겼다 (112) — 상한은 "세로 팬이 필요 없다"는 편의였지 정확성 조건이 아니고,
카메라의 `tallEnough` 분기가 이미 세로 팬을 처리한다.

죽어 있던 `landW`/`landH` 를 살렸다. 게이트 쪽 모서리에서 자라는 사각형이고, **세로는
1등급부터 물가를 넘는다** — 세로를 조금씩 늘리면 3등급 전에는 물에 못 닿고, 빠지 게임에서
물이 잠겨 있으면 그건 다른 게임이다. 넓어지는 축은 주로 가로(강변을 따라)다.

| 등급 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 토지 | 18×34 | 30×38 | 42×42 | 54×46 | 64×48 |

바깥 칸은 어둡게 칠한다. 선만 그으면 "저기도 지을 수 있는데 선이 왜 있지"로 읽힌다.

**⚠ 봇에도 같은 제약을 넣었다.** 안 넣으면 헤드리스 밸런싱이 실제로 못 쓰는 땅을 쓰고,
숫자와 손으로 하는 판이 갈라진다 — 검증이 조용히 통과하는 전형이다.

### 밸런스

52주 × 12판 **경보 0 · 파산 0.** 현금이 826만에 머문다 (예전 1.6억). 다만 후반 건설비가
여전히 0 이다 — 막는 것은 토지가 아니라 **등급 상한**이다 (`자리 부족 0회` · `상한 도달 9회`).
토지 해금은 지금 밸런스를 바꾸지 않는다. 넓어지는 것이 보이는 것이 목적이었다.

### 세이브 v2

옛 벽 배열은 "이 칸이 벽이다"라 새 모델로 옮길 방법이 없다 — 한 칸을 네 경계로 펴면
통행이 통째로 막히고, 두 개만 고르면 어느 쪽인지 알 수 없다. **버리고** 건물 영역을 빈
채로 넣는다. 시설 배치는 남으므로 판은 계속 돈다.

## K26 건물 검토 ①②③ — "실내"가 sim 에 없었다

K25 직후 건물 규칙을 다시 훑고 의심 지점을 헤드리스로 재현했더니 **8건 중 6건이 실제로
재현됐다.** 그중 뿌리가 같은 셋을 고쳤다 — 셋 다 sim 에 **"실내"** 와 **"손님이 설 수 있는
칸"** 이라는 개념이 없어서 생긴 것이다.

### ① 실내 시설이 건물 *바깥*에도 붙었다

```
① 벽부착  실내 ok · 바깥 ok(❗)
```

`requiresWallAdjacent` 를 `walls.hasAnyEdge(i,j)` 로 판정했는데, **경계는 두 칸이
공유한다.** 건물 밖에서 벽에 접한 칸도 참이라 샤워실·탈의실 9종이 야외 잔디에 놓였다.

붙는 대상은 벽이 아니라 **방**이다. 데이터 필드를 `requiresIndoor` 로 바꾸고,
`BuildingStore.isIndoor` 를 배치 검사에 넘긴다. **발자국이 전부** 실내여야 한다 —
반만 실내인 시설은 없다.

넘기는 걸 잊으면 조용히 느슨해지지 않도록, 판정을 안 주면 **가장 엄한 쪽**(실내 시설
거절)으로 떨어뜨린다.

### ② 문이 시설로 막힌 칸에 뚫렸다

```
② 문 (6,6) → 바깥칸 (5,6) · 그 칸이 시설로 막혔나: 막힘(❗)
⑧ 시설로 완전히 막힌 뒤 — walls.reachable 이 닿는다고 보나: 예(❗ 손님은 못 간다)
```

`reachable()` 은 지형만 봤고 손님은 `placement.blocksWalk` 도 본다. **정의가 둘이었다.**
`guestWalkable(terrain, placement)` 하나로 합치고 손님·문·도달 검사가 전부 그걸 쓴다.

고치는 과정에서 **같은 뿌리의 버그를 두 개 더** 팠다:

- **시설이 든 방을 넓힐 수 없었다.** 실내 도달 검사가 시설이 놓인 칸까지 "못 닿는다"로
  셌다. 시설이 놓인 칸은 막힌 게 아니라 **쓰이는 중**이다 → 설 수 없는 칸은 건너뛴다.
- **문이 안쪽으로 열릴 곳을 안 봤다.** 바깥칸만 검사해서, 문이 시설로 꽉 찬 실내 칸으로
  열렸다. 문은 **양쪽 다** 설 수 있어야 한다.

둘 다 내가 아니라 **헤드리스 밸런싱이 잡았다** — 사유별 집계를 붙이자
`place-unreachable 33` 이 바로 떴다.

### ③ 격자 가장자리 건물은 한 면이 열려 있었다

```
③ 가장자리 3×3 — 경계 9 (온전하면 12)
```

`WallGrid` 배열이 w×h 라서 (0,j) 의 `-I` 경계, 즉 **(−1,j) 의 +I 경계**를 담을 자리가
없었다. `setEdge` 가 조용히 버렸다. 게이트가 (0,0) 이고 토지가 거기서 자라니 **초반
건물은 거의 다 가장자리**에 붙는다 — 그쪽 면이 통째로 뚫린 채 지어졌다.

배열을 (w+1)×(h+1) 로 늘리고 인덱스를 1 밀었다. "지나갈 수 없는 것"과 "벽이 보이는 것"은
다른 문제다.

### 봇에 진짜 건물을 줬다

①을 고치면 봇은 실내 시설을 **하나도 못 짓는다** — 예전엔 경계 몇 줄만 세워 뒀기 때문이다.
그대로 두면 밸런싱이 실제 게임과 완전히 다른 판을 돌게 된다. `BuildingStore` 를 넣고,
방이 차면 **기존 방을 넓히도록** 했다 (새 방만 찾게 했더니 `no-room` 106건).

건물값(칸당 4만원)은 아직 안 낸다 — 플레이어만 낸다. 검토 ⑥ 으로 남긴다.

### 남긴 것 (검토 ④~⑪)

맞닿은 두 채가 문이 둘 · 봇이 건물값을 안 냄 · 값이 코드에 박힘 · 미리보기 없음 ·

## K27 카이로 모델로 되돌리기 — 바닥을 깔면 그게 방이다

"카이로소프트 느낌이 전혀 아니다"는 지적을 받고 레퍼런스와 우리 화면을 나란히 재봤다.

### 우리가 카이로보다 복잡한 걸 만들고 있었다

위키의 한 줄이 전부다:

> "Any indoor tile created will make an indoor area, which requires an Entrance for
> customers to access."

건설 메뉴는 `Tiling`(바닥) / `Utilities`(입구·화장실·샤워) / `Decorations` 세 갈래고,
플레이어의 동사는 **"바닥을 산다"** 하나다. 벽은 결과로 그려질 뿐 플레이어가 다루는
물건이 아니다.

K25 는 "영역을 두 번 탭하면 외곽선이 벽이 된다"를 만들었다. 화면은 비슷했지만 모델이
다르고, **그 모델에서만 생기는 문제가 여섯 개** 나왔다 (K26 검토 ④~⑪). 모델을 바꾸니
전부 사라졌다:

| 사각형 모델의 문제 | 바닥 모델에서 |
|---|---|
| 맞닿은 두 채가 문이 둘 | 이어 깔면 **한 덩어리 · 문 하나** (연결성분) |
| 겹치면 흡수, 인접은 안 함 | 구분이 없다 — 옆 칸에 한 칸 더 까는 것뿐 |
| 1×1 거절 | 한 칸도 정상이다 |
| 미리보기 없음 | 한 칸씩 칠하므로 미리보기가 필요 없다 |
| 취소가 "최소 2×2" 에러로 뜸 | 취소가 없다 — 다른 바닥으로 덮으면 된다 |
| 철거 확인 없음 | 잔디로 되돌리면 그 칸만 사라진다 |

`BuildingStore`(사각형·흡수·롤백, 279줄)가 통째로 사라지고 `indoor.ts` 가 됐다.
실내 여부는 **지형이 이미 안다** (`terrain.isIndoor`) — 따로 저장하지 않으므로
지형과 어긋날 수가 없다. 세이브에서도 건물 저장소가 사라졌다 (v3, 옛 사각형은
`floor_indoor` 로 옮겨 보존한다).

`PlaceOptions.indoor` 도 사라졌다. 넘길 것이 줄면 넘기는 걸 잊을 일도 준다.

### 벽 높이 24 → 10, 그리고 거꾸로였던 규칙

계약에 이런 규칙이 있었다: **"실내 시설은 벽보다 낮아야 한다"** (`bodyH ≤ 24-4`).
지키려던 것은 "벽 뒤로 숨지 않게"인데, 벽이 앞에 서면 낮은 쪽이 **완전히 가려진다** —
정반대다. 벽을 유리 스티플로 만든 것도 이 가림 때문이었다.

벽을 10텍셀(타일 높이 16보다 낮게)로 낮췄다. 이제 지켜야 할 계약은 하나다:

```
KAIRO.wall.heightTexels < KAIRO.guest.cellTexels[1]   // 벽은 손님보다 낮다
```

캔버스도 32×40 → **32×26** 으로 줄었다.

## K29 표면 이식 — 카메라는 이미 같았고, 평평한 게 문제였다

"카이로소프트를 모방한다고 해도 무방할 정도로" 라는 요구를 받고, **먼저 카메라 각도부터
쟀다.**

### 투영은 이미 똑같다

레퍼런스 바닥의 **2D 자기상관**으로 격자 벡터를 뽑았다:

| | 격자 벡터 | \|dx/dy\| |
|---|---|---|
| 카이로 | `(-10,5)` · `(-20,10)` | **2.00** |
| 우리 | `(6,3)` · `(12,6)` | **2.00** |

둘 다 정확히 **2:1 다이메트릭**이다. 타일 30×15 vs 32×16(6% 차) · 손님 키 타일의 1.5배 ·
가로 화면 타일 수 26.6 vs ~28 — **투영·확대·비율은 손댈 것이 없었다.**

⚠ 첫 시도는 그라디언트 방향 히스토그램으로 쟀는데 45° 가 나왔다. **픽셀 계단을 잰
것**이라 틀렸다 — 2:1 인 우리 화면도 45° 가 나왔다. 측정법이 틀렸는지 먼저 물어야 했다.

### 잰 차이 — 우리 UI 는 평평하다

레퍼런스 UI 픽셀을 직접 뽑으니 버튼이 `#1879fe` 에 어두운 테두리, 하단 바가 `#cce6f3`
(밝은 하늘)이었다. 우리는 어두운 남색 **평면 + 1px 단색 테두리**였고, `style.css` 800줄에
`transition` 이 **1개**뿐이었다.

**팔레트는 어두운 톤을 유지하기로 했다** (사용자 결정). 밝은 팔레트로 가면 패널 7종의
하드코딩 색 **127곳**(토큰 0곳)을 같이 바꿔야 하는데, 안 바꾸면 HUD 만 밝고 패널은 어두워
지금보다 더 어색해진다. 얻는 것은 "카이로 느낌의 절반" — 색은 우리 것, 재질은 카이로.

### 적용한 것 — MengTo/Skills 에서 셋

주제(랜딩페이지 vs 게임)가 아니라 **기법**으로 골랐다. 처음엔 주제로 걸러서 85개를 통째로
"무관"으로 넘겼는데, 그중 순수 CSS 기법 셋은 매체와 무관하게 그대로 쓴다.

- **`skeuomorphic-ui`** — 세로 그라디언트 + 1px 그라디언트 보더 + 바깥/인셋 그림자 +
  상단 하이라이트 + 텍스트 양각. 카이로 버튼의 구성과 같다
- **`css-border-gradient`** — `padding-box` + `border-box` 이중 배경
- **`animation-systems`** — 마이크로 160ms · 상태 변화 220ms · `transform`/`opacity` 만

`.kbtn`/`.kcap`/`.kitem`/`.kbar`/`.ksheet` 다섯에만 적용했다. **HUD 블록의 하드코딩 색을
전부 토큰으로 뺐다** (`--panel-sunk`/`--risk-*`/`--bar-bg` 등 15개) — 정적 검사가 이걸 지킨다.

### 말풍선 — 있었는데 너무 작았다

`bakeEmoteAtlas()` 가 이미 흰 풍선 + 꼬리 + 기호를 굽고 있었다. **12텍셀이라 손님 키의
절반**이라 화면에서 안 보였다. 20 으로 키우고 기호를 다시 그렸다.

키우고 나니 **거의 모든 손님에게 붙어 화면을 덮었다.** `emoteTicks` 30(3초) → 12 로 줄여
몇 명에게만 뜨게 했다. 표시 전용 값이라 RNG·결정론·밸런스와 무관하다.

글자는 안 넣었다 — 카이로는 "Nom nom!" 같은 짧은 영어를 쓰는데 20텍셀에 한글은 물리적으로
안 들어간다.

### 정적 검사 — 브라우저 없이 파일만 읽는다

전환이 레이아웃 속성을 안 만지는지 · `prefers-reduced-motion` 가드 ·
**HUD 블록에 하드코딩 hex 0** · 쓰는 토큰이 `:root` 에 실제로 선언됐는지(오타로 `var()` 가

## K30 물려받은 빠지 — 새 판이 빈 땅이었다

"건물이 미리 설치돼 있어서 거기서 확장하는 건? 건물 설치가 따로 없어서 아무것도 설치가
안 돼" 라는 지적을 받고 잰 것:

```
북한강형  토지 18×34 · 1등급에 놓을 수 있는 시설 24종
  못 놓는 이유: needs-indoor 9 · 등급 34 · wrong-terrain 6
```

**위생 시설 9종 전체가 막혀 있었다.** 그런데 첫 의뢰가 "기본 위생 3개"다. 뚫으려면 건설
시트의 바닥 탭에서 `실내 바닥 3만` 을 여러 칸 칠해야 하는데 **그걸 알려주는 것이 화면
어디에도 없었다.** K27 에서 "바닥을 깔면 그게 방"으로 모델을 바꾸며 생긴 구멍이다.

시나리오 이름이 **"물려받은 빠지 — 작은 빠지를 물려받아 키운다"** 인데 데이터에는
`startCash` 와 `grade` 뿐이었다. 설계 문서(§0:00, §4.4)는 처음부터 답을 갖고 있었다:

> 플레이어는 완전히 빈 땅에서 시작하지 않는다. 손님이 어디서 오는지 모르면 동선 판단이
> 안 된다. v3 초안은 코스를 25분에 만나게 했다 — 10분 하고 끄는 사람은 시그니처를 아예 못 본다.

### 맵마다 다른 시작 배치

`kairo-maps.json` 에 `start` 를 넣었다. 지형이 다르므로 같은 배치가 안 맞는다.

| | 마당 | 실내동 | 데크 | 코스 |
|---|---|---|---|---|
| 북한강형 (육지 0.34) | 9×6 | 5×3 | 3 | ○ |
| 계곡형 (육지 0.7) | 12×7 | 6×3 | 1 | ✕ — 넓은 수역이 없다는 설정과 맞춘다 |
| 호수형 | 10×6 | 5×3 | 2 | ○ |

`applyStartKit()` 은 **RNG 을 안 쓴다.** 게이트 모서리와 찾아낸 물가를 기준으로 고정
오프셋만 쓴다. 어느 단계든 실패하면 건너뛰고 `skipped` 에 남긴다 — 시작 배치가 부팅을
막는 것이 최악이다. 봇도 **같은 함수**를 쓴다 (예전엔 8×4 바닥을 즉석으로 칠했다).

**실내동은 비워서 준다.** 설계가 "화장실이 없다 — 어디에 둘 것인가"를 첫 결정으로 두기
때문이다. 없앨 것은 *결정*이 아니라 **보이지 않는 전제조건**이다.

### 밸런싱이 게임 규칙 구멍 두 개를 잡았다

킷을 넣자 **"자리가 없어 건설이 막힌다" 경보**가 떴다 (`no-room` 98). 네 번을 추측으로
고치려다 전부 빗나갔고(단일 칸 확장 · 문 자리 우선 · 방 둘레 비우기 · 미리 넓히기),
**봇 실행 안에서 실패 순간의 판을 직접 찍고 나서야** 원인이 보였다:

```
 1|   f...             |    . = 빈 실내   X = 시설 찬 실내   f = 실외 시설
 2|    XX.             |
 3|XX.X.X..   f        |
 [DUMP] bake: {"ok":false,"fail":"unreachable"}
```

**봇 문제가 아니라 게임 규칙이 빠져 있었다.** 두 가지를 `placement.check` 에 넣었다:

1. **`blocks-door`** — 문이 있는 경계에 접한 칸에는 시설을 못 놓는다.
   방을 만든 뒤 **나중에 놓은 시설이 문 앞칸을 덮으면** 그 방은 죽는다. 벽에는 문이 그대로
   남아 있어 화면상 멀쩡해 보이고, 안의 시설이 조용히 매출 0 이 된다
2. **`would-strand`** — 실내에 놓아 다른 실내 칸을 못 가게 만들면 거절한다.
   벽에는 밀폐 차단(`would-seal`)이 있는데 **시설에는 없었다.** 방 안쪽을 갈라 놓으면
   그 칸들은 영영 못 쓰고 방은 그 뒤로 넓히지도 못한다

둘 다 **플레이어가 똑같이 겪을 수 있던 버그**다. 넣고 나니 `자리 부족` 이 8 → **0**,
경보가 사라졌다 (26주·52주 모두).

### 하네스도 같이 고쳤다

새 판에 배치가 생기자 **빈 판을 가정하던 검사 6개**가 깨졌다. 절대값을 증분으로 바꾸고,
킷과 안 겹치는 자리를 쓰게 했다. 둘은 더 근본적이었다:

- **손님 검사를 새 판에서 돌린다.** 그 앞 열네 개 검사가 지형을 칠하고 방을 만들고
  지우고 시설을 놓은 잔해 위에서 재고 있었다 — 같은 코드가 새 판에서는 손님이 시설을
  쓰는데 하네스 안에서는 25초를 기다려도 0 이었다
- **고정 9초 대기를 조건 대기로.** 고정 시간은 판이 달라지면 조용히 깨진다

단위 **636** (신규 9: 위생 시설 배치 · **음성 대조군** · 결정론 · 도달) ·

## K31 건물을 넓히는 것이 게임이 되게 — 직접 플레이하다 막혔다

K30 을 끝내고 **새 판을 직접 해봤더니** 두 번째 시설에서 막혔다:

```
facility:toilet       → (4,3) −31만
✕ facility:shower_row   놓을 자리 없음        ← 화장실 하나 놓으면 끝
```

사용자도 같은 것을 지적했다: *"이 안에 설치되는 요소들이 설치가 안 될뿐더러, 이걸
확장하는 부분들도 있어야 하는데 없네. **이걸 확장하면서 안에 여러 요소를 넣는 게
카이로소프트적인 부분이야.**"*

### 잰 것

| 맵 | 시작 방 | 처음 들어가는 실내 시설 | **화장실 하나 놓은 뒤** |
|---|---|---|---|
| 북한강형 | 5×3 | 9/9 | **4/9** — 4칸짜리(샤워·락커)가 즉시 사라진다 |
| 계곡형 | 6×3 | 9/9 | 7/9 |
| 호수형 | 5×3 | 9/9 | **4/9** |

문제는 둘이었다:

1. **방이 너무 작다** — 첫 시설 하나에 다음이 막힌다
2. **넓히는 길이 안 보인다** — 기능은 있었다 (`건설 ▸ 바닥 ▸ 실내 바닥`). 그런데 화면
   어디에도 "이게 건물을 넓히는 것"이라고 안 쓰여 있고, 거절 메시지도 방법을 안 알려줬다

카이로의 핵심 루프가 "건물을 넓히며 안을 채운다"인데 **그 루프의 입구가 없었다.**

### 고친 것

- **건설 시트에 `건물` 탭** (2탭 → 3탭). `실내 바닥` 을 바닥 탭에서 꺼내 `건물 바닥
  3만 · 칠하면 넓어짐` 으로. 확장이 카이로의 핵심 동사라 자기 탭을 줘야 보인다.
  `BuildItem.tab` 을 `kind` 와 따로 뒀다 — 건물 바닥은 지형이지만 탭은 건물이다
- **안 들어가는 실내 시설을 시트에서 미리 잠근다** — `자리 없음 · 건물을 넓히세요`.
  등급 잠금과 같은 방식이다 ("열어봐야 아는 정보면 아무도 안 연다"). 실내 칸만 훑으므로
  싸고, 바닥을 칠하거나 시설을 놓고 지울 때마다 다시 만든다
- **거절 메시지가 방법을 말한다** — `건물 안에만 지을 수 있습니다 — 건설 ▸ 건물 에서 넓히세요`
- **시작 방을 키웠다** — 북한강 5×3 → 7×4 · 계곡 6×3 → 8×4 · 호수 5×3 → 7×4 (마당도 함께).
  목표는 "처음 세 개를 연달아 놓을 수 있다" — 그 다음부터는 넓혀야 한다.
  **넓히는 것이 게임이지, 못 놓는 것이 게임은 아니다**

### 다시 플레이해서 확인했다

```
시작: 시설 4 · 현금 500만
  ✓ toilet       → (4,3) −31만
  ✓ shower_row   → (6,3) −31만
  ✓ locker_row   → (6,4) −31만 · 콤보 2개 발동

결과: 시설 9 · 현금 356만
카드 1/2 폭염 예보 → 카드 2/2 장마 예보 → 결산 (입장 75명 · 손익 34만 · 퇴장 만족 60)
```

(플레이 중에 "결산이 안 뜬다"고 두 번 헛짚었는데, **주간 카드가 먼저 뜨는 것**이 정상이고

## K32-A 배치를 손에 잡히게 — 그리고 죽어 있던 기능 하나

새 판을 해본 뒤 나온 다섯 요구를 **먼저 재고** 시작했다. 절반은 이미 있었다.

|---|---|
| 건물 바닥 2×2 / 4×4 | 없다 |
| 견인기구 루트 | **이미 다 된다** (검사 6개 통과) — 다만 K28 에서 메뉴 시트로 들어가 **버튼이 안 보였다** |

### ⚠ 토지 표시는 K25 부터 죽어 있었다

`setLand` 가 **씬 타일이 만들어지기 전에** 불려 빈 배열을 돌고 끝났다. K27 에서
`refreshAllWalls` 로 겪은 것과 같은 타이밍 문제인데, 그때는 크래시가 나서 잡혔고
이번엔 **조용히 아무 일도 안 해서** 일곱 페이즈를 넘겼다. 검사 155개 중 **tint 를 보는
것이 하나도 없었다.**

고치는 방식도 그때와 다르게 했다 — 부르는 쪽의 순서를 고치는 대신 **씬이 값을 기억했다가
타일이 생기면 적용한다.** 호출 순서에 기대지 않으면 다시는 이렇게 안 죽는다.
그리고 음성 대조군까지 붙였다 (토지를 다 열면 구분이 사라진다).

### 건물 바닥 2×2 · 4×4

16칸이 아니다.

### 고스트 + 확정 (회전 자리를 비워 둔다)

탭하면 바로 놓던 것을 **탭 → 고스트 → 확정**으로 바꿨다. 회전과 "장비를 타고 있는 손님"
그림이 나중에 들어오므로 **놓기 전에 만질 수 있는 상태**가 필요하다.

- `KairoScene.setGhost(defId, i, j, ok, facing)` — 실제 스프라이트를 반투명으로.
  못 놓는 자리는 붉게. `facing` 은 지금 안 쓰지만 **인자를 열어 뒀다**
- 확정 바는 v1 의 `.place-label` / `.place-btn` 을 그대로 쓴다 (위치만 카이로용)
- **회전 버튼은 자리만 잡고 비활성** — 방향 스프라이트가 생기면 켠다
- 못 놓는 자리에서도 고스트를 띄운다. 왜 안 되는지 라벨로 붙어 있는 편이 스치는

## K32-B 포장한 바닥만 걷는다 — 그래서 길이 곧 입구다

### 두 요청이 사실 한 기능이었다

"도로 혹은 사람들이 갈 수 있는 바닥을 정하면 좋겠다"와 "건물마다 입구·방향이 있어야
할 것 같다"는 따로 만들 일이 아니었다.

문은 `bakeIndoorWalls` 가 자동으로 고른다 — 외곽 경계 중 **게이트에서 가장 가깝고 양쪽에
설 수 있는** 곳. 그런데 잔디도 걸을 수 있으니 사실상 아무 데나 났다. **포장한 바닥만
걷게 되면 문은 포장된 칸으로만 날 수 있다.** 즉 플레이어가 길을 어디로 내느냐가 곧
입구의 위치와 방향을 정한다. 새 메커니즘도, 새 저장 상태도 없다.

### `walkable` 을 둘로 나눴다

| 필드 | 뜻 | 잔디 |
|---|---|---|
| `walkable` | 육지인가 (지을 수 있나) | **참** |
| `guestWalk` | 손님이 지나가나 | **거짓** |

`guestWalkable()`(손님이 설 수 있는 칸의 유일한 정의, K26)이 새 쪽을 본다. `isWalkable`
을 쓰는 카이로 코드 9군데 중 **바꾼 것은 이 하나**다 — 물/육지 판정, 덱 연결, 물가 찾기는
그대로다. K26 에서 정의를 한 곳에 모아 둔 것이 여기서 값을 했다.

⚠ `placement.check` 의 `unreachable` 도 손님 판정으로 바꿨다. 안 바꾸면 "검사는 통과하는데
손님은 못 온다"가 다시 생긴다 (K26 ② 와 같은 구멍).

### 파급은 테스트 92개였고, 그게 정상이었다

판을 잔디로 깔던 테스트가 전부 깨졌다. 그 헬퍼들의 의도는 "통행 가능한 평지"였지
"잔디"가 아니었으므로 석재로 바꿨다. **골든 12주 못박은 숫자는 그대로**다 — 전부 포장하면
K32-B 이전과 보행 조건이 같으니, 이 변경이 경제에 중립이라는 증거가 된다.

### 되돌릴 수 있는 실수는 막는다

포장만 걷게 되면 **길 한 칸 지우고 리조트가 죽는** 일이 생긴다. 시설의 `would-strand`,
벽의 `would-seal` 과 같은 기계(`reachable` 전후 비교)를 바닥 철거에도 걸었다.

### 봇도 길을 깐다

`ensurePath` — 0-1 BFS 로 **새로 깔 칸이 가장 적은** 경로를 찾아 포장한다. 안 넣으면
헤드리스가 "아무것도 못 짓는 판"이 되어 실제 게임과 갈라진다 (토지 해금을 봇에 안 넣었을
때와 같은 사고). 12판 26주에서 **137번 · 562칸** 실제로 깔았다.

재기준선: 초반 현금이 낮아지고(4주 309만→259만, 8주 636만→459만) 후반은 오른다
(24주 609만→966만). 경보 0 · 파산 0 유지.

### 길 붓 1·2·3

길이 가장 자주 하는 동작이 됐는데 한 칸씩 찍어서는 폰에서 못 깐다. 건물 바닥에 쓰던
블록 붓(K32-A)을 길에도 붙였다. 목록의 `sub` 에 **통행 여부**를 적는다 — 규칙을 바꿔
놓고 화면 어디에서도 안 알려주는 것이 이 게임의 반복된 실수였다.

`unreachable` 문구도 바꿨다: "손님이 닿을 수 없는 자리입니다" → **"손님이 못 옵니다 —
여기까지 길을 까세요"**. 처방이 없는 거절은 막다른 길이다.

### 문 앞 발판 — 깊이를 두 번 틀렸다

문은 벽 스프라이트의 틈이라 눈에 안 띈다. 그런데 이제 문 위치는 플레이어가 길을 낸
**결과**다. 결과가 안 보이면 원인을 못 배운다.

1. 깊이 1 → 지면이 칸마다 `depthKey` 로 정렬되므로 지면이 위로 와서 **아무것도 안 보였다**
2. 칸 깊이 +1 → 이번엔 **건물 자기 뒷벽**에 가렸다. 게이트가 (0,0) 이라 문은 대개
   카메라 반대쪽(−I·−J)에 나고, 그쪽 발판은 벽 뒤가 된다
3. → 세계 물체가 아니라 **힌트 층**(999_998, 토지 표시 옆)으로. 반투명이라 밑의 손님이 비친다

그리고 **한 경계가 두 번 잡혔다** — (2,3)의 +I 와 (3,3)의 −I 는 같은 경계다 (K25).
그대로 그렸더니 발판이 방 안에도 깔렸다. 실내가 아닌 쪽에만 한 장 그린다.

### 검증이 또 조용히 통과할 뻔했다

시작 킷의 "문 바깥이 포장인가" 검사를 처음엔 `바깥 || 안쪽` 으로 썼다. 안쪽은 실내
바닥이라 **언제나** 참이어서 아무것도 안 보고 있었다. 실내가 아닌 쪽을 정확히 골라 잰다.

### 검증

단위 **653** (신규 14: 잔디/포장 대조 + 음성 대조군 · 문이 길을 따라온다 2건 ·
길 철거 거절 4건 · 시작 킷 연결 2건) · 브라우저 **167/167** (신규 5) · 정적 18/18 ·

## K33 코스를 실제로 그릴 수 있게 — 그리고 백도어 검사를 걷어냈다

### "없는" 게 아니라 "못 만지는" 것이었다

코스 편집은 처음부터 다 있었다 — 프리셋 6종·적합도 배지·장비·대수·지표·확정·철거,
핸들 드래그까지. 브라우저 검사 5건도 통과했다. 그런데 **폰에서 열어 보니 못 썼다.**

| 잰 것 | 값 |
|---|---|
| 핸들 2개의 화면 좌표 | **x = −284, −380** (화면 밖) |
| 패널 상단 | y = 434 / 852 → 화면의 **49%** |
| 선착장 | 코드가 찾은 **첫 번째** 데크로 고정 |

패널 주석에는 "핸들은 화면에서 직접 끈다"고 적혀 있었다. 끌 게 화면에 없었다.

### 왜 CI 가 통과했나 — 검사가 화면을 안 봤다

```js
panel.moveHandleForTest(k, w.i, w.j);   // 좌표를 직접 넣는다
panel.confirmForTest();                  // 버튼을 안 누른다
```

sim 이 맞는지는 봤지만 손가락이 닿는지는 아무도 안 물었다. 이 프로젝트가 여덟 번 겪은
"검증이 조용히 통과" 그대로다. 그래서 이번엔 **화면만 보는 검사**를 따로 넣었다:
진짜 CDP 터치로 핸들을 끌고, 확정도 버튼을 눌러서 한다.

### 선착장 — 잔교 하나가 후보 하나 (`dockCandidates`)

데크는 칸 단위 시설이라 3칸짜리 잔교가 후보 3개가 되면 고르는 의미가 없다. 4-이웃으로
묶고, 게이트에서 가장 먼 칸을 `tip`(잔교 끝), 뭍쪽 끝→`tip` 을 `dir` 로 낸다.

**이 `dir` 이 진짜 소득이다.** 패널이 뻗는 방향을 `{x:0, y:1}` 로 박아 뒀는데, 그건 물이
+j 쪽인 맵 하나만 가정한 값이었다 — 가로로 뻗은 잔교에서는 코스가 육지로 나갔다.
순수 함수라 단위 테스트가 이걸 정면으로 본다.

고르는 것은 **지도에서 탭**한다. 목록이 아니라 화면에서 고르는 쪽이 카이로답고,
"어느 칩이 어느 잔교인지" 되짚을 필요가 없다.

### 카메라 — `centerOn` 이 없어서 팬으로 우회하고 있었다

`KairoCamera` 에 중심을 옮길 수단이 없어 `focusTile` 이 "가고 싶은 스크롤과 지금 스크롤의
차이만큼 팬"했다. 팬은 고무줄(`clampSoft`)을 타므로 가장자리에서 목표를 못 맞춘다.

`centerOn(texel, bottomInsetCss)` 를 더했다 — `bottomInset` 은 화면 아래가 UI 에 가려진
만큼이고, **보이는 영역의** 중앙에 놓는다. `frameCourse` 가 선착장+핸들의 경계상자를
재서 이걸 부르고, 안 들어가면 배율을 1로 내린다.

⚠ 단위 테스트에서 표본을 두 번 잘못 골랐다. 판 아래끝 근처 점을 쓰니 `clampHard` 가
물어서 2텍셀이 어긋났고, inset 500 을 넣으니 90텍셀이 어긋났다 — **검사가 아니라 표본이
틀린 것**이었다. 월드 한복판 + 실제 UI 만큼(160px)으로 잡았다.

음성 대조군도 처음엔 틀렸다. "inset 0 이면 가려진 영역에 들어간다"는 화면의 절반을 넘게
가릴 때만 참이다. **"inset 을 주면 정확히 그 절반만큼 올라간다"**로 바꿨다 — 인자를
무시했다면 두 결과가 같아야 한다.

### 슬림 바 — `.kconfirm` 과 같은 꼴

접힘이 기본이고 ▲ 를 눌러야 펼쳐진다. 접힘 **59px = 화면의 7%** (예전 49%).

예전 패널은 `bottom:0; z-index:20` 이라 하단 바를 통째로 덮었고 세이프에어리어도 안 봤다.

접거나 펼 때마다 카메라를 다시 잡는다. 가림 높이가 바뀌었는데 안 잡으면 펼치는 순간
핸들이 바 밑으로 숨는다.

### 표면 — 인라인 22곳·색 35개 → 클래스만

`tools/check-ui-surface.mjs` 는 `style.css` 의 K28 마커 **아래만** 본다. 그래서 이 패널은

## K34 패널 6종을 한 가족으로 — 그리고 게이트를 TS 까지

### 실측으로 드러난 것

K28 이 이미 진단을 적어 뒀다 — *"스타일 체계가 둘로 갈라져 있던 것이 투박하다의 근본
원인"*. 그대로 남아 있었다:

**그래서 게이트를 TS 까지 넓혔다.** 규칙은 "인라인 금지"가 아니라 **"하드코딩 색 금지"**다
— 진행바 폭이나 캔버스 크기 같은 **데이터**는 인라인으로 남아야 한다. 색만 `style.css`
가 소유한다. 지금 10개 파일 전부 0이다.

### 여섯 패널은 표면 셋 + 속 한 벌이었다

| 표면 | 패널 |
|---|---|

`.kcaption`. **새 버튼 클래스를 하나도 안 만들었다** (`.kbtn`/`.on`/`.primary` 로 충분했다).

어두운 채로 남는 사고가 안 생긴다.

### 선택 색을 노랑으로 합쳤다

`--sel-edge` 토큰을 새로 만들어 청록을 유지할 수도 있었지만, 그러면 "고름"이 두 색으로
남는다 — 그게 문제 자체였다. `.kbtn.on`·`.kcourse-item.on` 과 같은 `--accent` 로 통일했다.
브라우저 검사가 세 패널의 실제 테두리 색을 읽어 하나인지 확인한다.

### 조사가 미리 잡은 함정 둘

1. **여섯 중 다섯의 `visible` 이 인라인 `display` 를 읽고 있었다.** 그대로 두고 표면만
   옮겼으면 `kairo-card.pickForTest()` 가 조용히 `false` 를 돌려줬을 것이다 — 카드 검사가
   통과한 채 아무것도 안 고르는 상태. 전부 `!this.root.hidden` 으로 바꿨다
2. **showcase 가 형제의 인라인 `display` 를 직접 만진다.** 마지막에 변환하고
   "닫으면 HUD 가 그대로 돌아온다"를 검사로 못박았다 (버튼 3 → 2 → 3)

### 게이트가 내 구멍을 잡게 만들었다

`prefers-reduced-motion` 검사는 "미디어 쿼리가 존재하나"만 봤다. 그래서 K33 에서 더한
`.kcourse`·`.kcourse-item` 이 가드에 안 들어간 것을 못 잡았다. **"움직임을 선언한 클래스가
전부 가드에 있나"**로 바꿨다 — 대조군으로 확인했다 (하나를 빼면 이름을 짚어 낸다).

주석 안의 색은 검사에서 뺀다. 안 빼면 "예전엔 청록이었다" 같은 설명을 못 쓰고,
그러면 왜 바꿨는지가 코드에서 사라진다.

⚠ 그러다 `rule()` 이 모션 가드 블록의 `.kcourse-item` 을 먼저 집어 재질 검사 3건이
한꺼번에 빨개졌다. 재질은 미디어 밖의 본 규칙에만 있으므로 미디어 블록을 빼고 찾는다.

### 스크린샷으로 잡은 것 셋

숫자가 다 통과한 뒤에도 눈으로 봐야 했다:

1. **도감 티어 줄이 절반만 보였다** — 세로 flex + `overflow-y:auto` 에서 자식이 눌린다.
   `.kover > * { flex: 0 0 auto }`
2. **경영 머리에서 닫기가 탭 사이에 끼어** 탭처럼 읽혔다 — 맨 오른쪽으로
3. **새 판 상세 상자가 가운데 정렬**이었다 — `.krow` 의 `align-items:center` 가
   여러 줄 상자에도 걸렸다

## K35 밝은 팔레트 — 그리고 "예쁘지만 안 읽힘"을 막는 검사

### 레퍼런스에서 실측한 값에서 출발했다

감으로 정하면 되돌릴 근거가 없다. Pool Slide Story 스크린샷의 픽셀을 직접 읽었다:

| 자리 | 값 |
|---|---|
| 하단 바 바탕 | `#d5ecf2` ~ `#b9ddf3` (실내 화면은 아예 `#ffffff`) |
| 주버튼 (MENU·SNS) | `#1b76ff` · `#0880fb` |
| 말풍선 | `#feffed` 바탕 |

**밝은 표면 + 진한 글씨 + 파란 주버튼.** K34 에서 색을 `:root` 한 곳에 모아 둔 덕에
이 블록 하나가 팔레트의 전부였다.

### 뒤집어야 했던 것 — 단순 치환이 아니었다

1. **재질 레시피가 뒤집힌다.** 어두운 표면에서는 위쪽 흰 테두리가 하이라이트였지만,
   흰 표면에서는 흰 테두리가 안 보인다. 위는 거의 흰색, 아래는 **남색** 그림자로 —
   검정 그림자를 그대로 두면 밝은 표면에 물때가 낀다
2. **글씨 양각이 두 종류가 됐다.** 밝은 표면의 진한 글씨에는 아래로 밝은 선을 깔아야
   하는데, 진한 칠 위의 **흰 글씨**(위험도 칩·주버튼·토스트·감상 띠)에 그걸 쓰면
   흰 글씨에 흰 그림자라 뭉갠다 → `--sk-emboss` / `--sk-emboss-on-solid`
3. **모달 스크림만은 어둡게 남긴다.** 밝은 스크림 위에 밝은 상자를 얹으면 상자가 안 떠
   보인다 — 스크림의 일은 뒤를 눌러 앞을 띄우는 것이다
4. **감상 화면 띠는 흰 글씨 그대로.** 지도를 안 가리려고 반투명 검정을 깐 자리라,
   `--text`(진한 남색)를 쓰면 글씨가 띠에 묻힌다
5. 진행바 안쪽의 `흰 15%`, 디버그 상자의 `검정 55%` — 어두운 표면 전용 값이었다

### ★ 대비 검사를 넣었다 — 새 실패 방식이 "안 읽힘"이라서

밝은 팔레트의 실패는 눈으로 잘 안 보인다. 어두운 팔레트에서 맞던 대비가 그대로
뒤집히기 때문이다. **WCAG 대비비**로 14쌍을 잰다 (본문 4.5:1 · 보조 3:1).
그라디언트는 **두 끝 중 나쁜 쪽**으로 판정한다 — 한쪽만 맞으면 절반은 안 읽힌다.

넣자마자 **둘을 잡았다**:
- 잠김 글씨 · 가라앉은 면 **2.8:1**
- 흰 글씨 · 주버튼 **2.8:1** — 레퍼런스의 `#1b76ff` 를 그대로 쓰면 흰 글씨가 안 읽힌다.
  `#2472c6`~`#0f4fa4` 로 내려서야 통과했다

눈으로는 못 봤을 것들이다. 음성 대조군도 확인했다 (본문색을 밝게 하면 네 쌍이 한꺼번에 잡힌다).

### 게이트가 또 내 실수를 잡았다

빌드 시트의 **선택된 탭만 시커멓게** 남았다 — v1 의 `.tab-btn.on` 이
`linear-gradient(#2b4a63,#1d3648)` 로 어두운 팔레트 전용인데, 마커 위라 정적 검사가
안 본다. 스크린샷으로 잡아 시트 안에서만 재질을 통일했다.

그런데 그 새 규칙에 `transition` 을 넣자 **K34 에서 만든 모션 커버리지 검사가 바로
`ksheet-head` 를 짚었다.** 검사가 제 일을 했다.

### 검증

단위 **670** · 브라우저 **179/179** · 정적 **26/26** (25 → 26) · PWA 8/8 · 밸런스 경보 0.

## K36-A 맵을 넓히고, 공원 밖을 만들었다

사용자 요청: 맵을 더 넓게 · 도로 같은 **건설 불가 바깥 영역** · 버스에서 내려 매표소를 거쳐
입장. 이건 새 아이디어가 아니라 **미구현 명세**다 — `design.md` §4.2·§4.4·§13.1 이
"도로(맵 상단 가장자리)", "주차장에서 걸어 들어온다", "입장료 ₩10,000" 을 이미 적어 뒀다.

A(구조)와 B(동선)로 나눠 각각 커밋한다. 한 번에 하면 격자 때문인지 동선 때문인지 못 가린다.

### `buildable` — 세 번째 축

`GroundKindDef` 에 이미 `walkable`(육지인가)과 `guestWalk`(손님이 지나가나)가 갈려 있었다.
여기에 **`buildable`(플레이어가 지을 수 있나)** 을 더했다. 도로·보도·가로수는 걸을 수는
있어도 못 짓는다.

`landRect` 를 오프셋 사각형으로 만들어 테두리를 표현할 수도 있었지만, 지형 플래그면
막을 곳이 **셋**뿐이다 (`placement.check` · 바닥 붓 · `paintFloor`). 실제로 그 셋을
전부 막았다 — 시설만 막고 바닥을 열어 두면 플레이어가 도로를 석재로 덮는다 (K32 와 같은 구멍).

### 격자 96×72 + 도시 띠 8줄

위에서부터 가로수 · 차도 2 · **정류장 보도** · 가로수 4. 정류장에서 입구까지 다섯 칸을
걸어 내려온다 — 처음엔 3줄로 붙여 놨는데 "밖에서 안으로 들어온다"가 안 읽혔다 (사용자 지적).

**격자 크기를 `render/kairo/iso.ts` 에서 `KairoTerrain` 으로 옮겼다.** 세이브
마이그레이션이 새 크기를 알아야 하는데 `save/` 가 `render/` 를 import 하면 의존 방향이
뒤집힌다. 크기는 렌더 사정이 아니라 게임 사정이다.

### 입구를 가운데로, 토지는 좌우로

처음엔 입구를 왼쪽 끝(i=4)에 뒀다. 사용자 지적: *"중간에서 시작해야 나중에 좌우로
확장해나간다."* 맞다 — `landRect` 가 `(0,0)` 에 붙은 사각형이라 한쪽으로만 자랐다.
`landRectAt` 으로 **입구를 중심으로** 좌우로 자라게 바꿨다.

⚠ 파급이 컸다: `withinLand` · `placement.check` 의 `opts.land` · 바닥 붓 · `applyLand` ·
시작 킷 · 봇 · 하네스. `{w,h}` 만 보면 **왼쪽 경계를 안 봐서** 입구 왼쪽이 통째로 열린다.

### 세이브 v4 — 안 하면 조용히 죽은 칸이 생긴다

`fromSnapshot` 셋이 전부 **저장된 크기**를 그대로 쓴다. 상수만 올리면 새 영역이
"잔디처럼 보이지만 영원히 죽은 칸"이 된다 (`paint` 실패 · `outside` · 플로우필드 밖).
렌더는 그것도 그려 준다.

옮기는 방법: 지형을 새 크기로 다시 짜고 **가장자리 줄을 이어 붙인다** (강이 아래·오른쪽으로
이어진다 — 잔디로 채우면 강이 끊긴 지형이 된다) · 모든 좌표를 `+CITY_BAND` 만큼 내린다 ·
벽은 버린다 (실내 바닥이 정본, K27) · 게이트를 새 입구로.

### ⚠ 봇과 골든이 10페이즈 동안 **다른 세계**를 재고 있었다

**아예 못 썼다.** 골든도 같은 40×32 라 **실제 격자를 검증하는 것이 하나도 없었다.**

둘 다 실제 격자로 올렸다. 그러자 숫자가 통째로 달라졌고, 그게 정상이다:

## 검증이 조용히 통과하던 것을 다섯 번 잡았다

1. WebGL 프레임버퍼를 그냥 `readPixels` 하면 **검은색이 돌아와** "배경색 0" 으로 통과한다.
   `?px=1` 로 `preserveDrawingBuffer` 를 켜고, 표본 최빈색이 `0,0,0` 이면 검사를 실패로.
2. 표본 위치를 화면 비율로 잡아 **배경 대역**을 재고 있었다 — 씬에 타일 좌표를 묻는다.
3. 유리 투과를 합성 화면에서 재려다 **옆 벽의 뚜껑**을 읽었다 — 스프라이트 알파를 직접.
4. 유리 뒤를 "구명조끼 주황"으로 세면 0 이 나온다 — 유리 대역과 겹치는 건 손님의 **다리**고
   조끼는 벽의 불투명한 뚜껑에 가려진다. **손님 유무로 픽셀이 달라지는지**(색 무관)로.
5. 골든 테스트의 기댓값을 `g.x` 로 써서 **자기 자신과 비교하는 동어반복**이었다.
