> 2026-08-19. 사용자 지적: "설계한 게 생각보다 중독성 등 불편한 게 많다".
> **주장 대신 측정으로** 확인했다. 조사(웹) + 실제 조작(폰 크기 393×852) + 헤드리스 실측.

## 조사에서 얻은 기준

- 카이로소프트가 중독적인 이유는 "**항상 무언가를 향해 가고 있다**"는 것 —
  해금·확장·순위가 끊기지 않는다 ([TheXboxHub](https://www.thexboxhub.com/lights-camera-kairosoft-silver-screen-story-is-your-new-xbox-pc-management-sim/),
  [Grokipedia](https://grokipedia.com/page/Kairosoft))
- 그 철학은 "**중독적 단순함**" — 짧은 세션을 지원하되 진행은 깊게
- 모바일 온보딩: **첫 세션이 가장 중요**하고, 잘하면 리텐션이 최대 50% 오른다.
  단계가 5개를 넘으면 화면당 완료율이 10~15%씩 떨어진다
  ([Playio](https://blog.playio.co/mobile-game-onboarding-retention),
  [Hubapps](https://hubapps.team/blog/mobile-game-retention-strategies))
- **정보 과부하가 리텐션 킬러**다. 온보딩의 원칙은 더하기가 아니라 **빼기**
  ([UX Collective](https://uxdesign.cc/games-ux-building-the-right-onboarding-experience-a6e99cf4aaea),
  [OpenSpace](https://www.openspaceservices.com/blog/mobile-app-development/mobile-app-ux-that-actually-retains-users-guide-to-onboarding-friction-points-and-first-session-design))

우리 상태를 이 기준에 대면 — **"항상 무언가를 향해"가 화면에 없고, 첫 세션이 실패로
시작하며, 건설 시트가 정보 과부하다.**

## 1. 다음에 뭘 할지가 화면에 없다 (치명)

상시 목표란(`#kairo-goal`)이 실제로 보여 주는 것:

```
북한강형 · 물려받은 빠지
자유 플레이
```

**이건 목표가 아니라 판 설정이다.** 진짜 목표는 있다 — 메뉴를 열고 스크롤하면:

```
의뢰 0/16 · 1등급 무허가 빠지 · 동시 40명
첫 손님 0/10명 · 먹거리를 갖추자 0/2개 · 기본 위생 0/3개
✓ 물 위로 3/3개 · 첫 슬라이드 0/1개 · 만족한 한 주 0/70
```

목록은 잘 만들어져 있다. **자리가 틀렸다.** 카이로의 핵심(항상 무언가를 향해)이
2탭 뒤에 숨어 있고, 화면에 상시로 뜨는 자리에는 "자유 플레이"가 있다.

⚠ `자유 플레이` 는 시나리오 이름이다. 시나리오가 자유 플레이면 **목표가 없다는 뜻이
아니라 시나리오 제약이 없다는 뜻**인데, 화면은 전자로 읽힌다.

**의도는 맞았고 자리가 비었다.** `main.ts:1018` 에 이렇게 적혀 있다:

```ts
/** 목표 표시 — "얼마나 남았나"가 안 보이면 시나리오가 목표가 아니다 */
```

목표란은 `시나리오`를 비추게 만들어져 있는데 **기본 시나리오가 자유 플레이**다.
즉 새 판을 시작한 100%의 플레이어가 **빈 목표란을 본다.** 목표란이 비춰야 할 것은
시나리오가 아니라 **의뢰**였다 (`#kairo-quests`, `kairo-hud.ts:158` — `menuBody` 안).

## 2·3. 시작부터 실패로 읽힌다 (치명)

### 브라우저 1주차 결산 실물

```
입장 25명 · 만석으로 돌려보냄 78명 · 매표소를 못 지나감 0명
매출 4만 (ㄴ 입장료 3만) · 유지비 −1만 · 손익 3만
퇴장 만족도 0 · 헛걸음 15명
부족한 것: 운영 (공급 4)
```

**들어온 사람보다 돌려보낸 사람이 3배다.** 첫 주에.

### 헤드리스 8주 (아무것도 안 짓고 — "뭘 할지 모르는 플레이어")

```
주  입장  만석  만족  헛걸음  손익
 1    83     0     0     32    8만
 2    96     4     0    104    9만
 4    92     8     0     95    8만
 8   100     0     0     88    9만
```

**퇴장 만족도가 8주 내내 0이고 헛걸음이 주당 ~100명이다.**
(브라우저 수치와 다른 이유: 브라우저는 1등급 동시 40명 상한이 걸린다. 상한을 빼도
만족도 0 은 그대로다 — 상한 탓이 아니다.)

물려받은 빠지는 시설이 **4개**다. 손님이 와서 갈 곳을 못 찾고 나간다.
설계서(§2)는 "0:00–0:03 물려받은 빠지"로 **시그니처를 5분에 만나게** 한다고 적었는데,
실제로는 **첫 화면부터 만족도 0** 을 본다.

⚠ 이건 밸런스 버그가 아니라 **온보딩 설계 공백**이다. 시작 킷이 "굴러가는 빠지"가
아니라 "실패한 빠지"로 되어 있다. 26·52주 밸런스 경보가 0인 이유는 그 검사가
**중반 성장**만 보기 때문이다 — 1~8주를 보는 검사가 없다.

## 4. 건설 시트가 벽이다 (큼)

한 시트에 **73항목**, 그중 **33개(45%)가 잠김**. 393px 폭에서 스크롤로 훑어야 한다.

카이로는 반대로 간다 — 해금된 것만, 적게. 조사 결과의 "정보 과부하가 리텐션 킬러"에
정확히 해당한다.

⚠ 잠긴 것을 보여 주는 것 자체는 **동기 부여로 쓸 수 있다** (다음 목표가 보인다).
문제는 **비율**과 **자리**다: 45%가 잠긴 채 섞여 있으면 목록이 아니라 소음이 된다.

---

## 5. 주를 누르면 결과가 아니라 질문이 온다 (중간)

측정한 흐름:

```
[한 주] 탭 → 주간 카드(모달) → 선택 → 압축 연출 → 결산 → [계속]
탭 3회 · 4.6초
```

탭 수와 시간 자체는 좋다 (2분 세션에 맞는다). 문제는 **순서**다.
플레이어가 `한 주` 를 누른 이유는 **결과를 보려고**인데 먼저 오는 것은 **질문**이다.
게다가 그 질문은 지난주 결과를 모르는 상태에서 답해야 한다.

## 무엇을 고칠까 — 순서 제안

**초반이 먼저다.** 후반 공백은 진짜지만, 그 앞이 무너져 있으면 후반까지 갈 사람이 없다.

| 순서 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| A | **상시 목표란에 다음 의뢰 하나**를 띄운다 | 가장 싸고 가장 크다. 목록은 이미 있다 — 자리만 옮기면 된다 |
| B | **시작 킷이 굴러가게** 만든다 (만족도 0 탈출) | 첫 세션이 실패로 시작하는 것을 막는다. 시작 시설 구성·정원·동선 재조정 |
| C | **1~8주 검사**를 만든다 | 지금 밸런스 검사는 중반만 본다. 초반이 깨져도 아무도 안 잡는다 |
| D | 건설 시트에서 **잠긴 것을 접는다** | 목록을 목표로 바꾼다 (`다음 등급에 열림` 접이식) |
| E | **결산 → 카드** 순서로 바꾼다 | 결과를 보고 결정하게 |
| F | 후반의 새 축 (원래 문제) | 위가 풀린 뒤 |

⚠ A~E 는 **UI 와 초반 밸런스**이고, F 만 새 시스템이다. 사용자가 "UI 적인 문제일
수도 있다"고 한 직감이 맞았다 — 다섯 중 셋이 "있는 것을 안 보여 준다"는 문제다.
