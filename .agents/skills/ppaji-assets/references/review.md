# Evidence, reports and adoption

Save one fresh run with input/output paths and hashes, chosen method, edits, rejected versions, test commands/results, technical limits, visual judgment and authorization state. Use ordinary JSON/Markdown that later agents can inspect; do not label fabricated results PASS.

Report continuously: original → candidate directions/combinations on the **same floor grid and scale** → detailed line/contact examples → actual game map captures below. No click-per-asset navigation. A synthetic grid board is useful but must say it is synthetic; it does not replace a game screenshot. Preserve original captures before adoption because the live original route may subsequently serve the candidate. Show a working Tailscale100.x URL when available; verify the listener and page rather than promising a dead link.

For runtime claims, verify the actual running checkout/build and provider-selected images, decoded pixels/hash, anchors/density, placement and representative interactions. Avoid writing saves during preview; preserve local state. Do not assume files in a generated directory or an atlas were registered in the game. Explicitly list unreviewed combinations and skipped/occluded measurements.

Technical validation, visual review, user art acceptance and live adoption are separate facts, not four mandatory permission prompts. Existing user approval persists. If adoption is authorized, stage only reviewed IDs, retain rollback images/manifests, preserve registration and native visualSource aliases, update cache-sensitive resources as needed, run relevant contracts, then inspect HTTP-loaded images and actual provider. Keep temporary review UI, hardcoded review paths and symlink dependencies out of production.

If a test fails, retain the failure and fix its cause. A baseline failure may be documented after reproducing on unchanged code; do not update a golden just to pass. Do not claim a full suite passed when it was only a targeted run or was interrupted.

For black-box evaluation of this skill, use a fresh-context worker with only a realistic request, this skill and the needed raw artifacts. Do not provide the expected decision or known solution. Use isolated outputs, execute actual operations when feasible, and distinguish workflow behavior, deterministic replay, new-asset art quality and game integration. Include relevant adverse inputs (missing heading, altered source/hash, malformed geometry, missing contact evidence) and examine resulting files rather than prose keywords alone.

Keep offline decoded RGBA comparison separate from browser canvas comparison across encodings. In the dry-room replay, lossless PNG/WebP decoded identically offline, but browser readback differed on partially transparent pixels only. Record that difference; compare runtime with the same candidate URL/encoding for exact readback, and do not silently weaken thresholds or label the cross-encoding comparison exact.
